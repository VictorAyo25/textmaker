UNIT 10.1 · EXCEPTIONS

What happens when the world misbehaves

By the end of this unit you should be able to explain exception handling and its importance, identify types of exceptions and errors, implement try, catch and finally, use throw and throws, write custom exceptions, and handle file input and output.

MUST-MEMORISE · An exception

An exception is an event that disrupts the normal flow of a program. It is an object representing an error condition.

Handle them because: they prevent program crashes, they let you give a user-friendly error message, and they let the program recover and carry on.

"An object representing an error condition" is worth pausing on. When something goes wrong, Java constructs an object describing it and hands it to you. That is why you can call e.getMessage() on it: it is a thing, with fields, in the sense of Module 6.

MEMORY HOOK: an exception is a note thrown out of a burning building. The method that hit trouble cannot carry on, so it writes down what went wrong and throws it to whoever will catch it. If nobody catches it, the building comes down: F.7's run-time error.

UNIT 10.2 · TRY, CATCH, FINALLY

Saying what you will do about it

SYNTAX · The three blocks
try {    // code that MIGHT throw} catch (SomeException e) {    // runs ONLY if that exception was thrown} finally {    // runs ALWAYS: exception or not, caught or not}
MUST-MEMORISE · The five keywords

try: defines a block that might throw.
catch: catches and handles a specific exception from that block.
finally: always executes afterwards, for cleanup such as closing files.
throw: actually throws an exception, right now. One word, inside a method.
throws: declares that a method might throw, in its signature. It throws nothing itself; it warns the caller.

"What are the main keywords used in Java for handling exceptions, and how do they differ?" is a stated in-text question, and the answer is that card.

MEMORY HOOK: throw is an act; throws is a warning. The s is the difference between doing it and declaring you might. "I throw a ball" versus "this job throws balls at you".

CODE · Multiple catch blocksFROM THE SLIDES
public class MultiCatch {    static void attempt(int which) {        try {            int[] arr = {1, 2, 3};            if (which == 1) System.out.println(arr[5]);       // bad index            if (which == 2) System.out.println(10 / 0);       // bad maths            if (which == 3) System.out.println(Integer.parseInt("abc")); // bad text        } catch (ArrayIndexOutOfBoundsException e) {            System.out.println("  Array index out of bounds!");        } catch (ArithmeticException e) {            System.out.println("  Arithmetic problem: " + e.getMessage());        } catch (Exception e) {            System.out.println("  Something else: " + e.getClass().getSimpleName());        }    }    public static void main(String[] args) {        attempt(1); attempt(2); attempt(3);    }}
Output  Array index out of bounds!
  Arithmetic problem: / by zero
  Something else: NumberFormatException

Only the matching catch block runs. The third call was not an index or arithmetic problem, so it fell through to catch (Exception e), which catches everything because every exception is a subclass of Exception: Module 6's inheritance doing real work.

That third line printed the exception's name because of e.getClass().getSimpleName(). Any object can be asked getClass() for the class it belongs to, and a class can be asked getSimpleName() for its own name with the package left off: NumberFormatException rather than java.lang.NumberFormatException. It is how you report what went wrong when your catch is broad enough that you do not already know. getMessage() answers a different question, the detail (/ by zero), which is why a catch this wide is usually worth printing both.

TRAP · Order your catch blocks narrowest first

Put catch (Exception e) first and the code will not compile: every later catch is unreachable, because the general one already caught everything. Java tells you so.

The rule follows from inheritance: catch the specific before the general, always. A catch for a parent class shadows every child below it.

Your course's slide shows registerUser(15) uncaught, and prints the crash: Exception in thread "main" java.lang.IllegalArgumentException: Age must be 18. That is what happens with no try-catch, and it is worth seeing. Here it is caught, so the program survives and prints a civil message. Same throw, two fates, and the difference is entirely whether anyone was listening.

A custom exception is a user-defined exception class that extends either Exception (for checked) or RuntimeException (for unchecked). Which parent you pick is the decision: it decides whether every caller is forced to handle it. Note checkAge needs throws in its signature and checkScore does not: that is Unit 10.1's table, enforced by the compiler.

That bans PrintWriter, Scanner and all of Files. The 2024/25 paper does the opposite and asks about PrintWriter and Files.write() by name. Know all four pairs.

MUST-MEMORISE · The file I/O shape

Every file operation is the same four steps:

1. open it (constructing the writer/reader opens the file)
2. use it
3. close it, in a finally or with try-with-resources
4. handle IOException, because you have no choice: it is checked.

MEMORY HOOK: a file is a library book. Take it out, read it, and give it back, even if you were interrupted. That last clause is why finally exists.

MUST-MEMORISE · try-with-resources

A try-with-resources block declares the resource in brackets after try, and closes it automatically, whatever happens:

try (FileWriter w = new FileWriter("f.txt")) { ... }

No finally, no close(), no leak. It is the modern way and it is what the 2025/26 paper means by "either in a finally block or via try-with-resources".

"Define try-with-resources block" is asked outright on the 2024/25 paper.

MEMORY HOOK: the resource in the brackets is on loan for the duration of the block. When the block ends, by success or by explosion, Java gives it back for you.

Two sentinel values to memorise, and they are different: read() returns -1 at the end of the file, and readLine() returns null. Both loops use the same trick, while ((x = read()) != sentinel), which assigns and tests in one breath. That idiom appears in every file-reading program you will ever write.

MUST-MEMORISE · The NIO one-liners, and the 24/25 question that asks for them

The four names in those two listings that are not readers or writers at all:

CallWhat it does
Paths.get("data.txt")Turns a file name into a Path, the object the NIO methods take instead of a String.
Files.write(path, lines)Writes every line to the file and closes it, in one call. Creates it if absent; replaces it if present.
Files.readAllBytes(path)Reads the whole file into a byte array in one call. new String(...) around it turns those bytes into text.
Arrays.asList("a", "b")Makes a fixed list out of loose values, because Files.write wants a collection of lines, not one String.

Learn these because the paper asks for them by name. The 24/25 paper, Question Three part A, is: "Define the following: PrintWriter, Files.write() method and try-with-resources block." Three marks for three sentences, and one of them is on this table.

What they are for. They are the whole file operation in one line, with no loop and no close(), because the method opens, works and closes before it returns. That is their appeal and also their limit: they hold the entire file in memory at once, so they suit a settings file and not a five-gigabyte log. The reader-and-writer way further up the page is the one that streams.

MEMORY HOOK: Paths.get names it, Files does it. Everything in java.nio.file takes a Path, and Paths.get is how a String becomes one.

They are not allowed in the 25/26 file question, which names its five permitted classes and none of these are among them. Knowing an API and being allowed to use it are different things: read the restriction before you reach for the shortcut.

TRAP · FileReader.read() returns an int, not a char

It has to. A char has no spare value to mean "the file is over", because every possible char is a legitimate character. So read() widens to int and uses -1, a value no character has, as the end-of-file marker. That is why the loop declares int ch and casts (char) ch to print it.

Declare char ch and the comparison != -1 is never true, and you loop forever on a file that has ended.
