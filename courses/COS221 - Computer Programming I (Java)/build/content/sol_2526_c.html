Q5 A · Conference ticket pricing12 MARKS

The question. Using JOptionPane only, price tickets for a 3-day conference and produce a sales summary, with four methods:

  1. takes a day number, uses a switch to return a base price for Day 1, 2 or 3 (pick any three distinct prices and state them clearly); any other day throws IllegalArgumentException;
  2. takes a tier and days attending, and uses nested if-else to return a discount: Gold 3 days 25%, Gold 1-2 days 15%, Silver 3 days 15%, Silver 1-2 days 5%, Bronze 0%, and any tier that is not "Gold" or "Silver" is Bronze. The nesting must reflect that days are only checked within each tier branch;
  3. takes a base total and a discount percentage, applies it, and returns 50.0 if the result would fall below 50.0 (a price floor);
  4. main(): ask for N attendees; loop N times asking days and tier; sum the day prices into a per-attendee base total; get the discount; get the final price; accumulate total revenue and a count of Gold, Silver and Bronze; then show one summary dialog.
MUST-MEMORISE · Choose prices that let the floor fire

The question lets you pick the three prices. That freedom is a trap with a right answer.

Pick 15000, 12000 and 9000 and part 3's price floor can never fire. The largest possible discount is 25%, so nothing ever falls near 50.0. You will have written a floor you cannot demonstrate and the examiner cannot see work.

Pick 30.0, 25.0 and 20.0 and the floor becomes live: one Gold day is 30, less 15% is 25.50, which is below 50.0, so the method returns 50.0. The 50.0 floor is itself the hint about the scale the examiner had in mind.

MEMORY HOOK: when a question lets you choose the numbers, choose numbers that make every rule visible. A rule that never fires is a rule you cannot be shown to have written correctly.

TEACH · What "nested, not separate" actually means here

Part 2 is unusually explicit: nested if-else, not a switch, not independent if checks, and "the nesting must reflect that days attending is only checked within each tier branch, not as a separate top-level check."

So the shape is forced. The tier decides the branch; the days are examined inside it:

Right answers, wrong structure: days is tested at the top level, four separate times. This is what "not independent checks" forbids.

Why the final else is the whole Bronze rule. "Any tier string that is not Gold or Silver must be treated as Bronze" is not an extra check you add: it is what a bare else already means. Write else if (tier.equals("Bronze")) and you have broken the rule, because "Platinum" would then match nothing and fall through with no discount assigned. The bare else catches Bronze, Platinum, "gold" in lower case, and an empty string, which is exactly what was asked (Unit 4.4).

The same else must also do the counting. If "Platinum" is treated as Bronze for the discount, it is a Bronze attendee in the summary too. Count it anywhere else and your dialog contradicts your own pricing.

TRAP · The switch must return, or fall through

Part 1's method must give back a price for 1, 2 and 3 and throw otherwise. Writing return inside each case is what makes that safe: a return leaves the method immediately, so no break is needed and there is no fall-through to worry about (Unit 4.3).

Use double price; with assignments instead and you must not forget the breaks, and the compiler will additionally complain that price "might not have been initialized" unless every path assigns it. The default: throw is what convinces the compiler every path is covered: an exception is a legitimate way to leave a method that promised to return a double, because it does not return at all.

Note also that throw needs no throws clause here. IllegalArgumentException is unchecked (Unit 10.1), which is Q1 B's distinction being examined a second time on the same paper.

Q5 B · Sustained breaches of a safe limit13 MARKS

The question. A warehouse records its temperature once an hour for 24 hours. A reading is a breach if it is above 8 degrees C. Using JOptionPane only:

  1. prompt 24 times, one dialog per hour. Each input must parse as a number between -20 and 50 inclusive; if invalid, re-prompt for the same hour using a nested loop, until valid. Store all 24 in a 1-D array;
  2. scan the array once, using only loops and conditionals (no extra arrays), to find the number of qualifying streaks (runs of 3 or more consecutive breach-hours) and the length of the longest breach streak;
  3. using nested if-else, classify: CRITICAL if the longest streak is >= 6, WARNING if it is 3 to 5, SAFE if no streak of 3 or more occurred;
  4. show one dialog with the streak count, the longest length, and the classification.
MUST-MEMORISE · Count the run when it turns 3, and measure it as you go

The whole of part 2 is three variables and one pass:

currentRun: breach hours in a row right now, reset to 0 on any non-breach.
longestStreak: updated every breach hour, not at the end of a run.
qualifyingStreaks: incremented when currentRun == 3, exactly.

Why == 3 and not >= 3. A run passes through 3 exactly once, on its third hour. So == 3 counts each qualifying run once, however long it becomes. Use >= 3 and a 6-hour run is counted four times, giving 4 streaks where there is one.

MEMORY HOOK: a run is counted at the moment it qualifies, not while it continues. The threshold is a door you pass through once, not a room you stay in.

TRAP · The streak that is still running when the day ends

The instinct is to close each run in the else, where the non-breach hour is: "the run just ended, so now measure it."

if (readings[hour] > 8) {    currentRun++;} else {    if (currentRun > longestStreak) longestStreak = currentRun;  // only on a NON-breach    if (currentRun >= 3) qualifyingStreaks++;    currentRun = 0;}

It works, until the day ends mid-streak. If hours 18 to 23 are all breaches, the loop finishes with currentRun = 6 and never reaches the else. The longest streak of the day is never measured and never counted. The program reports SAFE on a day the freezer was over temperature for six straight hours.

The fix is not to bolt a copy of the else-block on after the loop. That is the usual patch and it duplicates the logic in two places, so the next edit changes one and forgets the other. Instead, update on every breach hour:

Measure longestStreak as the run grows, and count the run the instant it turns 3. Then a run that is still going when the array ends has already been measured and already been counted, and the end of the array needs no special case at all.

This is worth more than one exam question. A boundary you never treat specially cannot be got wrong at the boundary.

Q6 A · Classify a number by its digit pattern12 MARKS

The question. Using JOptionPane only, classify one positive integer N. Constraints: everything inside main(), using loops and nested/chained if-else and/or switch. No arrays and no user-defined helper methods. Everything inline.

  1. in one loop, built only on % and / (no converting N to a String or array), compute both the digit sum of N and N with its digits reversed;
  2. N is a palindrome if it equals its reversed value;
  3. inline, decide whether the digit sum is prime, testing divisibility only up to its square root;
  4. classify, strictly in this priority order: PALINDROME-PRIME-SUM (palindrome and sum prime), PALINDROME (palindrome, sum not prime), HARSHAD (not a palindrome, but N divides exactly by its digit sum), STANDARD otherwise;
  5. show N, its digit sum, its reversed value and its classification in a single dialog.
MUST-MEMORISE · The digit loop, and the copy that saves it

Peeling digits off a number is three lines you should be able to write without thinking:

int digit = temp % 10;   takes the last digit
reversed = reversed * 10 + digit;   pushes it onto the right of the answer
temp = temp / 10;   drops the last digit

Loop while (temp > 0). Both answers fall out of one pass.

The line the marks hang on is int temp = n;. The loop destroys whatever it walks: temp ends at 0. Walk n itself and by step 2 there is nothing left to compare the reversed value against, and nothing left to divide in step 4. Copy it, consume the copy.

reversed * 10 + digit is worth a moment. Take 4821: the loop pulls 1, then 2, then 8, then 4. Start at 0, and each step shifts what you have one place left and drops the new digit into the units: 1, then 12, then 128, then 1284. The digits come off backwards, which is exactly why pushing them on in the order they arrive reverses the number.

MEMORY HOOK: % takes the last digit, / removes it. Every digit problem in this course is those two lines and a loop.

TEACH · The square root test, without Math.sqrt

Part 3 says test divisibility only up to the square root of the digit sum. The clean way needs no square root at all:

boolean sumIsPrime = (digitSum >= 2);for (int f = 2; f * f <= digitSum; f++) {    if (digitSum % f == 0) { sumIsPrime = false; break; }}

f * f <= digitSum is "f is at most the square root of digitSum", squared on both sides. It stays in whole numbers, so there is no Math.sqrt, no double, and no floating-point comparison to get wrong at the boundary (Unit 3.6).

Why stopping at the square root is correct, not just faster. If digitSum = a * b, then a and b cannot both be above the square root, or their product would exceed digitSum. So every factor pairs with one at or below the square root. Find none there and there are none at all.

And the initialiser is the whole edge case. digitSum >= 2 is what makes 1 not prime and 0 not prime. The loop cannot help you: for digitSum = 1 it never runs, so whatever you started with survives. Start at true and the program declares 1 prime, and then N = 1 (a palindrome with digit sum 1) is misclassified. See the table below, last row.

TRAP · "Priority order" means else-if, not four ifs

Part 4 says checked strictly in this priority order and exactly one category. Both phrases point at the same structure: one chain, where reaching a test means every test above it already failed.

Write four independent ifs and a palindrome with a prime digit sum matches the first, then falls into the others too, and your single dialog reports whichever assignment landed last. The chain is what makes "exactly one" true, and it is also what makes HARSHAD's rule readable: HARSHAD never has to say "and is not a palindrome", because it is only ever reached when the palindrome test failed. The question. Using JOptionPane only, process vehicles exiting on one day and total the fees. Clear separation of concerns: each task must be its own method. No collection classes (e.g. ArrayList) anywhere.

MUST-MEMORISE · Three counts, one return, no collections

Part 3 asks for three numbers back. A Java method returns one value. And ArrayList is banned.

So return an int[] of length 3.

An array is not a collection class. That distinction is the question: "collection classes (e.g. ArrayList)" means java.util's List/Set/Map family. An array is a built-in Java type, not a class you import, which is why F.10 and Module 8 exist and why the ban costs you nothing.

Document the slots in a comment ([0] short, [1] standard, [2] extended) and use them in that order. The alternative the ban is steering you away from is three separate fields or three methods walking the same array three times.

MEMORY HOOK: one return value, several numbers, no collections: that is an array.

TEACH · Parallel arrays, and the invariant that keeps them honest

Two arrays are parallel when index i in one and index i in the other describe the same thing. hoursParked[3] and permitType[3] are one car.

The whole idea rests on one invariant: they are the same length and they are always written together. The loop in part 1 fills both in the same iteration, which is what keeps them aligned. Fill them in two separate loops, or continue past one but not the other, and vehicle 3's hours are paired with vehicle 4's permit. Nothing throws. Every fee is simply wrong.

In Module 6's terms this is what a class is for: a Vehicle object holding hours and permit together cannot fall out of step, because there is no "step" to fall out of. The paper asks for parallel arrays, so write parallel arrays; but knowing what they are the poor relation of is what Q4 was testing.

MUST-MEMORISE · A cap is a ceiling you apply after, not a rule you fold in

Compute the fee, then clamp it:

fee = 6.00 + (hours - 3) * 2.50;
if (fee > 25.00) { fee = 25.00; }

The temptation is to work out the hour at which the cap bites (for Visitors, 10.6 hours) and branch on that. It gives the same answers and it is a worse answer: you have hidden a magic number that no line of the question contains, and changing the rate to 3.00 silently breaks it, because the crossover moves and your constant does not.

This is the same shape as Q5 A's price floor, which is a cap from below. Both read as one line placed after the sum, and both then say plainly what the question said: capped at a maximum of 25.00/day.

MEMORY HOOK: compute, then clamp. Never solve for where the clamp starts.
