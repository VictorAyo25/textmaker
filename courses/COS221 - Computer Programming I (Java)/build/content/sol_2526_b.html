MUST-MEMORISE · Parts i and ii count DIFFERENT things

Part i counts positions. Part ii lists values. They are not the same question asked twice, and they do not give the same number.

Part i asks how many boundaries have a twin across them. Part ii asks which elements are touching a twin at all.

Look at the three 40s. They contain two boundaries (index 3 to 4, and 4 to 5) but three elements. So part i counts 2 there and part ii lists 3. Read the two parts as one question and you will answer one of them wrong.

MEMORY HOOK: fences and posts. Part i counts the fences between posts, part ii counts the posts. A run of n twins has n posts and n-1 fences, always.

TRAP · Three ways to lose marks on part A

1. Starting part i's loop at 0. The question says i >= 1, and for a reason: sales[0 - 1] is sales[-1], which throws ArrayIndexOutOfBoundsException (Unit 8.1). Index 0 has no predecessor, so the loop starts at 1. This is where "one pass" is easiest to get right and easiest to throw away.

2. Forgetting the boundary guards in part ii. Index 0 has no predecessor and the last index has no successor. The guards (i > 0) and (i < sales.length - 1) are what stop the reads from running off either end. They work because && is short-circuit (Unit 3.6): when i > 0 is false, Java never evaluates sales[i - 1], so it never throws. Swap the two sides of the && and the program crashes on the first element.

3. The leading comma. Concatenating ", " + sales[i] every time gives , 20, 20, 40... with a comma stuck on the front. The test if (result.equals("")) writes the first value bare and every later value with its separator in front. Compare Strings with .equals(), never with == (Unit 7.3).

The question bans StringBuilder deliberately: it wants to see that you can handle the separator yourself. Use StringBuilder anyway and you have answered a question the paper did not ask.

TEACH · The five classes, and why the list is exactly these five

The restriction looks arbitrary. It is not: the five are exactly what you need and nothing more (Unit 10.3).

ClassDirectionWhat it is for
FileWriteroutWrites characters to a file. On its own it writes one character at a time.
BufferedWriteroutWraps a FileWriter and collects characters, writing them in blocks. Also gives you newLine().
FileReaderinReads characters from a file. On its own it reads one character at a time: it has no readLine().
BufferedReaderinWraps a FileReader and gives you readLine(), which is the whole reason it is on the list.
IOException-The checked exception every one of the above can throw. You must catch it or declare it (Unit 10.1).

The pairing is the point. The question says "read using FileReader" and "one student per line". A FileReader alone cannot give you a line. So you wrap it: new BufferedReader(new FileReader(fileName)). That is why both appear on the list, and it is why the list is not padding.

And read "or its subclasses" carefully. Those three words are permission. FileNotFoundException is a subclass of IOException, so you are explicitly allowed to catch it separately, which is exactly how you answer part 2's "including the case where output.txt does not exist" with a message that says what actually happened.

TRAP · Catch the child before the parent, or it will not compile

When you catch both, the subclass must come first. Java tries catch blocks top to bottom and takes the first that fits. Put IOException first and it swallows everything, leaving the FileNotFoundException block unreachable. Java does not let that pass:

import java.io.BufferedReader;import java.io.FileNotFoundException;import java.io.FileReader;import java.io.IOException;public class CatchOrder {    public static void main(String[] args) {        try (BufferedReader in = new BufferedReader(new FileReader("any.txt"))) {            System.out.println(in.readLine());        } catch (IOException e) {            System.out.println("the parent is caught first");        } catch (FileNotFoundException e) {            System.out.println("this line can never run");        }    }}
Compiler outputerror: exception FileNotFoundException has already been caught

This is one of Java's friendlier errors: it refuses to compile code containing a block that could never run. Reverse the two catch blocks and it compiles. Specific first, general last, every time.

TEACH · Four decisions in that program worth defending

1. try-with-resources answers part 4 on its own. Writing try (BufferedWriter out = ...) closes the writer automatically, whether the block ends normally or throws (Unit 10.2). The paper allows a finally block instead, and it is worth knowing why the bracket form is better: a close() inside finally can itself throw, and if it does while an earlier exception is already travelling, the second exception replaces the first and the real cause disappears. If you do use finally, the close must sit inside its own try-catch, and it must test for null, because the resource may have failed to open at all.

2. Wrapping means closing one thing, not two. out.close() on the BufferedWriter closes the FileWriter inside it. Closing the wrapper closes what it wraps, so one bracket handles both.

3. countRecords returns -1, not 0, when it fails. The method must "handle its own exceptions internally", so it cannot throw, so it must return something. Return 0 and the caller cannot tell a missing file from an empty one. -1 is impossible as a line count, so it can only mean failure. A value chosen because it cannot be mistaken for a real answer is called a sentinel, and picking a good one is a real skill.

4. Read the last two lines of the output in the right order. "Cannot count output.txt" prints before "output.txt holds -1 records", even though the second is the println that contains the first as an argument. Java evaluates the arguments before it calls the method: countRecords runs to completion, printing its own message, and only then does the outer println receive -1 and print. Argument first, call second, always.

MUST-MEMORISE · The question contains a contradiction, and resolving it is the exam

Part 1 says the balance must be private.

Part 2 says the subclasses must change the balance.

A private field is invisible to a subclass. So the subclass cannot touch it.

This is not the examiner being careless. It is the whole of Units 6.4 and 6.6 arriving in one question: encapsulation says the field is private, and inheritance says the child must still be able to work with it. The way out is the only way out, and it is the answer being marked: the subclass goes through the parent's public methods, using getBalance() to read and super.withdraw(amount) or deposit(amount) to change.

MEMORY HOOK: the child knocks, it does not climb in through the window. getBalance() to look, super.withdraw() to act.

TRAP · A subclass cannot see a private field, and it will say so

The tempting move is to write the arithmetic straight into the subclass. Java stops you at the compiler:

class Account {    private double balance = 5000;}class Saving extends Account {    public boolean withdraw(double amount) {        balance = balance - amount;        return true;    }}public class SubclassReach {    public static void main(String[] args) {        new Saving().withdraw(100);    }}
Compiler outputerror: balance has private access in Account

Private means the declaring class only, and a subclass is a different class. Inheritance gives Saving the field (every Saving object really does contain a balance) but not access to it. The field is there and untouchable, which is exactly what private is for (Unit 6.4).

Would protected fix it? It would compile, and it is the wrong answer here, because part 1 said private. Marks are for doing what the question said. Beyond the exam, going through the parent's methods is better anyway: every rule the parent enforces on a withdrawal keeps being enforced. Make the field protected and each subclass has to remember those rules for itself, which is how a bank ends up with an account that can be overdrawn down one code path and not another. See the access table in Unit 6.6.

TEACH · Why withdraw returns boolean

The paper does not say what withdraw returns, and the obvious choice is void. Then read part 2 ii again: a CurrentAccount adds the reward on every successful withdrawal. Not on every attempt. So the override has to know whether the withdrawal succeeded, and a void method tells it nothing.

Making withdraw return boolean makes the override three honest lines:

boolean succeeded = super.withdraw(amount);if (succeeded) { deposit(50); }return succeeded;

The alternative, comparing the balance before and after, works but is worse: it re-derives an answer the parent already knew and threw away. When a method knows something the caller needs, it should return it. Notice that this decision is forced by a single word in part 2 ii, which is what "read the question" means in practice.

MUST-MEMORISE · How to prove polymorphism in six lines

Part 3 v asks you to confirm the correct overridden version runs. A proof needs a control: change one thing and show the behaviour changes.

So: same reference type, same method, same amount, same starting balance. Only the object differs.

BankAccount acc = new SavingAccount("SA-3003", "Ngozi Eze", 1500.0);acc.withdraw(600.0);        // rejected: would leave 900, under 1000acc = new CurrentAccount("CA-4004", "Tunde Ade", 1500.0);acc.withdraw(600.0);        // allowed, and pays a 50 reward: 950

Both variables are declared BankAccount. Both calls are acc.withdraw(600.0), character for character. Both accounts hold 1500.0. One is refused and one is paid a bonus.

That is the proof, and here is the sentence that earns the mark: the compiler only knew acc was a BankAccount, so the choice of which withdraw to run could not have been made at compile time. It was made at run time, from the object's actual class. That is dynamic method dispatch, and it is what "polymorphism" names (Unit 6.7).

MEMORY HOOK: the reference decides what you may call. The object decides what actually runs.

Compare this with the TRAP at the end of Unit 6.6, where the same setup silently ran the parent's method because the override was really an overload. Same two lines of code, opposite outcomes, and the difference was one parameter type. That is why @Override sits on every override here.
