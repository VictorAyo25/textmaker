F.1 · WHAT A COMPUTER ACTUALLY DOES

A machine that follows instructions, very fast, very literally

Before any Java, one idea. Everything else in this book is built on it.

TEACH · A computer does one thing

A computer takes a list of instructions and performs them, one at a time, in order, exactly as written. That is the whole of it. It is not clever, it does not know what you meant, and it will not fix your mistake for you. It is simply very fast and perfectly obedient.

Those two properties together are why programming is hard. The machine will do precisely what you said, several billion times a second, including the part you got wrong.

TEACH · A program is a recipe you cannot be present for

Think of writing instructions for someone making tea in a kitchen you will never visit, for a person who has no common sense and will not ask questions. "Add milk" is not good enough. How much? Before or after the water? What if there is no milk?

A program is that recipe, written for that person. The skill you are learning is not typing. It is thinking precisely enough that a literal machine cannot misunderstand you.

RECALL AND CHECK

Your program produces the wrong answer. Before you look at anything else, what is the single most likely explanation?

Answer

That the machine did exactly what you told it to do, and you told it the wrong thing. Suspect your instructions before you suspect the computer. In a whole degree you will almost never meet a genuine hardware or compiler fault; you will meet your own logic errors daily.

F.2 · SOURCE CODE

The instructions are just text

TEACH · Source code

Source code is the text you write, in a language with rules strict enough that a machine can read it without guessing. It is ordinary text: you could type it in Notepad. There is nothing magical in the file.

A programming language is that set of rules. Java is one. Python, C and C++ are others. They differ the way natural languages differ: same ideas, different grammar and vocabulary.

TEACH · Why not just write English?

Because English is ambiguous, and a machine cannot resolve ambiguity. "Take the number and add one to it, then double it" has two meanings. Java's grammar exists to make every statement mean exactly one thing.

The price is that Java is unforgiving. A missing semicolon is not a small slip it can overlook; it is a sentence with no full stop, and the compiler refuses to continue. Beginners read this as hostility. It is the opposite: every complaint at compile time is a bug that cannot reach your exam script.

F.3 · FROM YOUR TYPING TO A RUNNING PROGRAM

The compiler, bytecode, and the virtual machine

This section explains the three words your course uses constantly and never defines: compile, bytecode, and JVM. Every one of them is examinable.

TEACH · A processor cannot read Java

The chip in your laptop understands only its own machine code: numbers meaning "add these two", "put this there". It has never heard of System.out.println. Something must translate.

That translator is a compiler: a program whose input is your source code and whose output is something closer to what a machine can run. Java's compiler is called javac, and it comes with the kit you will install in Module 2.

TEACH · Java compiles to bytecode, not to machine code

Here is where Java differs from C, and where most exam confusion lives. javac does not produce machine code for your particular chip. It produces bytecode: instructions for an imaginary computer that does not physically exist.

Bytecode lands in a .class file. It is not readable text and it is not something your processor can run.

TEACH · The JVM is the imaginary computer, made real

The Java Virtual Machine (JVM) is a program that pretends to be that imaginary computer. It reads bytecode instructions and carries them out using the real chip underneath. It is a translator standing between your compiled program and the actual hardware, working while your program runs.

So a Java program runs on a machine that is itself a program. That sounds wasteful, and it costs a little speed. What you buy with it is the single most famous property of the language.

MUST-MEMORISE · WORA, and why it is true

Write Once, Run Anywhere (WORA). You compile your source to bytecode once. That same .class file then runs on Windows, macOS or Linux without being changed or recompiled, because each platform has its own JVM that knows how to translate the same bytecode for its own hardware.

The bytecode is identical everywhere. The JVM is what differs. That single sentence is the answer to "what is the role of the JVM?", which both papers we have ask in some form.

MEMORY HOOK: bytecode is a document written in one language; the JVM is the local interpreter hired in each country. One document, many interpreters, same meaning everywhere.

TEACH · The whole journey, in five steps
StepWhat exists afterwardsWho does it
You typeHello.java, plain textYou, in any editor
CompileHello.class, bytecodejavac Hello.java
Loadbytecode in memory, checked for safetythe JVM
Executeyour program runningthe JVM, using the real chip

You only ever type two of these: javac to compile, then java to run. Everything else happens for you.

TRAP · javac and java are different programs

javac compiles, and its name ends in c for compiler. It takes a file name, with the .java on the end: javac Hello.java.

java runs, and it takes a class name, with no extension at all: java Hello. Not java Hello.java, and not java Hello.class. Both of those fail, and both are typed by almost every beginner in their first hour.

RECALL AND CHECK

Your friend compiles a Java program on a Mac and emails you the .class file. You are on Windows. Does it run, and why?

Answer

Yes. The .class file holds bytecode, which is not specific to any machine or operating system. Your Windows JVM reads that same bytecode and translates it for your hardware. That is WORA, and it is exactly why Java compiles to bytecode instead of machine code.

F.4 · GETTING JAVA ONTO YOUR COMPUTER

Installing the kit, and telling your computer where it is

Do this once, now, before Module 1. Nothing else in this book can be practised until it works, and it is worth marks directly: the setup is examinable.

MUST-MEMORISE · JDK, JRE, JVM

JVM: the virtual machine that runs bytecode. Runs programs.
JRE: the JVM plus the standard library. Everything needed to run a Java program, but not to write one.
JDK: the JRE plus the development tools, above all the compiler javac. Everything needed to write Java.

You install the JDK, because you are a developer, not just a user. Installing the JDK gives you the JRE and the JVM inside it.

MEMORY HOOK: nested Russian dolls, biggest first: JDK > JRE > JVM. The kit contains the environment contains the machine. Developers need the outermost doll.

WORKED EXAMPLE · Installing the JDKDO THIS NOW
  1. Download the JDK installer for your operating system from Oracle's Java downloads page. Any version from 17 upward suits this course. Your course notes point at Oracle. Any build of the same version behaves identically for everything in this book.
  2. Run the installer and accept the default location. On Windows that is C:\Program Files\Java\jdk-<version>. Write that path down. You need it in the next step, and <version> is whatever number you actually installed.
  3. Open a terminal. On Windows press Win+R, type cmd, press Enter.
  4. Type java --version and press Enter. If you see a version number, the installer already set your PATH and you are done. If you see "not recognised", do F.4.1 below.

Now redo it: close the terminal, open a new one, and run javac --version as well. Both commands must answer. If java answers and javac does not, you have installed the JRE instead of the JDK, and you cannot compile anything.

F.4.1 Setting the environment variables

TEACH · What PATH is, and why "not recognised" happens

When you type javac, your terminal does not search your whole hard disk for it. It looks only in a specific list of folders. That list is an environment variable called PATH: a setting that belongs to your operating system rather than to any one program.

"javac is not recognised" almost never means Java is missing. It means Java is installed somewhere your PATH does not mention, so the terminal looked in its usual places, did not find it, and gave up.

JAVA_HOME is a second variable holding the folder where the JDK lives. Java tools read it to find each other, so set it too.

WORKED EXAMPLE · Setting JAVA_HOME and PATH on Windows
  1. Open File Explorer and confirm the JDK folder really exists, for example C:\Program Files\Java\jdk-17. Look inside it for a bin folder containing javac.exe. Never set a path you have not looked at. A typo here produces the exact error you are trying to fix.
  2. Right-click This PC, choose Properties, then Advanced system settings, then Environment Variables.
  3. Under System variables click New. Variable name: JAVA_HOME. Variable value: the JDK folder, C:\Program Files\Java\jdk-17. The folder itself, not its bin. No trailing backslash, no quotes.
  4. In the same list select Path, click Edit, click New, and add %JAVA_HOME%\bin. This is the bin, because that is the folder holding the commands. %JAVA_HOME% means "whatever JAVA_HOME says", so upgrading Java later means changing one setting, not two.
  5. Click OK on all three dialogs. Close every open terminal and open a new one. A terminal reads PATH once, when it starts. This is why it "didn't work" for you and did for the person next to you.
  6. Verify.

TRAP · The three that catch everyone
  • Old terminal. Changing PATH does not affect terminals that are already open. Close and reopen.
  • JAVA_HOME pointing at bin. JAVA_HOME is the JDK folder; PATH gets the \bin. Put bin in both and PATH becomes ...\bin\bin, which exists nowhere.
  • JRE not JDK. java works, javac does not. You installed the thing that runs Java, not the thing that compiles it.

F.6 · THE ANATOMY OF A PROGRAM

Every word in Hello.java, explained

You just typed nine words you were not told the meaning of. That is the last time this book does that. Here is every one.

SYNTAX · The smallest Java program that does anything
public class NAME {                    <- the file must be NAME.java    public static void main(String[] args) {   <- where running begins        your statements, in order    }}
TEACH · class, and why your file has that name

A class is a named container for code. For now that is all you need: Java has nowhere to put a statement except inside a class, so every program has at least one. Module 6 will show you what classes are really for.

public means anything may use it. The rule that catches beginners: a public class must live in a file with exactly its own name. Class Hello goes in Hello.java. Capitals count. Rename the file to hello.java and the compiler refuses it, which is one of the planted errors in your past papers.

TEACH · main, the door in

When you type java Hello, the JVM must decide which line to run first. It does not guess or start at the top. It looks for one exact method:

public static void main(String[] args)

Every word is load-bearing, and the JVM matches it letter for letter:

WordWhat it means
publicVisible to everything, so the JVM (outside your class) is allowed to call it.
staticBelongs to the class itself, so it can be called without creating an object first. Since nothing exists yet when your program starts, it must be static.
voidHands nothing back when it finishes.
mainThe name the JVM looks for. Not Main, not start.
String[] argsA list of text values typed after the class name on the command line. You will rarely use it, and it must still be there.

Get any of it wrong and the program compiles perfectly, then refuses to start: the class is fine, it simply has no door.

MUST-MEMORISE · The main method signature

public static void main(String[] args)

Write it from memory until you cannot get it wrong. You will write it on every program in the exam, and a mangled main costs marks in a question you otherwise answered perfectly.

MEMORY HOOK: say it aloud as one word, in rhythm: "public-static-void-main-string-args". It is a chant, not five decisions.

TEACH · System.out.println, and the semicolon

System.out.println("Hello, world!"); reads right to left as: inside the class System there is out, which represents your screen, and you are asking it to println (print line) the text you gave it.

The double quotes mark a String literal: text meant literally rather than as an instruction. Without them, Java would read Hello as the name of something and complain that it does not exist.

The semicolon ends a statement, as a full stop ends a sentence. Java ignores line breaks entirely, so the semicolon is the only way it knows one instruction has finished. A missing one is the most common compiler error in the world, and it appears as a planted bug on both of your past papers.

TRAP · println versus print

println prints and then moves to a new line. print prints and stays put. Use print and the next output continues on the same line, which is exactly what a past paper's PrintWriter question turns on. When an exam asks for the precise output, this is worth a mark on its own.

F.7 · YOUR FIRST ERRORS

Reading what the compiler is telling you

Both past papers ask you to find errors in code. That is not a trick: it is the actual daily work. Here is how to read a complaint.

MUST-MEMORISE · The two kinds of error

Compile-time error: the code is not legal Java. Nothing runs at all. The compiler tells you the file and line. These are the cheap ones.

Run-time error: the code is legal and the program starts, then hits something impossible and stops. Java calls this throwing an exception. Module 10 handles them properly.

And the dangerous third case, which is not an error at all: a logic error. It compiles, it runs, it finishes, and the answer is wrong. Nothing warns you. Only a dry run (F.9) finds these.

MEMORY HOOK: compile-time is a letter rejected by the post office. Run-time is a letter delivered to a house that has burned down. A logic error is a letter delivered perfectly, to the wrong person, who never tells you.

CODE · Broken on purposeDOES NOT COMPILE
public class Broken {    public static void main(String[] args) {        System.out.println("Hello")    }}
What the compiler saysBroken.java:3: error: ';' expected
        System.out.println("Hello")
                                   ^
1 error

Read it as four facts: the file (Broken.java), the line (3), the complaint (';' expected), and the caret pointing at the exact column. The compiler has told you precisely what to type and where. Most beginners panic at the word "error" and never read the sentence.

TRAP · The line number can lie, but only forwards

A missing semicolon on line 3 is often reported on line 4, because the compiler only realises the sentence never ended when it meets the next word. If line N looks perfect, look at N-1. The compiler is never wrong about that something is wrong; it is sometimes late about where.

RECALL AND CHECK

A program compiles with no errors and runs to completion, but prints 141 when the right answer is 142. Which of the three kinds is this, and which tool finds it?

Answer

A logic error. No tool finds it. The compiler is satisfied and the JVM never complained, because nothing illegal or impossible happened: you simply told the machine to compute the wrong thing. Only tracing the program by hand, a dry run, will locate it. This is exactly what the exam's "find the errors" questions are testing, and why they hand you the correct output.

F.8 · VARIABLES

A named box that holds one value

Module 3 covers types in full. You need enough now to read the rest of Foundations.

TEACH · Variables

A variable is a named box in memory holding one value at a time. You must say what kind of thing goes in the box before you use it, which is called declaring it:

int score = 0;

reads as: make a box called score, allow whole numbers in it, and put 0 in it now. int is the type, score the name, 0 the initial value.

The box holds exactly one value. Putting a new one in destroys the old one.

TRAP · = does not mean equals

In mathematics x = x + 1 is a false statement. In Java it is an instruction, and a perfectly normal one.

= means put the value on the right into the box on the left. So x = x + 1 says: work out what is in x, add one, put the result back in x. Right side first, always.

Java writes "is equal to" as ==. Confusing the two is the most common single-character bug in the language, and both papers plant it.

TEACH · The four types you need right now
TypeHoldsExample
inta whole numberint n = 42;
doublea number with a decimal pointdouble p = 15.5;
booleantrue or false, nothing elseboolean done = false;

String is capitalised and the other three are not. That is not a typo, and Module 6 explains the real reason: the first three are built into the language, while String is a class.

TRAP · int division throws away the remainder

Divide one int by another and Java gives you an int, discarding anything after the decimal point. It does not round; it truncates.

1 / 2 is 0. Not 0.5, not 1. Zero.

This looks like pedantry until you see that a past paper's dry-run question is built entirely on it, and the answer is 0 when every student's instinct says otherwise. F.9 traces exactly that question.

F.9 · THE DRY RUN

Being the computer, on paper

Your lecturer's own word for this is "dry run", and the exam asks for it by name, for marks, on both papers we have. It is also the only way to find a logic error. Learn it now and use it for the rest of the book.

TEACH · The method

A dry run means executing the program by hand, one statement at a time, writing down what every variable holds after every step. No skipping, no "obviously this loops five times". The machine does not skip, so neither do you: the whole point is to catch the step where your assumption and the code part company.

Draw a table. One column per variable, plus one for anything printed. One row per step. Then walk the code.

F.10 · ARRAYS, EARLY AND HONEST

A row of numbered boxes

TEACH · Why this is here and not in Module 8

Your course teaches arrays in Module 8, near the end. But every recent exam puts array problems in Section A, and arrays are the natural thing to loop over when you meet loops in Module 4. Waiting until Module 8 would mean using them before explaining them, which this book does not do.

So here is an honest introduction, enough to read any listing in this book. Module 8 is still where arrays are taught in full: searching, copying, two dimensions, the standard algorithms. This is the floor, not the whole house.

TEACH · An array

An array is a fixed row of boxes, all of the same type, sharing one name and told apart by a number called an index.

int[] nums = {2, 4, 6, 8};

makes four int boxes in a row. int[] means "array of int". You reach one box with square brackets: nums[0] is the first, nums[1] the second.

nums.length is how many boxes there are: 4. It is a property, not a method, so there are no brackets after it.

MUST-MEMORISE · Indexes start at zero

An array of length n has indexes 0 to n-1. There is no nums[n]. The last item is always nums[nums.length - 1].

Reaching outside that range does not give you rubbish or zero: the JVM stops the program with ArrayIndexOutOfBoundsException. Every past paper plants this, usually as i <= arr.length in a loop.

MEMORY HOOK: an index is not "which one" but "how far from the start". The first box is zero steps from the start. So {2,4,6,8} has a box 3 and no box 4.

CODE · Indexes, length, and the edge
public class ArrayBasics {    public static void main(String[] args) {        int[] nums = {2, 4, 6, 8};        System.out.println("length      : " + nums.length);        System.out.println("first  [0]  : " + nums[0]);        System.out.println("last   [3]  : " + nums[nums.length - 1]);        // walk every box: i stops BEFORE length        for (int i = 0; i < nums.length; i++) {            System.out.print(nums[i] + " ");        }        System.out.println();    }}

F.11 · JOPTIONPANE, EARLY AND HONEST

Pop-up boxes, and a promise about what they are

TEACH · Why this is here too

The most recent paper demands JOptionPane for input and output in five of its six questions, sometimes saying "JOptionPane only". You cannot pass that paper without it. It is also a method call on a class from a library, and this book will not pretend that means nothing.

So: here is the pattern, and an honest account of what each word is. The full explanation of classes, objects and libraries is Module 6, and this box will make complete sense then. Until then you may use this as a shape you copy exactly. That is not cheating; it is the order the exam forces on us.

MEMORY HOOK: the dialog is a form, and everything written on a form is handwriting, even the numbers. parse is you reading the handwriting and deciding it is a number.

TRAP · "25" + 1 is not 26

Forget to parse, and + does something perfectly legal and completely wrong. With text on either side, + means join, not add: "25" + 1 is the text "251". It compiles, it runs, it prints nonsense. A logic error, in the sense of F.7, and no tool will warn you.

public class JoinVsAdd {    public static void main(String[] args) {        String typed = "25";              // what a dialog hands you        System.out.println(typed + 1);      // join: WRONG        System.out.println(Integer.parseInt(typed) + 1);   // add: right    }}

TEACH · System.exit(0), and why the exam papers end with it

Look at the end of almost every JOptionPane program on both papers:

JOptionPane.showMessageDialog(null, "Sum: " + sum);System.exit(0);

System.exit(0) ends the whole program immediately, right there, whatever was going to happen next. The number is the exit status that the program hands back to whatever started it, and the convention is older than Java: 0 means it finished normally, and anything else means it failed. That is why the line is System.exit(0) and never System.exit(1).

Why it is there. A plain main ends when its last line runs. A program that has opened a dialog is different: showing one starts extra threads to run the window, and those threads are not finished just because main is. System.exit(0) is the author saying "we are done, stop everything", instead of waiting for the window machinery to decide.

Now the honest part, because you will be told otherwise. You will hear that without System.exit(0) a Swing program hangs forever. We tested it on the JDK this book is built against: after touching Swing, two non-daemon threads (AWT-Shutdown and AWT-EventQueue-0) are indeed still alive when main returns, and the program exited anyway, cleanly. Modern Java shuts that machinery down once no window is left showing. So the line is insurance, not a rescue.

Write it anyway, for the reason that matters in an exam: the paper's own code has it, so it is what the marker expects to see, and it costs one line. But if someone tells you your dialog program will hang without it, that is a claim about a Java old enough to be worth checking.

MEMORY HOOK: exit(0) means "stop now, and nothing went wrong." Zero is success, every other number is a complaint.

TEACH · A note on practising this

JOptionPane opens a real window, so it cannot show its output on a printed page and the listings in this book use System.out.println instead. They are the same program with a different mouth.

When the exam says "JOptionPane only", it means the marks are for the dialogs, so write the dialogs. When you are practising at home and want to see what your loop did, System.out.println is faster. Know both, and read the question.
