Question Four, worked in full

Q4 A · Describe decision-making, looping and branching3 MARKS

Model answer. These are the three families of control structure (Unit 4.1): the statements that decide which code runs and how often, rather than doing the work themselves.

  1. Decision-making. Choosing between paths by testing a condition, so that some code runs and some does not: if, if-else, the if-else ladder, and switch.
  2. Looping (iteration). Repeating a block while a condition holds: for, while and do-while. The do-while is the one that always runs at least once, because it tests at the bottom.
  3. Branching (jumping). Transferring control out of the normal flow: break leaves a loop or a switch case, continue skips to the next iteration, and return leaves the method entirely.

Where the marks are: name the actual keywords. "Looping means repeating" is the idea; "for, while, do-while, and do-while tests at the bottom so it runs at least once" is the answer. Units 4.1 to 4.7.

Q4 B · Debug the while loop3 MARKS

The code as printed:

public class WhileDebugBroken {    public static void main(String[] args) {        int count = 1        float output = "";        while(count <=5); {            output = output + count + " ";            Count        }        System.out.println(output);    }}
Compiler outputerror: ';' expected

The errors, listed.

  1. int count = 1 has no semicolon.
  2. float output = ""; is the wrong type. A float is a number; "" is text. They are not interchangeable and Java will not convert one to the other. Fix: String output = "";
  3. while(count <=5); has a stray semicolon. This is the one worth the mark. That semicolon is the loop body: an empty statement. The block below it then runs once, on its own, as an ordinary block. Since count never changes inside the empty body, the condition stays true forever and the program hangs.
  4. Count is not a statement. Wrong case (Java is case sensitive) and, even spelled right, count alone does nothing. Fix: count++; which is what stops the loop.
TRAP · The semicolon that eats the loop body

while (condition); and for (...); are both legal Java. The semicolon is an empty statement, and an empty statement is a perfectly good loop body. So the compiler says nothing at all.

What you wrote:

while (count <= 5); { ... }

What Java read:

while (count <= 5) { }   then, separately,   { ... }

The braces you meant as the body became a free-floating block that runs once, after the loop finishes. Except the loop never finishes, because nothing inside an empty body can change count.

This exact trap appears twice on this paper: here, and again in Q6 C as for (int i = 0; i <= n; i++);. The examiner is not being subtle about how much they want you to notice it. Whenever a loop misbehaves, look at the character immediately after the closing bracket. Unit 4.5.

The else if only runs when t < 15 was false, which already means t >= 15. So writing else if (t >= 15 && t <= 30) is not wrong, it is redundant: the ladder has already established the lower bound. Let the structure carry what it has proved (Unit 4.2).

Question Five, worked in full

Q5 A · Describe inheritance, polymorphism and method overriding3 MARKS

Model answer.

  1. Inheritance. One class acquiring the fields and methods of another with extends, so the subclass has everything the superclass has without repeating it, and may add or replace behaviour. It models an is-a relationship: a Bicycle is a Vehicle.
  2. Polymorphism. One reference, many behaviours: a variable of the superclass type may hold an object of any subclass, and a call through it runs the object's own version, decided at run time. "Many forms".
  3. Method overriding. A subclass supplying its own version of a method the superclass already has, with the same signature, which replaces the inherited one for objects of that subclass.

Where the marks are: these three are one idea in three parts, and saying so earns the mark. Inheritance makes the family; overriding makes the members differ; polymorphism is what you get when you then hold any of them in one variable and call the method. Distinguish overriding (same signature, subclass, run time) from overloading (different parameters, same class, compile time), which is Q1 of this same paper. Units 6.6 and 6.7.

Now every element is declared Vehicle, the loop body is one identical call, and it still prints two different lines. That is the demonstration, and it is what the last four words are asking for. The listing above does both: the literal answer first, then the proof.

Part iii is the one being marked. A do-while whose condition is false still runs once, and "print 10 once" is the cleanest possible demonstration of that. Choose a condition that is false immediately, and the body still prints.

Q6 D · hasEqualAdjacentPairs7.5 MARKS

The question. Write hasEqualAdjacentPairs(int n) returning true if the positive integer n contains at least two pairs of equal adjacent digits, and false otherwise. Write main to test at least two cases. The paper's examples:

112233 → true (pairs: 11, 22, 33). More than two adjacent pairs.
1223 → true (pairs: 22). Only one pair → return false

TRAP · The paper contradicts itself, and you must answer anyway

Read the second example again. It says "1223 - true" and then, in the same line, "Only one pair - return false". Both cannot be right.

The specification says "at least two pairs". 1223 has one pair, the 22. One is not at least two.

The correct return is false. The leading "true" is a slip of the pen.

The examiner's own explanation ("Only one pair") agrees with the specification, so the specification and the reasoning outvote the stray word. This book shows you the paper exactly as printed and tells you what is true, and it never quietly corrects a source (compare the six errors in Module 3, which come from this course's own slides).

What to do in the hall. Do not agonise, and do not answer the typo. Implement the specification, and write one line saying why: "1223 has only one adjacent pair, so by the stated rule of at least two pairs the method returns false; the 'true' in the example appears to be a typographical error." That sentence costs ten seconds and it protects you whichever way the marking scheme reads, because it proves the answer was a decision and not a mistake.

MEMORY HOOK: when a question contradicts itself, follow the specification and say that you did.

CODE · Q6 D, completeVERIFIED ON THE JVM
public class AdjacentPairs {    // i/ii. true when n has AT LEAST TWO pairs of equal adjacent digits.    public static boolean hasEqualAdjacentPairs(int n) {        int pairs = 0;        int previous = n % 10;        n = n / 10;        while (n > 0) {            int current = n % 10;            if (current == previous) {                pairs++;            }            previous = current;            n = n / 10;        }        return pairs >= 2;    }    // iii b. main testing more than the two cases the question asks for    public static void main(String[] args) {        int[] tests = {112233, 1223, 1122, 111, 123, 7, 122333};        for (int t : tests) {            System.out.println(t + " -> " + hasEqualAdjacentPairs(t));        }    }}

The paper asks for at least two test cases; there are seven, and each earns its place. 112233 and 1223 are the paper's own. 1122 is the boundary: exactly two pairs, so exactly true. 111 asks what a triple counts as. 123 has no pairs and 7 has no adjacent digits at all, so the loop never runs and pairs stays 0.

MUST-MEMORISE · Compare adjacent digits by remembering the last one

Take the last digit before the loop and call it previous. Then each turn: take the new current, compare it with previous, and make current the new previous.

That is the whole technique, and it is the same % 10 and / 10 pair as Q6 A on the 2025/26 paper. The only new idea is carrying one value forward so that each digit can see its neighbour. You never need the digits in an array; you need exactly one of them remembered.

111 gives two pairs, not one. The digits are compared in overlapping pairs: positions 1-2 and 2-3. The middle 1 belongs to both. If you think a triple should count once, that is a different specification, and this one does not say so: it says pairs of equal adjacent digits, and 111 contains two of them.

MEMORY HOOK: to compare neighbours, remember one. Peel a digit, compare, then let it become the memory for the next.
