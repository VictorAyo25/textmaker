MUST-MEMORISE · The five planted errors, both years

Part C plants the same five kinds of error in both Q1 and Q2:

1. Wrong array type: int[] holding decimal literals.
2. Wrong accumulator type: int sum for a decimal total.
3. Off by one: i <= arr.length.
4. Inverted continue: skipping exactly what it should keep.
5. Wrong stop count: the wrong number in the final if.

Check for those five first, in that order, and you will find them in about a minute. They are the same five in both questions and in both years.

MEMORY HOOK: TTOIS: Type, Total, Off-by-one, Inverted, Stop. Read the snippet five times, once per letter, rather than once hoping to spot everything.

Taught inUnits 5.6 and 5.2.
Q1 A · Define method overloading, and the role of the signature2 MARKS

Model answer.

Method overloading is a feature that allows a class to have more than one method with the same name but different parameter lists (differing in the number, types, or order of parameters).

The method signature is a method's name together with its parameter list. Its role in resolution is this: at a call such as add(2, 3), the compiler compares the number, types and order of the arguments written at the call site against the parameter list of every candidate with that name, and selects the one whose signature matches (widening the argument types if no exact match exists). Because the resolution uses only what appears at the call site, and the return type is not part of the signature, the return type plays no role: two methods differing only by return type are rejected by the compiler as a duplicate definition. The choice is therefore made entirely at compile time, which is why overloading is called compile-time (static) polymorphism.

Where the marks are: one for the definition, one for "signature = name + parameter list" and the fact that the return type is excluded. Saying "the compiler picks the right one" without saying how is half an answer. See Units 5.1 and 5.6.

Q1 B · Three differences: checked vs unchecked3 MARKS

Model answer. Three differences, one mark each:

  1. When they are detected. Checked exceptions are checked by the compiler at compile time; unchecked exceptions occur at run time and the compiler does not examine them.
  2. Whether you must handle them. A checked exception must be either caught in a try-catch or declared with throws, or the code will not compile. An unchecked exception carries no such obligation.
  3. What causes them. Checked exceptions represent conditions outside the program's control (a missing file, a failed network call), whereas unchecked exceptions represent programming errors (dereferencing null, a bad index, dividing by zero).

Examples (add them; they cost one line and prove the point): checked: IOException, FileNotFoundException, ClassNotFoundException. Unchecked: NullPointerException, ArrayIndexOutOfBoundsException, ArithmeticException.

Where the marks are: three distinct axes. Writing "one is checked and one is not" three different ways scores one mark. See Unit 10.1.

CODE · Every loop converted, same outputVERIFIED ON THE JVM
public class ArmstrongConverted {    public static void main(String[] args) {        int[] numbers = {370, 371, 372, 407, 408};        // FOR -> WHILE: init out, condition in, update at the bottom        int idx = 0;        while (idx < numbers.length) {            int n = numbers[idx], digits = 0, temp = n, sum = 0;            // WHILE -> FOR: no init needed, temp is the counter            for (; temp > 0; temp /= 10) {                digits++;            }            temp = n;            // WHILE -> FOR            for (; temp > 0; temp /= 10) {                int d = temp % 10, power = 1;                // FOR -> WHILE                int p = 0;                while (p < digits) {                    power *= d;                    p++;                }                sum += power;            }            System.out.println(n + " -> "                + (sum == n ? "ARMSTRONG" : "NOT ARMSTRONG"));            idx++;                      // the update, at the bottom        }    }}

407 -> ARMSTRONG

Identical output to the original. That is the test of a conversion: same program, different clothes.

Two points a marker looks for. The for (; temp > 0; temp /= 10) has an empty initialisation, which is legal and is the honest conversion: the original while had nothing to initialise, because temp already existed. Do not invent a variable to fill the slot. And idx++ sits at the bottom of the while body, which is Unit 4.6's step 3 and the one people forget: leave it out and the program runs forever.

Q2 A · Define encapsulation2 MARKS

Model answer.

Encapsulation is the OOP principle of bundling data (fields) and the methods that operate on them into a single unit (a class), while restricting direct access to some of its components.

In Java it is achieved by declaring the fields private and exposing controlled access through public getter and setter methods. This gives data hiding (unauthorised code cannot read or modify the state), validation (a setter can reject invalid input, for example preventing a negative balance), and flexibility (the internal representation can change without breaking any code that uses the class).

Where the marks are: one for the bundling-plus- restricting definition, one for how it is achieved (private fields, public getters and setters). Add one benefit if you have room. See Unit 6.4.

BREAK IT DOWN · 2025/26 Question Two B

The marks3 marks, one each.

Taught inUnits 5.6 and 8.4.
Q2 B · Three differences: overloading vs overriding3 MARKS

Model answer. Three differences, one mark each:

  1. Where they occur. Overloading happens within a single class: several methods share a name. Overriding happens between a superclass and a subclass: the subclass replaces the inherited method.
  2. The parameter list. Overloaded methods must have different parameter lists. An overriding method must have exactly the same name and parameter list as the one it overrides.
  3. When the method is chosen. Overloading is resolved at compile time by the compiler (static polymorphism); overriding is resolved at run time by the JVM, from the object's actual type (dynamic polymorphism).

Where the marks are: three separate axes. If you have room, add that overriding requires inheritance and overloading does not. See Unit 6.7.
