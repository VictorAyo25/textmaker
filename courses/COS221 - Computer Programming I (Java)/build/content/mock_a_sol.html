MUST-MEMORISE · The compiler counts errors in waves, not in bugs

The number of errors javac prints is not the number of bugs you have. Once the compiler cannot work out what a name or a type means, it stops looking inside it, so the bugs hiding behind that one are simply not reported yet. Fix the front row and a new row appears.

TEACH · Why "list the errors" is never "list what javac printed"

This is why every debug question on both real papers is worth 3 marks and contains four or five errors. The examiner is not counting your ability to read a compiler transcript. You do not have a compiler in the hall. You are being asked to read code the way the compiler cannot: all the way down, including the parts it gives up on.

So read for faults, not for messages, and use F.7's three kinds as your checklist rather than the compiler's list as your answer. Compile-time errors are the ones it reports, and it reports them late and in waves. Run-time errors it never mentions: ReverseArrayBroken's out-of-bounds crash is perfectly legal Java. Logic errors are invisible to the machine entirely, and two of the six snippets above contain one, which is exactly why the exam hands you the correct output: that output is the only instrument that detects them.

MS.2 · MOCK A SOLUTIONS · QUESTION ONE

Question One, worked in full

Q1 A · Formal parameter, actual argument, return type3 MARKS

Model answer.

A formal parameter is the variable named in a method's declaration, inside its brackets. It does not hold a value while the method is not running; it is a name waiting for one, and it exists only inside that method. In public static int cube(int s), the formal parameter is s.

An actual argument is the value written at the call site, which is copied into the formal parameter when the call is made. In cube(side), the actual argument is side, and what reaches s is a copy of its value (Unit 5.4).

The return type is the type of the value a method hands back, written immediately before the method's name. In public static int cube(int s) it is int. A method that returns nothing declares void. The return type is not part of the method signature, which is why two methods cannot differ by return type alone.

Where the marks are: one each. The word doing the work in the first two is copy: parameter is the name, argument is the value, and the value is copied in. Say that and both marks are yours.

TRAP · This question is answerable. Its ancestor was not

Compare this with the 2024/25 paper's Question One D, solved in S.9. That one asked for area overloaded for a circle, a rectangle and a triangle. A circle takes one length, but a rectangle takes two and a triangle takes two, so two of the three overloads have the same signature, area(double, double), and the compiler rejects the class outright with "method area(double,double) is already defined". That question, as printed, cannot be answered as printed.

volume escapes because 1, 2 and 3 lengths are three different counts. That is luck, not design, and it is worth understanding rather than enjoying: overloading resolves on the parameter list alone. Not on the names you give the parameters, not on what you meant, and not on the return type. Two shapes that need the same numbers cannot be overloads, and the fix is to name them rectangleArea and triangleArea, or to make the lists genuinely differ.

RECALL AND CHECK

Why can volume(double side) and volume(double radius, double height) coexist, when area(double, double) twice cannot?

Answer Because the signature is the name plus the parameter list, and one parameter is a different list from two. The two area methods have identical lists, so they have identical signatures, so they are the same method declared twice. What the parameters mean to you is not in the signature.

Question Two, worked in full

Q2 A · Declaration, creation, index, parallel arrays3 MARKS

Model answer.

Array declaration announces a name and its type: int[] a;. It creates no array. It creates a reference variable capable of referring to one, and until something is assigned to it the variable refers to null.

Array creation is what actually makes the array and reserves its elements: a = new int[4];, or the shorthand int[] a = {1, 3, 5, 7}; which declares and creates in one line. The length is fixed at the moment of creation and can never change afterwards.

The index is the position of an element, counted from 0. In an array of length 4 the valid indexes are 0, 1, 2 and 3, so the last index is always length - 1 and a[a.length] is always wrong.

Parallel arrays are two or more arrays of the same length in which the same index refers to the same subject: names[2] and ages[2] are the name and the age of one person. They are the way this course models a record without a class and without a collection.

Where the marks are: the distinction in the first two is the whole point. "Declaration names it, creation makes it." A declaration that is never followed by a creation is exactly the bug in part B.

TRAP · "-4 % 5" is not what you expect, and here it does not matter

-4 % 5 in Java is -4, not 1: the remainder takes the sign of the left operand (Unit 3.6). So the test values[i] % 5 == 0 still correctly rejects -4, because -4 is not 0 either way.

But had the question asked for odd numbers and you had written values[i] % 2 == 1, every negative odd number would have failed the test, because -7 % 2 is -1. That is why this book always writes % 2 != 0 for odd. It is right for negatives; the other is not.

Question Three, worked in full

Q3 A · FileWriter, BufferedReader, checked exception3 MARKS

Model answer.

FileWriter is a class in java.io that writes characters to a file. Constructing one, new FileWriter("log.txt"), creates the file if it does not exist and truncates it if it does; the two-argument form new FileWriter("log.txt", true) appends instead. It writes characters one at a time, which is why it is usually wrapped in something more convenient, such as PrintWriter or BufferedWriter.

BufferedReader is a class in java.io that wraps another reader and reads it in blocks rather than a character at a time. It is worth naming for one method: readLine(), which returns the next line as a String, or null at end of file. That null is the loop's stopping condition.

A checked exception is one the compiler insists you deal with: you must either catch it or declare it with throws, and if you do neither the program does not compile. IOException is the example that matters here. The reasoning is that a missing file is not a programming mistake, it is a fact about the world, so the compiler forces you to have a plan for it. An unchecked exception, such as ArrayIndexOutOfBoundsException, is not policed this way, because it is a bug rather than a circumstance.

Where the marks are: for the third, the phrase "caught or declared, or it will not compile" is the mark. Part B is that sentence with the compiler saying it out loud.

Q3 B · Debug NoteWriterBroken3 MARKS

Four errors, in two families. The compiler reports one.

  1. Line 5: FileWriter("log.txt") has no new. As written, that is a call to a method named FileWriter, which does not exist. A constructor is only a constructor when new is in front of it. This is the only error javac reports: "cannot find symbol: method FileWriter(String)".
  2. Lines 5, 6 and 7 all throw IOException, which is checked, and nothing here catches or declares it. Three errors, one cause. Wrap the work in try (FileWriter out = new FileWriter("log.txt")) { ... } catch (IOException e) { ... }, or declare throws IOException on main.
  3. The file is never closed on the failure path. Even with a catch, a plain out.close() at the end is skipped if write throws. try-with-resources closes it either way, which is exactly why it exists.

What the compiler actually said: one error, about new. The three unreported exception IOException errors are invisible until it is fixed, because until then the compiler does not know what type FileWriter("log.txt") has, so it cannot know what that line throws.

This is the single best illustration on the paper of MS.1's rule. The interesting error, the one the question is really about, is the one the compiler will not tell you about until you have fixed the boring one.

The answer, three lines:

Four things are being tested here at once, and each is worth a mark.

  1. print then println. print("Unit: ") adds no line break, so the 7 lands on the same line and then the line ends. One line, not two.
  2. %.1f of 12.345 is 12.3. One decimal place means the 3 stays and everything after it decides whether it moves. What follows is 45, and 0.045 is less than half of 0.1, so it does not. See the box below, because the reason this is ordinary is itself worth a mark.
  3. %n ends the line after the rate.
  4. %5.2f of 3.14159 is  3.14: two decimals, and then padded to a total width of 5, which is 4 characters wide, so one space goes in front. The line reads Total:, a space from the literal, then a second space from the padding.

And there is no line break after the last one, because printf("Total: %5.2f", ...) has no %n. The file ends without a newline.

MUST-MEMORISE · printf rounds the digits you wrote, half up. You can trust your paper arithmetic

To answer any printf rounding question: take the literal as printed, round it half up to the places asked for, and write that down. That is the answer. Every time.

You may have been told the frightening version: that double is inexact, so %.2f of 1.005 comes out as 1.00 because 1.005 is really stored as 1.00499999999999989. The first half is true. The conclusion is false in Java, and it is worth knowing why, because it is true in some other languages and the folklore travels.

Java's printf does not round the raw binary value. It first takes the shortest decimal that uniquely identifies that double, which for the literal 1.005 is the string 1.005, and rounds that, half up. So it prints 1.01, exactly as your paper arithmetic says.

This was measured, not assumed. Every three-decimal value from 0.001 to 99.999 was formatted with %.2f on a real JVM and compared against both rules:

RuleValues testedDisagreements
round the digits you wrote, half up99,9990
round the stored binary value, half up99,9994,800

Zero. The scary rule is the one that is wrong, and it is wrong about one value in twenty: at 0.015, printf prints 0.02 while the stored value sits just below 0.015 and the folklore predicts 0.01.

MEMORY HOOK: printf reads what you wrote, not what the hardware kept. Unit 3.7's warning about inexact doubles is about arithmetic, where the error accumulates and is real. It is not about displaying a literal.

TRAP · The inexactness is real. It just shows up somewhere else

Do not read the box above as "doubles are fine". They are not, and Unit 3.7 means what it says. The difference is where the damage lands.

Displaying a literal is safe, because printf rounds the decimal you wrote. Comparing and accumulating are not: 0.1 + 0.2 == 0.3 is false, and no formatting rule saves you from that, because the damage happened in the addition, before printf ever saw it.

So the rule has a boundary, and it is this: trust printf to show a value faithfully; never trust == between two doubles.

MUST-MEMORISE · Append lives on the FileWriter, not the PrintWriter

new PrintWriter("books.txt") truncates. There is no append flag on that constructor.

Question Four, worked in full

Q4 A · Counter-controlled, sentinel-controlled, continue3 MARKS

Model answer.

A counter-controlled loop repeats a number of times that is known before the loop starts. It counts. A for loop is its natural shape, because the start, the test and the step sit together on one line: for (int i = 0; i < 8; i++) runs exactly 8 times. It is also called a definite loop.

A sentinel-controlled loop repeats until a particular value arrives to say stop. That value is the sentinel, and it is not data: it is a signal, chosen so it cannot be mistaken for a real reading. Reading lines until readLine() returns null is sentinel-controlled, and so is "keep asking until the user types -1". The number of repetitions is not known in advance, which is why a while is its natural shape. It is also called an indefinite loop.

continue abandons the rest of the current iteration and goes straight to the next one. It does not leave the loop: that is break. In a for loop the update still runs, so continue is safe there; in a while loop it jumps straight back to the test, so if the increment sits below it, the loop never moves again and hangs (Unit 4.7).

Where the marks are: "known in advance" against "known only when it happens" carries the first two. For the third, the distinction from break is the mark: continue skips an iteration, break leaves the loop.

Q4 B · Debug CountUpBroken3 MARKS

  3. Line 6: while (count <= 5); has a stray semicolon. That semicolon is the loop body: an empty statement. The block below it then runs once, on its own, as an ordinary block. Q5 A · super, @Override, runtime polymorphism3 MARKS

Model answer.

super is a keyword that refers to the superclass part of the current object. It has two uses. super(...), as the first statement of a constructor, calls the superclass constructor, which is how a subclass gets the inherited fields initialised. super.method() calls the superclass version of a method that the subclass has overridden, which is how an override extends the original rather than replacing it.

@Override is an annotation placed above a method to state that it is meant to override an inherited one. It changes nothing at run time. Its whole value is that the compiler checks the claim: if the method does not actually override anything, because the name or the parameter list does not match, it is a compile error instead of a silent new method that never gets called.

Runtime polymorphism, also called dynamic method dispatch, is this: the method that runs is chosen by the object's actual class at run time, not by the type of the reference variable at compile time. So an Employee reference holding a Manager runs Manager's displayInfo(). It is what makes overriding useful, and it is the opposite of overloading, which is settled entirely at compile time (Unit 5.6).

Where the marks are: for the third, the sentence that earns it is "the object decides, not the reference". For the second, "the compiler checks it" is the mark; "it makes it override" is wrong, and that is the commonest answer.

MUST-MEMORISE · do-while runs first and asks afterwards

do { ... } while (false); runs its body exactly once.

while (false) { ... } runs its body exactly zero times.

That single difference is the entire reason do-while exists, and "print only the number 10 once" is a question built to test it. Note the semicolon after while (false): a do-while is the one loop that ends in one, and leaving it off is a compile error.

MEMORY HOOK: do first, ask later. A do-while is a shop that lets you in and then checks your ticket. You are always getting in at least once.

MUST-MEMORISE · A stray semicolon after for or while is the body

for (int i = 1; i <= n; i++); is a complete loop with an empty body. The indented block below it is not inside it.

It appears twice on this mock, in Q4 B and Q6 C, and once on the real 2024/25 paper, in its Question Four B and Question Six C. That is not a coincidence: this lecturer plants it deliberately, because it is the purest example of code that compiles and lies.

TRAP · "Strictly" is a whole mark, and 1223 is the test for it

1223 answers false, and the digits never go down. They stop going up: 2 is not strictly less than 2. Write digit > previous instead of digit >= previous and 1223 wrongly answers true, while every other example on the paper still passes. That is one character, one example, one mark.

The single digit 7 is the other test worth writing: the loop body never runs at all, and the method must still answer true. A method that cannot survive a one-digit input is a method that was never traced.

Choose your own test cases the way this book chose these four: one that passes, one that fails on a decrease, one that fails on a tie, and one edge. Two cases were asked for. Four cost you a minute and prove you thought.
