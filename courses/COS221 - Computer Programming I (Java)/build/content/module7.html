UNIT 7.1 · WHAT A STRING IS

An object that behaves like a value

By the end of this unit you should be able to explain strings, perform concatenation, substring extraction and searching, differentiate String, StringBuilder and StringBuffer, and use the mutable classes for efficient manipulation.

MUST-MEMORISE · String

A String is an object representing a sequence of characters (char values) enclosed in double quotes.

It is a final class in the java.lang package. Final means it cannot be subclassed.

"What is a String, and how can you create one?" is a stated in-text question, so this definition is a candidate for the two-mark slot.

MEMORY HOOK: a String is a necklace of chars. The beads are char values (Unit 3.3), each at a numbered position, and the clasp is welded shut: you can read any bead, and you can never swap one.

TEACH · Two ways to create one, and they are not the same

1. String literals, stored in the String Pool:

String s1 = "Hello";String s2 = "Hello";      // REUSES the same object from the String Pool

2. The new keyword, which always builds a fresh object:

String s3 = new String("Hello");String s4 = new String("Hello");   // a SECOND, separate object

The String Pool is a store Java keeps of every literal it has seen. Ask for the literal "Hello" twice and Java hands you the same object both times, because a String can never change, so sharing it is safe. Say new and you have explicitly demanded a new object, so Java makes one, pool or no pool.

This sounds like an implementation detail. It is the reason for Unit 7.3, which is the most important unit in this module.

MUST-MEMORISE · Immutability

Strings are immutable: once created, their value cannot be changed. Any operation that appears to modify a string actually creates a new String object.

"Why are Strings immutable, and what is the implication?" is a stated in-text question. The implication: it improves security and performance (sharing via the pool is safe), but it is inefficient for frequent changes, because every change allocates a new object. That inefficiency is why StringBuilder exists (Unit 7.5).

MEMORY HOOK: a String is printed, not written in pencil. "Editing" it means printing a new page. The old page still exists, unchanged, until nobody is looking at it.

CODE · Immutability, caught in the actFROM THE SLIDES
public class Immutable {    public static void main(String[] args) {        String s = "Java";        s.concat(" Programming");        // result thrown away!        System.out.println("without assignment: " + s);        String t = s.concat(" Programming");  // result kept        System.out.println("with assignment   : " + t);    }}
Outputwithout assignment: Java
with assignment   : Java Programming

s.concat(...) did not fail, and it did not change s. It built a new String and returned it, and because nobody caught the return value, that new String was discarded instantly. This is the practical meaning of immutable: every String method returns a new String and changes nothing. If you do not assign the result, nothing happened.

MUST-MEMORISE · substring: start inclusive, end exclusive

substring(start) gives everything from start to the end.

substring(start, end) gives characters from start up to but NOT including end.

So its length is exactly end - start.

Your course states this plainly ("start is inclusive while end is exclusive") and it is still the thing people get wrong under pressure.

MEMORY HOOK: the same rule as a for loop: for (int i = start; i < end; i++) also stops before end. Java is consistent: an end bound is always a fence you stop at, not a post you include.

TRAP · length vs length()

An array has arr.length, a property, with no brackets (F.10). A String has str.length(), a method, with brackets. A String is an object with methods; an array's length is a plain field.

Get it backwards and it does not compile, so it costs you seconds on a machine and marks on paper. Both papers hand you array and String code in the same question.

UNIT 7.3 · == VERSUS EQUALS · THE FAMOUS ONE

Why comparing text with == destroys programs

This unit is the reason Unit 3.7 told you to remember that == compares values for primitives and references for objects. Here is the bill.

MUST-MEMORISE · Never compare Strings with ==

== on two Strings asks "are these the same object?"

.equals() asks "do these have the same characters?"

You almost always mean the second. Always use .equals() for text.

MEMORY HOOK: == asks "are you living at the same address?"; .equals() asks "do you look the same?". Identical twins in different houses are equal but not ==.

CODE · The whole trap, in five lines of outputVERIFIED ON THE JVM
public class EqualsTrap {    public static void main(String[] args) {        String s1 = "Hello";                 // literal -> String Pool        String s2 = "Hello";                 // literal -> the SAME pooled object        String s3 = new String("Hello");     // new -> a fresh object        String s4 = new String("Hello");     // new -> another fresh object        System.out.println("s1 == s2       : " + (s1 == s2));        System.out.println("s3 == s4       : " + (s3 == s4));        System.out.println("s1 == s3       : " + (s1 == s3));        System.out.println("s1.equals(s3)  : " + s1.equals(s3));    }}
Outputs1 == s2       : true
s3 == s4       : false
s1 == s3       : false
s1.equals(s3)  : true

Every one of those four strings contains "Hello". Read the outputs again.

TRAP · The reason this bug is so vicious

Look at the first line: s1 == s2 is true.

That is what makes this the most famous bug in Java. If == were simply always wrong for Strings, everyone would learn it on day one. Instead it works perfectly whenever both sides are literals, because the pool hands you the same object twice. So you write ==, you test it with literals, it passes, you ship it.

Then a real String arrives, from JOptionPane.showInputDialog, from Scanner, from a file, built by concatenation, and it is a new object, not a pooled literal. Now == is false even though the text matches, your if never fires, and nothing crashes to tell you.

Every user input in your exam is one of those. Question Five's tier is typed by a user. if (tier == "Gold") would be false for a user who typed Gold. tier.equals("Gold") is true. That is the difference between a working program and a zero.

Ignore the number for a second and read the sign. compareTo returns negative if this comes before the other, zero if equal, positive if after. So -32 means "Java" sorts before "java". And the size is not magic: 'J' is 74 and 'j' is 106, so 74 - 106 = -32. It is comparing the char codes of Unit 3.3, and capitals come first.

UNIT 7.4 · STRINGBUILDER AND STRINGBUFFER

When immutability becomes the problem

TEACH · Why they exist

The String class is immutable. Every modification creates a new String object, which can be inefficient when dealing with frequent or large-scale string operations. To overcome this, Java provides two mutable alternatives: StringBuilder and StringBuffer.

Concretely: building a 1000-character string by adding one character at a time with + creates a thousand String objects, each a copy of the last plus one. A StringBuilder edits one buffer in place.

MUST-MEMORISE · The three compared
FeatureStringStringBuilderStringBuffer
MutabilityImmutableMutableMutable
Thread-safeNoNoYes (synchronized)
PerformanceSlow with many modificationsFast (single-threaded)Slower (synchronisation costs)

"When should you use StringBuilder instead of String?" is a stated in-text question. The difference between the two mutable ones is only thread-safety, and its cost is speed.

MEMORY HOOK: Builder is Buffer without the locks. Buffer is safe for many threads and pays for it; Builder assumes you are alone and is faster. Alone is the normal case, so StringBuilder is the default choice.

Outputstart          [Java]

Your course gives only the final answer, Result: gnimmargorP avaJ, which is correct but teaches nothing. The six lines above are the same program printing after every step, and now the double space is explicable: replace(5, 13, "Core ") swapped the eight characters "Language" for the five "Core ", leaving the original space at index 13 next to the new one. It survives every later step and ends up in the middle of the reversed text.

Note also that none of these returned anything you had to keep. sb.append(...) changed sb itself. That is the whole difference from Unit 7.1's concat, which changed nothing and returned everything.

TRAP · Your exam may forbid StringBuilder

2025/26 Question Three asks you to build a comma-separated list and says: "Build this string using plain String concatenation only (no StringBuilder, no array of booleans returned)."

So the efficient tool is banned, on purpose. The examiner is testing that you can do it with + and a loop, and probably that you handle the trailing comma. Read the constraint and obey it: using StringBuilder there scores zero regardless of correctness.

Which is the real lesson of this module: know both, and let the question choose.

WORKED EXAMPLE · Building a list with + and no StringBuilderPAST PAPER · 25/26 Q3 A ii

The classic difficulty is the separator: three items need two commas, not three, and a stray trailing comma looks like a bug to a marker.

  1. Start with an empty String, not null. null + "x" gives the text "nullx". An empty String gives "x".
  2. Before appending an item, append a comma only if the string is not already empty. This is the trick. It puts separators between items rather than after them, and needs no special case for the last one.
  3. Append the item.
public class JoinNoBuilder {    static String join(int[] vals) {        String out = "";                     // empty, never null        for (int i = 0; i < vals.length; i++) {            if (!out.isEmpty()) {                out = out + ", ";           // separator BEFORE, not after            }            out = out + vals[i];        }        return out;    }    public static void main(String[] args) {        System.out.println("three : [" + join(new int[]{20, 40, 60}) + "]");        System.out.println("one   : [" + join(new int[]{20}) + "]");        System.out.println("none  : [" + join(new int[]{}) + "]");    }}
Outputthree : [20, 40, 60]
one   : [20]
none  : []

No trailing comma, and the one-item and empty cases came out right without a single line written for them. Those are the edge cases a marker checks first.

Now redo it: on blank paper, write join from memory. Then say why starting with String out = null; would print null20, 40, 60.
