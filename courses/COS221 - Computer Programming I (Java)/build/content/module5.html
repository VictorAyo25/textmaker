UNIT 5.1 · WHAT A METHOD IS

Write it once, use it everywhere

By the end of this unit you should be able to identify the key parts of a method, define void and non-void methods and call them, compare formal parameters with actual arguments, differentiate static from instance methods, explain parameter passing, and use method overloading.

TEACH · A method

A method is a reusable block of code that performs a specific task. You have been writing one since F.5, called main, and calling others (println, parseInt) all along. This module is about writing your own.

Your course gives three reasons they exist, and an in-text question asks for them:

MUST-MEMORISE · The method signature

A method's signature is its name plus its parameter list (the number, types and order of its parameters).

The return type is NOT part of the signature. Neither is the access modifier, nor the parameter names.

This is not trivia. Your 2025/26 paper asks you to "state precisely the role that the method signature plays in enabling the compiler to resolve an overloaded call at compile time", and your 2024/25 paper asks you to define method signature outright. It is worth marks on both papers we have.

MEMORY HOOK: the signature is what you must write at the call site. When you call add(2, 3) you write the name and the arguments; you never write the return type. So the compiler cannot use what you never wrote. Signature = name + parameters.

UNIT 5.2 · VOID AND NON-VOID METHODS

Methods that do, and methods that answer

MUST-MEMORISE · void versus non-void

Void methods perform actions but do not return any value. Their return type is the keyword void.

Non-void (returning) methods return a value. Their return type is the type of that value, and every path through them must return one.

MEMORY HOOK: void is a command ("print this"), non-void is a question ("what is the square of 5?"). A command needs no answer; a question is not allowed to go unanswered.

CODE · Both kinds, from the slidesFROM THE SLIDES
public class Methods {    // VOID: does something, answers nothing    static void sayHello(String name) {        System.out.println("Hello " + name);    }    // VOID: prints a sum, but does not hand it back    static void printSum(int a, int b) {        System.out.println("The sum of " + a + " and " + b + " is " + (a + b));    }    // NON-VOID: answers, and prints nothing    static int square(int n) {        return n * n;    }    // NON-VOID: builds a String and hands it back    static String getGreeting(String name) {        return "Hello, " + name + "!";    }    public static void main(String[] args) {        sayHello("James");                        // call: nothing comes back        printSum(5, 10);        System.out.println("Square: " + square(5)); // call: use the answer        System.out.println(getGreeting("Oghenetega"));    }}
OutputHello James
The sum of 5 and 10 is 15
Square: 25
Hello, Oghenetega!
TRAP · Printing is not returning

The single most common beginner confusion in this module. printSum and square both "give you a sum", and they are completely different things.

printSum(5, 10) puts text on the screen and evaluates to nothing. You cannot write int x = printSum(5, 10);: it does not compile, because there is no value to put in x.

square(5) puts nothing on the screen and evaluates to 25, which you can store, add to, or print. It is useful to other code; printSum is only useful to a human watching.

Rule of thumb: a method that computes should return, not print. Printing is a decision about presentation, and it belongs to whoever called you. Your exam questions ask for methods that "return the count" and then display it in main: that separation is deliberate and it is marked.

UNIT 5.3 · PARAMETERS AND ARGUMENTS

Two words for two different things

MUST-MEMORISE · Formal parameter vs actual argument

A formal parameter is the variable in the method's declaration: static int square(int n). It is a name for a value that does not exist yet.

An actual argument is the value you pass at the call: square(5). It is a real value, right now.

Your learning outcome says "compare formal parameters with actual arguments", so this distinction is examinable in its own right.

MEMORY HOOK: the parameter is the empty seat; the argument is the passenger. The seat is described when the bus is built; the passenger arrives at departure.

TEACH · Parameterized and non-parameterized

Parameterized methods take one or more parameters to do their work. Non-parameterized methods take none: their brackets are empty.

A non-parameterized method is not useless: it either works on data it can already see, or it fetches something from the outside world. Your course's examples are the date and time, and a random number, neither of which needs you to supply anything.

CODE · Parameterized and notFROM THE SLIDES
public class Params {    // PARAMETERIZED: needs a name and an age to do anything    static String getAgeInfo(int age, String name) {        return name + " is " + age + " years old.";    }    static String getFullName(String first, String last) {        return first + " " + last;    }    // NON-PARAMETERIZED: empty brackets, needs nothing from you    static String banner() {        return "=== report ===";    }    public static void main(String[] args) {        System.out.println(banner());        // 45 and "Blake" are the ACTUAL ARGUMENTS.        // age and name are the FORMAL PARAMETERS.        System.out.println(getAgeInfo(45, "Blake"));        System.out.println("Full Name: " + getFullName("John", "Doe"));    }}
Output=== report ===
Blake is 45 years old.
Full Name: John Doe
TRAP · Arguments go in by position, not by name

getAgeInfo(int age, String name) is called as getAgeInfo(45, "Blake"). Note the order: age first, because that is the order the parameters were declared in, even though the sentence it builds reads "Blake is 45".

Java matches arguments to parameters by position only. The names are for you, not for the compiler. Swap them to getAgeInfo("Blake", 45) and it does not compile, which is lucky: if both parameters were String, it would compile and quietly print "45 is Blake years old."

UNIT 5.4 · PARAMETER PASSING · READ THIS TWICE

What actually crosses the boundary

This unit corrects your course, and the correction is the single most important idea in the module. It is also the most misunderstood topic in all of Java, so if you get this right you are ahead of most graduates.

TEACH · What your course says

"Parameter passing refers to the mechanism of transferring data between methods. The two types are:

  • Pass-by-value (primitive types): a copy of the value is passed. Changes inside the method do not affect the original variable.
  • Pass-by-reference (objects and arrays): changes inside the method affect the original."

The first bullet is right. The second is wrong, and your course's own slides contain the evidence that it is wrong.

MUST-MEMORISE · Java is always pass-by-value

Java is pass-by-value. Always. There is no pass-by-reference in Java.

For a primitive, the value copied is the number.

For an object or array, the value copied is the reference: the address, in the sense of Unit 3.3. So the method gets its own copy of the address, pointing at the same object.

That is why you can change what the address points at (and the caller sees it), but you cannot change which address the caller holds.

MEMORY HOOK: you photocopy your house key and hand over the copy. They can go in and rearrange the furniture, and you will see it. They cannot make your key open a different house. The key was copied; the house was not.

CODE · The proof, in one programVERIFIED ON THE JVM
public class PassByValue {    // a primitive: the NUMBER is copied    static void modifyValue(int n) {        n = 25;        System.out.println("  inside method: " + n);    }    // an array: the REFERENCE is copied. Same array underneath.    static void mutate(int[] a) {        a[0] = 99;                // rearranging the furniture    }    // an array: pointing the COPY of the reference somewhere new    static void reassign(int[] a) {        a = new int[]{7, 7, 7};  // making the copied key open a new house        a[0] = 55;                // caller cannot possibly see this    }    public static void main(String[] args) {        int myNumber = 15;        System.out.println("primitive before: " + myNumber);        modifyValue(myNumber);        System.out.println("primitive after : " + myNumber);        int[] nums = {1, 2, 3};        mutate(nums);        System.out.println("after mutate    : " + nums[0] + "   <- changed");        int[] nums2 = {1, 2, 3};        reassign(nums2);        System.out.println("after reassign  : " + nums2[0] + "    <- UNCHANGED");    }}
Outputprimitive before: 15
  inside method: 25
primitive after : 15
after mutate    : 99   <- changed
after reassign  : 1    <- UNCHANGED

Look at the last line, because it settles the argument. If Java really passed arrays by reference, then reassign would have replaced the caller's array and nums2[0] would be 7. It is 1. The method could reach through its copy of the reference and change the array (mutate), but it could not change which array the caller was holding. That is pass-by-value of a reference, and it is not pass-by-reference.

TRAP · Your course states the evidence and misses the conclusion

Read your own slide again, on the pass-by-reference array example. It says, correctly: "Because arrays are passed by reference, this change affects the original array. However, reassigning the array inside the method [does not affect the original]."

That "however" is the whole thing. It is not an exception to pass-by-reference; it is proof that this was never pass-by-reference. In a language that genuinely has it, reassignment propagates. The slide observed the exact behaviour that disproves its own label, and shrugged.

What to write in the exam. If asked to describe parameter passing, the safe and correct answer covers both: "Java passes all arguments by value. For primitives the value is the data itself, so the method's changes are invisible to the caller. For objects and arrays the value is a copy of the reference, so the method can modify the object the caller sees, but cannot make the caller's variable refer to a different object. Some texts call the second case pass-by-reference; strictly it is passing a reference by value." That is right, it earns the mark, and it shows you know why.

RECALL AND CHECK

What happens when you pass a primitive type to a method? And what one experiment proves Java is not pass-by-reference for arrays?

Answer

Only a copy of the value is used, so any change inside the method does not affect the original variable. The experiment: inside a method, reassign the array parameter to a brand-new array and change that. If Java were pass-by-reference, the caller's variable would now point at the new array. It does not: the caller still sees its original. Only the copy of the reference was redirected.

UNIT 5.5 · STATIC AND INSTANCE METHODS

Belonging to the class, or to an object

MUST-MEMORISE · static versus instance

Static methods belong to the class, not to instances. They can be called without creating an object, and they can only directly access other static methods and variables. Used for utility and helper methods.

Instance (non-static) methods belong to an object. You must create an object with new before you can call one, and they can see that object's own data.

This is why main is static, the loose end from F.6: when your program starts, no object exists yet, so the JVM needs a method it can call without one.

MEMORY HOOK: Math.sqrt(9) needs no object: square roots do not belong to any particular thing. rex.bark() needs Rex: barking belongs to a dog. Static is about the idea; instance is about the thing.

TEACH · Every method you have written so far is static

Your course notes this and it is worth pausing on. Every method in this book until now has carried static, because every one has been called from main without an object in sight.

Module 6 is where objects arrive properly and instance methods become the normal case. The Dog example back in Module 1 already showed one: bark() had no static, which is exactly why it needed a Dog to be called on, and why it could print name.

CODE · Both, and why static cannot see instance dataFROM THE SLIDES

UNIT 5.6 · METHOD OVERLOADING

One name, several methods

MUST-MEMORISE · Overloading

Method overloading is a feature that allows a class to have more than one method with the same name but with different parameter lists.

The compiler picks which one you meant, at compile time, using:

1. the method signature (name + parameter list), and
2. the arguments passed at the call.

This is your 2025/26 Section A, part A, worth two marks, and it wants the "state precisely" part: the compiler matches the types, number and order of the arguments you wrote against each candidate's parameter list, and since the return type is not part of the signature, it plays no role in the decision.

MEMORY HOOK: overloading is one word with several meanings, disambiguated by context, exactly like "run" in English. "Run a race" and "run a program" are different acts; you know which from what follows the verb. The compiler knows from what is in the brackets.

CODE · Overloading, from the slidesFROM THE SLIDES
public class Plus {    static void print(String name) { System.out.println("I am " + name); }    static void print(int age)     { System.out.println("I am " + age        + " years old"); }    static int add(int a, int b)            { return a + b; }    static int add(int a, int b, int c)     { return a + b + c; }    static double add(double a, double b)  { return a + b; }    public static void main(String[] args) {        print("John");        // String -> the first print        print(18);            // int    -> the second print        System.out.println(add(7, 8));       // two ints        System.out.println(add(2, 3, 4));    // three ints        System.out.println(add(1.5, 2.5));   // two doubles    }}

UNIT 5.7 · TYPE PROMOTION

When there is no exact match

MUST-MEMORISE · The promotion order

When an exact type match is not found, Java automatically promotes smaller types to larger ones:

byte → short → int → long → float → double

char → int

"Can Java promote data types automatically in method overloading?" is a stated in-text question. Yes: if no exact match exists, it promotes step by step along that chain until it finds a method that fits.

MEMORY HOOK: promotion only ever goes uphill, towards the bigger box, because a bigger box can always hold a smaller value without losing anything. Java will never quietly go downhill and lose your data: that needs a cast, and you have to ask.

CODE · Promotion, watchedVERIFIED ON THE JVM
public class Promotion {    static void show(int x)    { System.out.println("  show(int) got " + x); }    static void only(double d) { System.out.println("  only(double) got " + d); }    public static void main(String[] args) {        // there is no show(char). 'A' is promoted char -> int.        System.out.println("show('A'):");        show('A');        // there is no only(byte). Promoted byte -> short -> int        // -> long -> float -> double, step by step, until it fits.        byte b = 5;        System.out.println("only(byte 5):");        only(b);        // and the plain arithmetic version of the same rule        char letter = 'A';        System.out.println("letter + 0 = " + (letter + 0));    }}
Outputshow('A'):
  show(int) got 65
only(byte 5):
  only(double) got 5.0
letter + 0 = 65

"65" is the answer to your course's own example: 'A' was promoted to its Unicode value, because there was no method taking a char. This is the same fact as Unit 3.7's letter > num, seen from the other side: a char really is a number, and Java will use that whenever it needs to.

TRAP · An exact match always beats a promotion

Add a show(char) to the listing above and show('A') prints A, not 65. Java promotes only when it has to: it looks for an exact match first, and only widens if none exists.

This is why adding a harmless-looking overload can silently change what your existing calls do. It is also a favourite exam trick: given several overloads, being asked which one runs.
