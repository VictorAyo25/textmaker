UNIT 9.1 · WHAT RECURSION IS

A method that calls itself

By the end of this unit you should be able to explain recursion, write recursive methods, identify base cases and recursive cases, and recognise problems where recursion is advantageous.

TEACH · Recursion

Recursion is a programming technique in which a method calls itself in order to solve a problem.

The problem is broken into smaller sub-problems of the same type, solved independently until they reach a base case, which stops the recursion.

The phrase that does the work is of the same type. Recursion is only available when a smaller version of your problem is the same problem. Finding 5! means finding 4! and multiplying by 5: the sub-problem is another factorial, so factorial can call itself.

MUST-MEMORISE · The two cases

The base case is a condition that stops the recursion. Without one, the method calls itself indefinitely and the program dies with a StackOverflowError.

The recursive case is where the method calls itself, on a smaller input, moving towards the base case.

Every recursive method has both, and every recursive method that works has a recursive case that genuinely gets closer to the base case. Those are the only two things to check, and they are what an exam wants named.

MEMORY HOOK: a staircase. The recursive case is "take one step down, then solve the rest". The base case is the ground: the step where you stop. No ground and you fall forever; steps that do not go downward and you never reach it.

CODE · Factorial, the classicFROM THE SLIDES
public class Factorial {    static int factorial(int n) {        if (n == 0 || n == 1) {      // BASE CASE: stop here            return 1;        }        return n * factorial(n - 1);  // RECURSIVE CASE: smaller n    }    public static void main(String[] args) {        System.out.println("factorial(6) = " + factorial(6));        System.out.println("factorial(3) = " + factorial(3));        System.out.println("factorial(0) = " + factorial(0));    }}
Outputfactorial(6) = 720
factorial(3) = 6
factorial(0) = 1

Note n - 1: that is what makes it smaller. Write factorial(n) there and you have an infinite recursion, because the input never moves towards the base case.

DRY RUN · factorial(3), down and back up

A recursion trace has two halves, and beginners only ever draw the first. Going down, each call waits for the one below it. Coming back up, each answer is multiplied on the way out. Nothing is multiplied until the bottom is reached.

Each recursive call adds a new frame to the call stack until the base case is reached. Then the values are returned back up. The stack is real memory, and that is why an infinite recursion produces a StackOverflowError rather than simply hanging: it runs out of room to remember who is waiting for whom.

public class StackTrace {    static int fact(int n, String pad) {        System.out.println(pad + "-> fact(" + n + ") called");        if (n <= 1) {            System.out.println(pad + "   base case, returning 1");            return 1;        }        int smaller = fact(n - 1, pad + "    ");        int result = n * smaller;        System.out.println(pad + "<- fact(" + n + ") returns " + n + " * "                         + smaller + " = " + result);        return result;    }    public static void main(String[] args) {        fact(4, "");    }}

The shape of the output is the shape of the call stack. Every arrow going right is a call going deeper, and nothing returns until the innermost one hits the base case. Then the answers come back out in reverse order. That V shape is what recursion looks like, and if you can draw it you can trace any recursive question.

TRAP · No base case, or one you never reach

Two ways to recurse forever, and both end in StackOverflowError:

static int bad1(int n) {    return n * bad1(n - 1);        <- no base case at all}static int bad2(int n) {    if (n == 0) return 1;          <- a base case...    return n * bad2(n);            <- ...but n never changes, so never reached}

bad2 is the nastier one, because it looks right: it has a base case, so a careless reader ticks the box. The check is not "is there a base case" but "does every recursive call get closer to it".

And note bad1(-1): even the correct factorial recurses forever on a negative, because n == 0 || n == 1 is never true going down from -1. A base case must catch every way of arriving at the bottom.

UNIT 9.2 · THE STANDARD RECURSIONS

The four your course gives, and the pattern under them

MUST-MEMORISE · The recipe for writing any recursive method

1. Ask when it is trivially over. That is your base case.
2. Assume the method already works for a smaller input. Do not think about how.
3. Say how to build your answer from that smaller answer.
4. Check the smaller input actually moves towards the base case.

Step 2 is the leap everyone struggles with, and it is the whole trick. Writing factorial, you do not trace what factorial(n-1) does. You trust it, and only ask "given (n-1)!, how do I get n!?". The answer is "multiply by n", and you are done.

MEMORY HOOK: trust the smaller you. Recursion feels impossible while you try to hold every level in your head at once. It becomes easy the moment you delegate one level down and refuse to look.

CODE · All four of your course's examplesFROM THE SLIDES
public class Recursions {    // 1. FIBONACCI: f(n) = f(n-1) + f(n-2). TWO base cases.    static int fib(int n) {        if (n == 0) return 0;        if (n == 1) return 1;        return fib(n - 1) + fib(n - 2);    }    // 2. EXPONENTIATION: power(b, e) = b * power(b, e-1)    static int power(int base, int exp) {        if (exp == 0) return 1;          // anything^0 is 1        return base * power(base, exp - 1);    }    // 3. SUM OF NATURALS: sum(n) = n + sum(n-1)    static int sum(int n) {        if (n == 1) return 1;        return n + sum(n - 1);    }    // 4. SUM OF DIGITS: sumDigits(n) = (n % 10) + sumDigits(n / 10)    static int sumDigits(int n) {        if (n == 0) return 0;        return (n % 10) + sumDigits(n / 10);    }    public static void main(String[] args) {        System.out.print("fibonacci: ");        for (int i = 0; i < 8; i++) System.out.print(fib(i) + " ");        System.out.println();        System.out.println("3 raised to power 10: " + power(3, 10));        System.out.println("Sum of first 5 numbers: " + sum(5));        System.out.println("Sum of digits of 12345 is: " + sumDigits(12345));    }}
Outputfibonacci: 0 1 1 2 3 5 8 13
3 raised to power 10: 59049
Sum of first 5 numbers: 15
Sum of digits of 12345 is: 15

Look at sumDigits against Unit 3.6. It is the same % 10 and / 10 pair that walked a number's digits in a loop, said recursively instead: peel the last digit, add it to the answer for the rest. The loop and the recursion are the same idea, which is exactly the point of Unit 9.3.

Note also that fib needs two base cases, because its recursive case reaches two steps back. A recursion needs enough base cases to catch every way of hitting the bottom.

UNIT 9.3 · RECURSION VERSUS ITERATION

When it helps, and when it hurts

TEACH · They are equivalent

Anything you can write with a loop you can write recursively, and the other way round. Your learning outcome asks you to "recognise problems where recursion is advantageous", which means the choice is about clarity and cost, not about possibility.

CODE · The same job, both ways
public class BothWays {    static int factRecursive(int n) {        if (n <= 1) return 1;        return n * factRecursive(n - 1);    }    static int factIterative(int n) {        int result = 1;        for (int i = 2; i <= n; i++) result *= i;        return result;    }    public static void main(String[] args) {        boolean same = true;        for (int n = 0; n <= 12; n++) {            if (factRecursive(n) != factIterative(n)) same = false;        }        System.out.println("recursive(6) = " + factRecursive(6));        System.out.println("iterative(6) = " + factIterative(6));        System.out.println("identical for n = 0 to 12: " + same);    }}
Outputrecursive(6) = 720
iterative(6) = 720
identical for n = 0 to 12: true

MEMORY HOOK: recursion trades memory for clarity. If the clarity is not there, you paid for nothing.

TRAP · Naive Fibonacci is catastrophically slow

The fib in Unit 9.2 is the standard example and it is a terrible program. fib(n) calls itself twice at every level, so the number of calls roughly doubles with each step: fib(40) makes over 300 million calls to compute forty numbers.

It recomputes the same values endlessly: fib(5) computes fib(3) twice, fib(2) three times, and so on down. A loop does it in forty steps.

So Fibonacci is the classic recursion teaching example and a classic case of when not to use recursion in real code. Both facts are worth knowing, and an exam asking "when is recursion advantageous" is asking you to know the difference.

CODE · Counting the wasteVERIFIED ON THE JVM
public class FibCost {    static int calls = 0;    static int fib(int n) {        calls++;                        // count every single call        if (n == 0) return 0;        if (n == 1) return 1;        return fib(n - 1) + fib(n - 2);    }    static int fibLoop(int n) {        int a = 0, b = 1;        for (int i = 0; i < n; i++) { int t = a + b; a = b; b = t; }        return a;    }    public static void main(String[] args) {        for (int n : new int[]{5, 10, 20, 30}) {            calls = 0;            int v = fib(n);            System.out.printf("fib(%2d) = %,-8d recursive calls: %,9d   loop steps: " +                "%d%n",                              n, v, calls, n);        }        System.out.println("loop agrees: " + (fib(20) == fibLoop(20)));    }}
Outputfib( 5) = 5        recursive calls:        15   loop steps: 5
fib(10) = 55       recursive calls:       177   loop steps: 10
fib(20) = 6,765    recursive calls:    21,891   loop steps: 20
fib(30) = 832,040  recursive calls: 2,692,537   loop steps: 30
loop agrees: true

Read the last row. To find the 30th Fibonacci number, the recursion made 2.7 million calls. The loop took 30 steps and got the same answer. The two columns grow at completely different rates, and that gap is the entire argument for knowing when not to recurse.
