UNIT 6.1 · WHAT OOP IS

Organising software around things, not steps

By the end of this unit you should be able to define OOP and describe its purpose, and explain its key principles: classes, objects, encapsulation and abstraction.

TEACH · Object-oriented programming

OOP is a paradigm that organises software design around objects (instances of classes) rather than functions and logic, to model real-world entities.

Compare that with Module 1's imperative paradigm, which organises a program around steps. Both write the same instructions in the end. The difference is what you put at the centre of your thinking: the verbs, or the nouns.

MUST-MEMORISE · The four pillars

Your course lists six key concepts, and says the last four are the pillars of OOP:

i. Class    ii. Object
iii. Encapsulation    iv. Abstraction    v. Inheritance    vi. Polymorphism

Encapsulation: bundle data and methods together, and restrict direct access.
Abstraction: hide the internal detail, show only the essentials.
Inheritance: a class acquires the attributes and behaviour of another.
Polymorphism: different objects respond to the same method call in different ways.

MEMORY HOOK: A PIE: Abstraction, Polymorphism, Inheritance, Encapsulation. Four letters, four pillars, and you will not blank on the list under pressure.

UNIT 6.2 · CLASSES AND OBJECTS

The blueprint and the building

TEACH · Class and object, formally

Module 1 gave you these informally, and the definitions have not changed:

A class is a blueprint or template for creating objects. It defines the structure: the attributes (variables) and the behaviour (methods) an object will have.

An object is a specific instance of a class. Once a class is defined, you create objects from it.

UNIT 6.3 · CONSTRUCTORS

Setting an object up as it is born

MUST-MEMORISE · A constructor

A constructor is a special method used to initialise objects of a class. It is called automatically when an object is created.

Its key features:

1. Its name must be exactly the class name.
2. It has no return type. Not even void.
3. It is called automatically by new.

MEMORY HOOK: a constructor has no return type because it is not a question, it is the act of making the thing. Writing void Car() does not make a constructor; it makes an ordinary method that happens to be named Car, and your object is silently built by the default constructor instead. That is a real bug and hard to see.

TEACH · Default and parameterized

A default constructor takes no parameters. If you do not define any constructor at all, Java automatically provides one, which sets every field to its type's default value (Unit 3.3: 0, false, and null for objects).

A parameterized constructor accepts one or more arguments, letting you initialise an object with specific values at the moment of creation rather than assigning them afterwards.

CODE · All three casesFROM THE SLIDES
// 1. NO constructor written: Java supplies a default oneclass Book {    String title;    int pages;}// 2. A no-argument constructor, written by handclass Car {    String brand;    int year;    Car() {                       // name = class, no return type        brand = "Unknown";        year = 2000;    }}// 3. A parameterized constructorclass Bike {    String brand;    int year;    Bike(String brand, int year) {        this.brand = brand;         // 'this' = the object being built        this.year = year;    }}public class Constructors {    public static void main(String[] args) {        Book b = new Book();        System.out.println("Book  : " + b.title + ", " + b.pages);        Car c = new Car();        System.out.println("Car   : " + c.brand + ", " + c.year);        Bike k = new Bike("Trek", 2024);        System.out.println("Bike  : " + k.brand + ", " + k.year);    }}
OutputBook  : null, 0
Car   : Unknown, 2000
Bike  : Trek, 2024

The Book line is the one to study: null and 0. Nobody wrote those. Java's supplied default constructor filled each field with its type's default, and null for a String is exactly the value that will throw a NullPointerException the moment anyone uses it. This is why parameterized constructors exist.

MUST-MEMORISE · this

this refers to the object the method is currently running on.

this.brand = brand; means "the field called brand belonging to this object = the parameter called brand".

It is needed exactly when a parameter has the same name as a field, which is the normal case in a constructor, because both want the same obvious name. Without this, brand = brand assigns the parameter to itself and the field stays null. It compiles. It runs. It does nothing.

MEMORY HOOK: the nearer name always wins, and the parameter is nearer. this. is how you say "no, I mean my one".

TRAP · Writing a constructor removes the free one

Java supplies a default constructor only if you write no constructor at all. Add a parameterized one and the free no-argument version vanishes.

So a class with only Bike(String, int) cannot be built with new Bike(): it does not compile. If you want both, write both. This bites hardest in inheritance, in Unit 6.6, where a superclass with only a parameterized constructor forces every subclass to call it explicitly.

UNIT 6.4 · ENCAPSULATION

Private data, public doors

MUST-MEMORISE · Encapsulation

Encapsulation is the mechanism of bundling data (fields) and methods (behaviour) into a single unit (a class), while restricting direct access to some components.

You achieve it in two moves:

1. declare the fields private;
2. provide public getter and setter methods for controlled access.

"Define encapsulation as an OOP principle" is 2025/26 Section A, Question Two, part A, for two marks. Learn the sentence in the card, verbatim.

MEMORY HOOK: a cash machine. The money and the ledger are sealed inside; you interact only through the slot and the keypad. The bank does not trust you with a door into the safe, and the slot can refuse you.

TEACH · Why bother
ReasonMeans
Data hidingprevents unauthorised access or modification
Validationsetters can check input, for example preventing a negative balance
Flexibilitythe internals can change without breaking anyone who uses the class

Validation is the one that makes it concrete. A public double balance; can be set to -5000 by anybody, from anywhere, and the class is powerless. A private field with a setter means every change must pass through code you wrote, so the object can refuse to enter an impossible state.

CODE · Encapsulation, and what it preventsFROM THE SLIDES

UNIT 6.5 · ABSTRACTION

Showing what, hiding how

MUST-MEMORISE · Abstraction, and how it differs from encapsulation

Abstraction is the process of hiding internal implementation details and showing only the essential features of an object.

The pair everyone confuses:
Encapsulation hides DATA, using private fields and public methods. It is about protection.
Abstraction hides COMPLEXITY, using simple methods, abstract classes and interfaces. It is about simplicity.

MEMORY HOOK: a car. Encapsulation is the locked bonnet: you cannot reach the engine. Abstraction is the steering wheel: you do not need to. One says "you may not", the other says "you need not".

CODE · Method-level abstractionFROM THE SLIDES
class Car {    // the messy detail: private, and none of the driver's business    private void turnOnEngine()  { System.out.println("  engine on"); }    private void checkFuel()    { System.out.println("  fuel checked"); }    private void startIgnition() { System.out.println("  ignition started"); }    public void start() {         // the whole interface the driver needs        checkFuel();        turnOnEngine();        startIgnition();        System.out.println("Car started.");    }}public class CarStartSystem {    public static void main(String[] args) {        new Car().start();          // one word. That is the point.    }}
Output  fuel checked
  engine on
  ignition started
Car started.

The caller wrote start() and nothing else. Three private steps ran, in an order the caller never had to know, and could not have got wrong. "How does abstraction simplify code for users?" is a stated in-text question, and this listing is the answer.

TEACH · Abstract classes and interfaces

Two stronger tools, both about promising what without saying how.

An abstract class cannot be instantiated directly. It provides partial implementation of some methods and leaves others abstract, for subclasses to fill in.

An interface defines a set of methods that any implementing class must implement, without specifying how they work.

MUST-MEMORISE · Interface versus abstract class

"What is the difference between an abstract class and an interface?" and "when should you use an interface instead of an abstract class?" are both stated in-text questions.

MEMORY HOOK: an abstract class is what a thing is; an interface is what a thing can do. A Dog is an Animal (only one of those). A Dog can Swim, and Run, and Fetch (as many as you like). Hence one extends and many implements.

UNIT 6.6 · INHERITANCE

Getting behaviour for free

By the end of this unit you should be able to explain and implement inheritance, apply polymorphism, differentiate overriding from overloading, and understand access modifiers.

MUST-MEMORISE · Inheritance

Inheritance allows a class (the subclass, derived class or child class) to inherit attributes and behaviour from another class (the superclass, base class or parent class).

The keyword is extends:

class Dog extends Animal { ... }

Benefits: code reuse, extensibility, and hierarchical design.

MEMORY HOOK: the is-a test. A Dog is an Animal, so Dog extends Animal. A Car is not a Engine, it has one, so that is a field, not inheritance. If "is-a" sounds wrong out loud, do not use extends.

TRAP · The keyword is extends, with an s

Your course's slide titles it "The extend keyword". It is extends. Java has no keyword extend, and class Dog extend Animal does not compile.

Worth knowing because a debug question could plant exactly this, and because a wrong keyword in a written exam answer is a wrong answer.

TEACH · The three types of inheritance

You may notice one missing: multiple inheritance, where a class has two superclasses. Java does not allow it for classes, which is exactly why a class may only extend one thing but may implement many interfaces.

MUST-MEMORISE · super

super is a reference to the immediate superclass. Two uses:

1. super(args): call the superclass constructor. Must be the first statement in the subclass constructor.

2. super.method(): call the superclass's version of a method you have overridden.

If you do not call it explicitly, Java automatically invokes the superclass's no-argument constructor. And if the superclass has no no-argument constructor, the subclass must call a parameterized one with super(arguments), or it will not compile. That is Unit 6.3's trap arriving with consequences.

MEMORY HOOK: you cannot build the first floor before the ground floor. The superclass part of the object must exist before the subclass part, which is why super(...) must come first.

CODE · Both uses of superFROM THE SLIDES

Read the order. The Vehicle constructor ran before the Car constructor, even though you wrote new Car(...): ground floor first. Then start() printed the Car line and the Vehicle line, because super.start() reached back to the version it had replaced.

SYNTAX · @Override

Written on the line directly above a method that is meant to override one:

@Overridepublic void withdraw(double amount) { ... }

It changes nothing about how the program runs. It is a note to the compiler, and it asks one question: does this method really override something? If the answer is no, the code does not compile.

Java does not require it. Overriding works without it, and the exam will not fail you for leaving it out. Write it anyway. The next box shows why.

TRAP · The override that silently was not one

An overriding method must have the same name and the same parameter list as the one it replaces. Change the parameter type by one word and you have not overridden anything: you have written an overload (Unit 5.6), a second, unrelated method that merely shares a name. Nothing warns you.

Here Account.withdraw takes a double and Saving.withdraw takes an int:

class Account {    protected double balance = 5000;    public void withdraw(double amount) {        balance -= amount;        System.out.println("Account.withdraw ran. Balance is now " + balance);    }}class Saving extends Account {    // MEANT to override Account.withdraw. Look hard at the parameter type.    public void withdraw(int amount) {        System.out.println("Saving.withdraw ran: the 1000 rule was applied");    }}public class SilentOverload {    public static void main(String[] args) {        Account acc = new Saving();        acc.withdraw(600);        System.out.println("Did the saving rule run? Read the line above.");    }}
OutputAccount.withdraw ran. Balance is now 4400.0
Did the saving rule run? Read the line above.

The saving rule never ran. The money left the account with no rule applied, and the program printed no error, because as far as Java is concerned nothing went wrong. This is the worst kind of bug: a silent one.

Why it happens. The variable is declared Account acc, so at compile time the compiler sees only the methods Account has, and the only withdraw there takes a double. So it compiles the call as withdraw(double), widening the literal 600 to 600.0 (Unit 3.5). At run time, Java looks for an override of withdraw(double) in Saving. There is not one: Saving has withdraw(int), which is a different method. So the parent's version runs.

Overloading is chosen at compile time, from the type the variable is DECLARED as. Overriding is chosen at run time, from the type the object ACTUALLY is. Confuse the two and you get exactly this: a method that looks overridden and is not.

Now add @Override to the same broken method. The compiler is obliged to check the claim, and the claim is false:

class Account {    protected double balance = 5000;    public void withdraw(double amount) {        balance -= amount;    }}class Saving extends Account {    @Override    public void withdraw(int amount) {        System.out.println("the 1000 rule was applied");    }}public class OverrideCaught {    public static void main(String[] args) {        new Saving().withdraw(600);    }}
Compiler outputerror: method does not override or implement a method from a supertype

The silent runtime bug became a loud compile-time error, which is the trade you always want. One word turned a bug you would have hunted for an hour into a message that names the problem.

MEMORY HOOK: @Override is a claim the compiler checks. Make the claim, and Java will tell you when you are wrong.

UNIT 6.7 · POLYMORPHISM

One call, many behaviours

MUST-MEMORISE · Polymorphism and its two types

Polymorphism is the ability of different objects to respond to the same method in different ways. It lets objects be treated as instances of their parent class rather than their actual class.

Compile-time (static) polymorphism is achieved through method overloading. Which method runs is decided by the compiler.

Runtime (dynamic) polymorphism is achieved through method overriding. Which method runs is decided by the JVM, from the object's actual type, while the program runs.

MEMORY HOOK: the names say when the decision is made. Overloading is decided by reading; overriding is decided by running. The compiler can see which add() you wrote; only the running program knows whether that Animal variable is holding a Dog.

TEACH · Why the exam keeps asking for this shape

Your 2025/26 Question Four ends: "Demonstrates polymorphism by storing each object in a BankAccount reference and calling the withdrawal method through it, confirming that the correct overridden version runs."

That sentence is describing exactly the listing above. The marks are for three things: the declared type is the parent, the object is the child, and calling through the parent reference still runs the child's method. If you write SavingAccount s = new SavingAccount(); you have not demonstrated polymorphism, even though the right method runs: the point is lost, and so is the mark.

Write BankAccount acc = new SavingAccount();. That single line is the whole demonstration.

RECALL AND CHECK

Given Appliance a = new Microwave();, which operate() runs, and which type decides: the declared type or the actual object?

Answer

Microwave's. The actual object decides, at run time. The declared type (Appliance) decides only which methods you are allowed to call at compile time; among those, the object decides which version actually runs. That split is the whole of runtime polymorphism.
