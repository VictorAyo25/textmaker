UNIT 4.1 · WHAT CONTROL STRUCTURES ARE

Three ways to stop running in a straight line

By the end of this unit you should be able to define control structures and explain their purpose, identify and describe their types, and use conditional statements (if, if-else, if-else-if, switch and the ternary operator) to manage program flow.

TEACH · Control structures

Control structures are special instructions that manage the flow of execution in a program. They let it make decisions, repeat actions, or choose between paths based on conditions.

By default, code executes linearly, from top to bottom. Every program you have written so far did exactly that. A control structure is how you break that line.

MUST-MEMORISE · The three categories

1. Selection (decision making): executes different code based on conditions. if, if-else, switch.

2. Iteration (loops): repeats a block of code. for, while, do-while.

3. Jump (branching): transfers control elsewhere. break, continue, return.

"What are control structures in Java, and why are they important?" is a stated in-text question. Answer with the definition, then the three categories, then why: they let a program make decisions, repeat actions, and control which parts run.

MEMORY HOOK: choose, repeat, escape. Selection chooses, iteration repeats, jumping escapes. Everything a program does with its own flow is one of those three.

UNIT 4.2 · IF, IF-ELSE, AND THE LADDER

Choosing

SYNTAX · The three shapes
if (condition) {                 <- runs only when condition is true    // code}if (condition) {                 <- one block or the other, never both    // runs if true} else {    // runs if false}if (condition1) {                <- the else-if ladder: FIRST match wins    // runs if condition1} else if (condition2) {         <- only tested if condition1 was false    // runs if condition2} else {    // runs if nothing above matched}
TEACH · The condition is a boolean, and only a boolean

Whatever is inside the brackets must evaluate to true or false. That is why Unit 3.7's relational operators exist: they turn numbers into the booleans that if eats.

If you have come from C or Python, note that Java will not accept a number here. if (5) does not compile. This is a mercy: it makes the classic if (x = 5) typo, assignment instead of comparison, a compile error rather than a silent bug.

CODE · The else-if ladderFROM THE SLIDES
public class IfElseStatementTwo {    public static void main(String[] args) {        int score = 75;        if (score >= 90) {            System.out.println("Your grade is A");        } else if (score >= 80) {            System.out.println("Your grade is B");        } else if (score >= 70) {            System.out.println("Your grade is C");        } else if (score >= 60) {            System.out.println("Your grade is D");        } else {            System.out.println("Your grade is F");        }    }}
OutputYour grade is C
MUST-MEMORISE · A ladder stops at the first true

In an else if ladder, the first condition that is true wins, and nothing below it is even tested. Exactly one branch runs.

This is why the ladder above needs no upper bounds. score >= 70 would be true for 95 as well, but 95 never reaches that rung: it matched >= 90 three lines earlier and the ladder stopped.

It follows that order is everything. Write the same ladder with score >= 60 first and every score above 60 gets a D.

MEMORY HOOK: a ladder is climbed from the top and you get off at the first rung that holds you. Put the hardest condition first.

TRAP · A ladder is not the same as separate ifs

Replace every else if above with a plain if and the program still compiles, still runs, and prints two grades for a score of 75: C and D. Each if is now an independent question, so all of them get asked, and 75 answers yes to two of them.

This is not a small stylistic point. Your 2025/26 paper's Section C explicitly demands nested if-else "not independent/separate if checks", and says so twice, in two different questions. Unit 4.4 is about exactly this.

CODE · The same ladder, broken into separate ifs
public class SeparateIfs {    public static void main(String[] args) {        int score = 75;        // every 'else' removed. Each if is now its own question.        if (score >= 90) { System.out.println("A"); }        if (score >= 80) { System.out.println("B"); }        if (score >= 70) { System.out.println("C"); }        if (score >= 60) { System.out.println("D"); }        else            { System.out.println("F"); }    }}
OutputC
D

Two grades for one student, and the else now belongs only to the last if, so F is correctly skipped but for the wrong reason. Nothing crashed. Nothing warned. A logic error, in the sense of F.7, and it is exactly what the exam is guarding against when it insists on nesting.

UNIT 4.3 · THE SWITCH STATEMENT

Many cases, one expression, and the fall-through trap

TEACH · switch

The switch statement streamlines multiple if-else checks by evaluating an expression once and executing the block that matches the corresponding case value.

That is the difference from a ladder, and it is the answer to the stated in-text question "how does switch differ from an if-else ladder?": a ladder evaluates a new condition at every rung; a switch evaluates one expression once and jumps straight to the matching case.

The price is that a switch can only compare for equality against constant values. You cannot write case score >= 90:. Ranges need a ladder; exact values suit a switch.

SYNTAX · switch
switch (expression) {            <- evaluated ONCE    case value1:        // code        break;                   <- jumps out of the whole switch    case value2:        // code        break;    default:                     <- when nothing matched        // code        break;}
CODE · switch on an intFROM THE SLIDES
public class Switch1 {    public static void main(String[] args) {        int category = 1;        switch (category) {            case 1:                System.out.println("Pre-teen");                break;            case 2:                System.out.println("Teenager");                break;            case 3:                System.out.println("Adult");                break;            default:                System.out.println("Senior Adult!");                break;        }    }}
OutputPre-teen
CODE · switch on a StringFROM THE SLIDES
public class SwitchStringExample {    public static void main(String[] args) {        String level = "intermediate";        switch (level) {            case "beginner":                System.out.println("Welcome, beginner!");                break;            case "intermediate":                System.out.println("You're doing well!");                break;            case "advanced":                System.out.println("You're almost an expert!");                break;            default:                System.out.println("Unknown level.");        }    }}
OutputYou're doing well!

A switch works on int (and the smaller integer types), char, String and enums. Note the last break is missing here and it does not matter: default is last, so there is nothing to fall into. Write it anyway, out of habit, because the day you add a case below it the habit saves you.

MUST-MEMORISE · Fall-through

break terminates a case, jumping immediately to the end of the switch block.

Without a break, the program continues executing the subsequent case(s), a behaviour known as fall-through, until it meets a break or reaches the end of the switch.

Read that carefully, because it is stranger than it looks. Fall-through does not re-test the next case. Once a case matches, execution simply keeps going downward through the code, ignoring the case labels entirely, until something stops it.

MEMORY HOOK: case is a door in, not a box. You enter at the matching door and keep walking. break is the way out. No break, and you walk through every room after yours.

CODE · Fall-through, seenRUN THIS ONE TWICE
public class FallThrough {    static void withBreaks(int c) {        System.out.print("  with breaks, c=" + c + " -> ");        switch (c) {            case 1: System.out.print("one "); break;            case 2: System.out.print("two "); break;            case 3: System.out.print("three "); break;        }        System.out.println();    }    static void noBreaks(int c) {          // every break removed        System.out.print("  no breaks,   c=" + c + " -> ");        switch (c) {            case 1: System.out.print("one ");            case 2: System.out.print("two ");            case 3: System.out.print("three ");        }        System.out.println();    }    public static void main(String[] args) {        withBreaks(1); withBreaks(2); withBreaks(3);        noBreaks(1);   noBreaks(2);   noBreaks(3);    }}
Output  with breaks, c=1 -> one
  with breaks, c=2 -> two
  with breaks, c=3 -> three
  no breaks,   c=1 -> one two three
  no breaks,   c=2 -> two three
  no breaks,   c=3 -> three

Look at c=1 without breaks: it printed "one two three". It did not test case 2 and decide 1 equals 2. It entered at case 1 and kept walking. And c=3 printed only "three", because there was nothing below to fall into. The damage depends entirely on how far down the door is.

TEACH · Fall-through on purpose

Fall-through is a trap, not a bug: it is deliberate, and occasionally it is exactly what you want. Stacking cases with no code between them is the standard way to say "any of these":

switch (day) {    case 6:    case 7:                          <- 6 falls straight into 7        System.out.println("Weekend");        break;    default:        System.out.println("Weekday");}

Case 6 has no body, so it falls into case 7, and both print "Weekend". This is idiomatic and every Java programmer reads it instantly.

RECALL AND CHECK

What is the purpose of the switch statement, and how does it differ from an if-else ladder? Give one thing a ladder can do that a switch cannot.

Answer

A switch streamlines multiple if-else checks by evaluating one expression once and executing the block matching that value. A ladder evaluates a separate condition at each rung; a switch evaluates a single expression and jumps to the matching case. A ladder can test ranges and any boolean condition (score >= 90, a && b); a switch can only compare the expression for equality against constant values.

UNIT 4.4 · NESTED IF · THE ONE THE EXAM DEMANDS

Conditions inside conditions

TEACH · Nested if

Nested if statements occur when an if or else block contains another if or else statement inside it. This lets you test conditions hierarchically: check complex conditions that depend on multiple criteria, and act differently on each combination.

The word that matters is hierarchically. The inner question is only asked when the outer one has already been answered, which means the inner question can assume the outer is true.

CODE · Positive, then even or oddFROM THE SLIDES
public class NestedIf {    public static void main(String[] args) {        int number = 10;        if (number > 0) {                     // outer: is it positive?            if (number % 2 == 0) {            // inner: only asked if positive                System.out.println(number + " is positive and even");            } else {                System.out.println(number + " is positive and odd");            }        } else {            System.out.println(number + " is not positive");        }    }}
Output10 is positive and even
MUST-MEMORISE · Nested is not the same as combined

Nested: the inner condition is asked only inside the outer branch. Each branch can do something different, including doing nothing.

Combined with &&: one flat question. You get one answer, true or false, and you lose the ability to distinguish which part failed.

Your 2025/26 paper insists on nesting in Section C, twice, and it explains why in its own words: "the nesting must reflect that days attending is only checked within each tier branch, not as a separate top-level check". Marks are awarded for the structure, not just the answer.

MEMORY HOOK: nesting is a conversation: "are you Gold? Then how many days?" Combining is a form: "tick if Gold and three days." The conversation can respond differently to each answer.

WORKED EXAMPLE · The exam's own discount table, nested properlyPAST PAPER · 25/26 Q5 A ii

The paper's rules: Gold with 3 days 25%; Gold with 1 to 2 days 15%; Silver with 3 days 15%; Silver with 1 to 2 days 5%; Bronze any days 0%; and any tier that is not "Gold" or "Silver" must be treated as Bronze. It demands nested if-else, not a switch and not separate ifs.

  1. Branch on the thing the hierarchy is about: the tier. That is the outer question. The paper tells you this outright: days are checked within each tier branch.
  2. Inside each tier branch, ask about days. Now "3 days" can mean 25% under Gold and 15% under Silver, with no repetition of the tier test.
  3. Make the final else the Bronze case. This is how "anything that is not Gold or Silver is Bronze" falls out for free, rather than being a fourth test.
public class Discount {    static double discountFor(String tier, int days) {        if (tier.equals("Gold")) {              // outer: the tier            if (days == 3) {                    // inner: only for Gold                return 25.0;            } else {                return 15.0;            }        } else if (tier.equals("Silver")) {            if (days == 3) {                    // inner: only for Silver                return 15.0;            } else {                return 5.0;            }        } else {                              // not Gold, not Silver            return 0.0;                        // -> Bronze        }    }    public static void main(String[] args) {        String[] tiers = {"Gold", "Gold", "Silver", "Silver", "Bronze", "platinum"};        int[] days     = {3, 2, 3, 1, 3, 3};        for (int i = 0; i < tiers.length; i++) {            System.out.printf("%-9s %d day(s) -> %.0f%%%n",                              tiers[i], days[i], discountFor(tiers[i], days[i]));        }    }}
OutputGold      3 day(s) -> 25%
Gold      2 day(s) -> 15%
Silver    3 day(s) -> 15%
Silver    1 day(s) -> 5%
Bronze    3 day(s) -> 0%
platinum  3 day(s) -> 0%

The last row is the one that earns the mark: "platinum" is not Gold and not Silver, so it fell to the final else and was treated as Bronze, exactly as the paper demands, without a single line written to handle it. That is what good nesting buys you. (tier.equals(...) rather than == is Module 7's rule, and it is not optional: it is the most famous bug in Java.)

Now redo it: cover the listing and write discountFor from the rules alone. Then check: does your version handle "platinum" without mentioning it?

UNIT 4.5 · THE THREE LOOPS

for, while, do-while

By the end of this unit you should be able to explain the purpose of loops, compare and contrast for, while and do-while, and describe the branching statements break, continue and return.

TEACH · Loops

Loops are used to execute a block of code repeatedly based on a condition. Java provides three, and they differ only in when they ask the question.

MUST-MEMORISE · Which loop, and when

for: use when the number of iterations is known. Counting.

while: use when the number of iterations is not known in advance and depends on a condition. It may run zero times.

do-while: like while, but the body always runs at least once, because the condition is tested at the bottom.

MEMORY HOOK: for counts, while waits, do-while insists. The only structural difference between while and do-while is whether the question is asked at the top of the loop or the bottom, and that decides whether zero is a possible number of runs.

SYNTAX · The three, side by side
for (initialization; condition; update) {     <- all three parts, one line    // code}initialization;                              <- outsidewhile (condition) {                          <- tested BEFORE each pass    // code    update;                                  <- inside, and YOU must remember it}initialization;do {    // code                                  <- runs at least once, always    update;} while (condition);                         <- tested AFTER each pass. Note the ;

The semicolon after while (condition) in do-while is compulsory, and it is the only place in Java where a while is followed by one. Forgetting it is a compile error; adding one after an ordinary while is a disaster, and Unit 4.7 shows why.

CODE · The same job, all three ways
public class ThreeLoops {    public static void main(String[] args) {        System.out.print("for:      ");        for (int i = 1; i <= 5; i++) {            System.out.print(i + " ");        }        System.out.print("\nwhile:    ");        int j = 1;        while (j <= 5) {            System.out.print(j + " ");            j++;        }        System.out.print("\ndo-while: ");        int k = 1;        do {            System.out.print(k + " ");            k++;        } while (k <= 5);        System.out.println();    }}
Outputfor:      1 2 3 4 5
while:    1 2 3 4 5
do-while: 1 2 3 4 5

Identical output, three times. For a job where the count is known, all three work and the for loop is the right one, because it puts the counter, the test and the step on a single line where you can see all three at once. Note how the while and do-while versions scatter those same three parts across four lines: that is the cost, and it is also exactly what Unit 4.6 makes you undo and redo.

CODE · Where while and do-while part companyTHE WHOLE DIFFERENCE
public class ZeroTimes {    public static void main(String[] args) {        // a condition that is false from the very start        int i = 10;        System.out.println("while, i = 10, condition i < 5:");        while (i < 5) {            System.out.println("  ran");            i++;        }        System.out.println("  (body ran 0 times)");        int k = 10;        System.out.println("do-while, k = 10, same condition:");        do {            System.out.println("  ran anyway, k = " + k);            k++;        } while (k < 5);    }}
Outputwhile, i = 10, condition i < 5:
  (body ran 0 times)
do-while, k = 10, same condition:
  ran anyway, k = 10

Identical condition, identical starting value, different result. The while asked first and never entered; the do-while ran the body and asked afterwards. This is the entire difference between them, and it is why do-while is the right choice for "keep asking until the input is valid": you must ask once before you can have anything to validate.

TEACH · The for loop's three parts
PartIn for (int i = 0; i < 5; i++)When it happens
initializationint i = 0once, before anything else
conditioni < 5before every pass, including the first. False means stop.
updatei++after every pass, before the condition is retested

The order matters and people guess it wrong: init, test, body, update, test, body, update, ... The update runs after the body, not before, which is why i is 0 on the first pass and not 1.

UNIT 4.6 · CONVERTING BETWEEN LOOPS · WORTH 10 MARKS

Turning a for into a while, and back

TEACH · Why this unit exists

Both papers ask for this, by name, for real marks. The 2025/26 Section A says "Retain other things but change the For Loop to While loop and the While loops to For loops", inside a ten-mark question. The 2024/25 paper asks you to demonstrate all three loop types.

It is worth marks precisely because it is mechanical. Learn it as a recipe and it is free marks; improvise it under pressure and you will drop the update or the scope.

MUST-MEMORISE · The conversion recipe

for -> while, in three moves:
1. initialization goes above the loop;
2. condition goes in the while ( );
3. update goes at the bottom of the body.

while -> for: the same three moves, backwards. Find the variable being counted, its test, and where it changes, and fold all three into the for header.

MEMORY HOOK: a for loop is a while loop with its three parts collected onto one line. Converting is unpacking or repacking, nothing more.

WORKED EXAMPLE · for to while, step by step

Take the innermost loop from the 2025/26 Armstrong question:

for (int p = 0; p < digits; p++) power *= d;
  1. Lift the initialization out, above the loop: int p = 0;
  2. Move the condition into the while: while (p < digits)
  3. Push the update to the bottom of the body: p++; This is the step people forget, and forgetting it does not give a wrong answer. It gives an infinite loop.
  4. Add braces, because the body now has two statements where it had one. The original needed none: a one-statement body needs no braces. Two statements without braces is a bug.

Which gives, with everything else retained:

int p = 0;while (p < digits) {    power *= d;    p++;}
CODE · Both versions, proved identicalVERIFIED ON THE JVM
public class Convert {    static int withFor(int d, int digits) {        int power = 1;        for (int p = 0; p < digits; p++) power *= d;        return power;    }    static int withWhile(int d, int digits) {        int power = 1;        int p = 0;                    // 1. init lifted out        while (p < digits) {          // 2. condition            power *= d;            p++;                      // 3. update at the bottom        }        return power;    }    public static void main(String[] args) {        boolean allMatch = true;        for (int d = 0; d <= 9; d++) {            for (int n = 0; n <= 4; n++) {                if (withFor(d, n) != withWhile(d, n)) allMatch = false;            }        }        System.out.println("3^0 = " + withFor(3, 0) + " / " + withWhile(3, 0));        System.out.println("3^3 = " + withFor(3, 3) + " / " + withWhile(3, 3));        System.out.println("identical for every d 0-9, digits 0-4: " + allMatch);    }}
Output3^0 = 1 / 1
3^3 = 27 / 27
identical for every d 0-9, digits 0-4: true

Note the last line: rather than eyeballing two versions and trusting them, the program checked all fifty combinations and reported. That is how you verify a conversion in an exam too, on paper, with one or two values: convert, then trace both and compare.

TRAP · The two ways a conversion goes wrong

1. The dropped update. Leave out p++ and the condition never changes, so the loop runs forever. In an exam this costs you the marks; on a machine it hangs.

2. The scope change. for (int p = 0; ...) declares p inside the loop, so it ceases to exist afterwards. Lift it out and p now survives the loop. Usually harmless, occasionally a compile error ("variable p is already defined") if you convert two loops in the same method and both lift out an i.

Both are avoided by following the recipe rather than rewriting from scratch.

UNIT 4.7 · BRANCHING · BREAK, CONTINUE, RETURN

Escaping

MUST-MEMORISE · The three branching statements

break: exit the loop (or switch) immediately, even if its condition is still true.

continue: skip the rest of this pass and jump straight to the next iteration. The loop carries on.

return: exit the whole method immediately, optionally handing back a value.

MEMORY HOOK: break leaves the building, continue skips to the next floor, return quits the job. Notice the scale: break and continue act on the loop, return acts on the method containing it.

CODE · break and continue, side by sideFROM THE SLIDES
public class BreakContinue {    public static void main(String[] args) {        System.out.println("break at i == 5:");        for (int i = 1; i <= 8; i++) {            if (i == 5) break;        // leave the loop entirely            System.out.println("  i = " + i);        }        System.out.println("continue at i == 3:");        for (int i = 1; i <= 4; i++) {            if (i == 3) continue;     // skip just this pass            System.out.println("  i = " + i);        }    }}
Outputbreak at i == 5:
  i = 1
  i = 2
  i = 3
  i = 4
continue at i == 3:
  i = 1
  i = 2
  i = 4

Read the two outputs against each other. break stopped at 4 and 5 through 8 never happened. continue missed out 3 and carried on to 4. That is the whole distinction, and both papers plant a bug that turns on it.

TRAP · continue in a for loop still runs the update

continue jumps to the next iteration, which in a for loop means the update i++ still happens. Fine.

In a while loop it means the update is skipped, because the update is a statement in the body and you just jumped over the rest of the body. So this runs forever:

int i = 0;while (i < 5) {    if (i == 3) continue;    <- jumps back to the test with i STILL 3    System.out.println(i);    i++;                     <- never reached when i is 3}

This is the one listing in this book that is not executed for the obvious reason. It matters because Unit 4.6 tells you to convert for loops into while loops, and a continue inside one is exactly where a careless conversion turns a working program into a hang.

TRAP · The continue that inverts your logicBOTH PAPERS

Look at this, from the 2025/26 Section A:

if (arr[j] % 4 == 0) {    continue;                <- skips the multiples of 4}sum += arr[j] - j;           <- so this only ever sees NON-multiples

The question says the program should "find the first number that's a multiple of 4" and add it. The code continues when it finds a multiple of 4, so it skips precisely the numbers it was supposed to collect and processes precisely the ones it should have ignored. The logic is exactly inverted.

The other paper plants the mirror image: if (prices[i] > 20) continue; where the spec says skip anything under 20.

The lesson: continue means "skip this one". So the condition in front of it must describe the items you want to throw away, not the ones you want. Read every continue as the word "unless" and the bug becomes visible.

CODE · return: leaving earlyFROM THE SLIDES
public class ReturnDemo {    static void greet(String name) {        if (name == null || name.isEmpty()) {            System.out.println("Invalid name.");            return;                  // leave greet() right now        }        System.out.println("Hello, " + name + "!");    }    static int square(int n) {        return n * n;                // return WITH a value    }    public static void main(String[] args) {        greet("Jumoke");        greet("");        System.out.println("square(5) = " + square(5));    }}
OutputHello, Jumoke!
Invalid name.
square(5) = 25

Two shapes of return. greet is void, so its return; carries nothing and exists purely to leave early. square is int, so its return must carry a value. Module 5 is entirely about this.

The guard uses one library method worth naming. isEmpty() is a String method that answers true when the string holds no characters at all. So "" is empty, and " " is not: a space is a character. It is the same question as length() == 0, written so it reads like English.

And the order of the two tests is not a matter of taste. || is short-circuit (Unit 3.8): if name == null is already true, the right-hand side is never evaluated at all. Swap them to name.isEmpty() || name == null and a null name calls isEmpty() on nothing, which throws NullPointerException before the null check it was supposed to be protected by ever runs. Check for null first, always. It compiles either way.
