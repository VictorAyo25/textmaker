How to Attack an Objective Question

The paper carries an objective section as well as the long questions, and it is sat under more time pressure than anything else on it. This part is where you practise that half.

Teachwhere these questions come from

Say this plainly, because it decides how you should read them. This course has no computer-based test among its papers, so unlike the long questions in this book, which are quoted from the examiner word for word, these 70 questions were written for this manual. They are not the examiner's and they do not pretend to be.

What they are grounded in is real. Every one is drawn from something this manual teaches and something the ten past papers actually ask about, and the paper's own habits are copied on purpose: it leans hard on asking for the output of a code snippet, on asking you to identify and correct an error, and on asking for a property by name, such as lists being ordered, sets being unique, or strings being immutable. Those are descriptions of what the paper does, not quotations of its wording, which is why none of them is set in quotation marks here. So what you are drilling is this course's own material in objective form, even though the wording is ours.

Every code snippet below was run on a real interpreter and the answer is what came back, not what it ought to have been. If your answer differs from the book's, the interpreter settled it, not an opinion.

Key point

In a four-option question, three options are wrong for a reason you can state. Finding that reason is faster and safer than recognising the right answer, because recognition is exactly what a well-built distractor attacks.

Blunt version: do not hunt for the right one. Kill the wrong ones.

Teachthe four moves, in order
  1. Underline the instruction word. NOT, TRUE, BEST, PRIMARILY and EXCEPT each flip or narrow the question. A question containing NOT wants the odd one out, and read as an ordinary question every wrong answer starts to look right.
  2. For a code question, trace it on paper before you look at the options. Write the variables down the margin and update them line by line. The options are built from the answers you get by tracing it WRONG, so reading them first plants the mistake.
  3. Strike the impossible. Two of four usually die at once: an option that contradicts a definition, or that is true but answers a different question.
  4. Split the last two on the exact wording. It is nearly always one word: only, always, all, entirely, every. An option saying a function "eliminates complexity entirely" is wrong because of "entirely".
Trapthe five that decide most output questions

Five facts answer a large share of every output-tracing question this course can set. Know them cold and the tracing gets much shorter.

  1. input() returns a string, always, however numeric it looks.
  2. A slice excludes its stop, and range() excludes its stop too.
  3. A single slash always gives a float; double slash floors.
  4. Methods that change a list in place return None: sort, append, reverse, extend.
  5. Assignment does not copy. b = a gives one object two names.

Answers, and why every option is what it is

1. The answer is An interpreted, high-level, general-purpose language. Interpreted, high-level, general-purpose. Those three words are the definition the paper wants back.

  • A compiled language, translated to machine code before it runs. Wrong. Compilation to machine code ahead of running is the C and Java model. Python translates and runs statement by statement through an interpreter, which is why an error can appear only when that line runs.
  • An interpreted, high-level, general-purpose language. Correct. Interpreted means a program runs it line by line; high-level means it hides the machine; general-purpose means it is not tied to one kind of task.
  • A markup language for describing documents. Wrong. A markup language describes how content is structured, like HTML. Python computes, it does not mark up.
  • An assembly language for a specific processor family. Wrong. Assembly is tied to one processor and its instruction set. Python code runs unchanged wherever the interpreter runs.

2. The answer is Nothing runs: the whole file is checked before any of it executes. Syntax errors are found at parse time, before execution. Runtime errors are found when their line runs. Knowing which is which explains why some faulty scripts print nothing at all.

  • The first lines run, then the error is reported when that line is reached. Wrong, and it is the trap. This is true of a NAME error or a type error, which are found only when the line runs, but a SYNTAX error is found while the file is being parsed, before anything executes.
  • Nothing runs: the whole file is checked before any of it executes. Correct. Python parses the whole file first. A syntax error anywhere stops it before the first line runs, which is why a stray colon can produce no output at all.
  • The error is ignored and the script finishes normally. Wrong. Python never ignores an error. Something is always reported.
  • The line is skipped and the rest of the script continues. Wrong. Python does not skip statements it cannot parse. There is no "carry on regardless" mode.

3. The answer is It is the fastest executing language available. Speed of execution is a DISadvantage of Python, not an advantage. Everything else on that list is real.

  • It is easy to read, with a syntax close to English. Wrong choice, because readability IS an advantage. The whitespace rules exist to force it.
  • It is portable: the same code runs on different platforms. Wrong choice, because portability IS an advantage. The interpreter hides the platform.
  • It is the fastest executing language available. Correct, and this is the one to remember. Interpretation costs speed. Python is chosen for programmer time, not for execution time, and a paper listing slow execution as a disadvantage of Python is common.
  • It has a large standard library and a large community. Wrong choice, because the standard library IS an advantage. It is the "batteries included" claim.

4. The answer is The prompt echoes the value of any expression you type. The prompt echoes; a script does not. This is why the manual marks its three kinds of block differently, and why copying prompt examples into a file makes the output vanish.

  • The prompt echoes the value of any expression you type. Correct. The interactive prompt evaluates what you type and displays the result. That is a feature of the prompt, not of the language.
  • Python adds a print automatically to every line of every program. Wrong, and this is the trap. Inside a SCRIPT, 2 + 3 on its own line computes 5 and throws it away silently. Only the prompt echoes.
  • The plus operator prints its result. Wrong. The plus operator produces a value and does nothing else with it.
  • It does not appear; the prompt shows nothing without print. Wrong. The prompt does echo. Try it: this is the difference between the three kinds of code block this manual sets out.

5. The answer is python grades.py. python <filename>. The interpreter is the program; your file is the input to it.

  • run grades.py. Wrong. There is no run command. The interpreter is the program you launch, and the script is what you hand it.
  • python grades.py. Correct. You launch the interpreter, python, and give it the file to run as its argument.
  • grades.py run. Wrong. The order is wrong and run is not a Python word.
  • execute python grades.py. Wrong. There is no execute command wrapping it.

6. The answer is # this is a comment. Hash to end of line. Python has no block comment: a run of hashes, or a string used as a docstring, is how several lines are done.

  • // this is a comment. Wrong. Two slashes are the C, Java and JavaScript comment. In Python two slashes are the floor division operator, so this line is an error.
  • /* this is a comment */. Wrong. Slash-star is the C block comment. Python has no block comment syntax at all.
  • # this is a comment. Correct. The hash starts a comment that runs to the end of the line.
  • -- this is a comment. Wrong. Two hyphens are the SQL comment, which matters here because this course also writes SQL through Python. The two languages do not share it.

7. The answer is It marks which statements belong to a block, and is part of the syntax. Indentation is syntax, not decoration. It replaces the braces that other languages use to group statements.

  • Nothing: it is style only, as in C or Java. Wrong, and it is the single biggest habit to break coming from another language. In Python the indentation IS the block structure, so getting it wrong changes the meaning of the program or stops it running.
  • It marks which statements belong to a block, and is part of the syntax. Correct. Where C uses braces, Python uses the indentation itself. An inconsistent indent raises IndentationError.
  • It sets how far output is printed from the left edge. Wrong. Output position is decided by what you print, not by how the source is laid out.
  • It is required only inside functions. Wrong. Every block needs it: if, else, for, while, def, class, try, with.

8. The answer is _total2. Start with a letter or underscore, then letters, digits or underscores, and never a keyword. Names are case sensitive, so Total and total are two different variables.

  • 2nd_score. Wrong. A name may not start with a digit. Letters and the underscore only, then digits are allowed after the first character.
  • class. Wrong. class is a reserved keyword, so it cannot be used as a name. The same applies to if, for, def, and the rest.
  • total score. Wrong. A space separates two names, so Python reads this as two things and reports a syntax error. Use an underscore.
  • _total2. Correct. It starts with an underscore, which is allowed, and the digit is not in first position.

Answers, and why every option is what it is

1. The answer is The type belongs to the value, and a name may be rebound to a value of another type. The value carries the type; the name is only a label. That is why type() reports on the value and why a name can change type mid-program.

  • A variable must be declared with its type before use. Wrong, and this is the static-typing model of C and Java. Python needs no declaration at all: assignment creates the name.
  • The type belongs to the value, and a name may be rebound to a value of another type. Correct. x = 5 then x = "five" is legal, because the type travels with the value, not with the name.
  • Types are checked by the compiler before the program runs. Wrong. There is no compiler pass checking types ahead of time. A type error surfaces when the offending line runs.
  • Every value in Python is a string until converted. Wrong. This describes what input() returns, not what Python does generally. 5 is an int the moment you write it.

2. The answer is str then 2020. input() always returns a string. That is why age + 5 raises TypeError and age * 2 gives 2020, and it is the single most common first-program bug in this course. Wrap it in int() or float().

  • int then 40. Wrong on both lines. input() never returns an int, and star on a string repeats rather than multiplies.
  • str then 2020. Correct. input() always returns a str, so type reports str, and "20" * 2 repeats the characters to give 2020.
  • str then 40. Wrong on the second line. 40 would need age to be a number; it is a string, so star repeats it.
  • int then 2020. Wrong on the first line. The value came from input(), so it is a string however numeric it looks.

3. The answer is 3.5 then 3 then 1. Slash gives a float, double slash floors, percent is the remainder. Note 7 // 2 is 3 but -7 // 2 is -4, because flooring goes DOWN, not towards zero.

  • 3.5 then 3 then 1. Correct. A single slash is true division and always gives a float, even when it divides exactly. Double slash floors the result to an integer. The percent sign gives the remainder.
  • 3 then 3 then 1. Wrong. A single slash never truncates in Python 3. 7 / 2 is 3.5, not 3. That was Python 2 behaviour, and the change is a favourite exam point.
  • 3.5 then 3.5 then 1. Wrong. Double slash is floor division, so it produces 3, not 3.5.
  • 3.5 then 3 then 3.5. Wrong. The percent sign is remainder, not division, so 7 % 2 is 1.

4. The answer is 50. Exponent, then multiply and divide, then add and subtract. When in doubt in the exam, write the brackets in yourself: they cost nothing and remove the question.

  • 50. Correct. Exponent first: 4 ** 2 is 16. Then multiply: 3 * 16 is 48. Then add: 2 + 48 is 50.
  • 80. Wrong. That is (2 + 3) * 4 ** 2, which adds before multiplying. Addition is last, not first.
  • 400. Wrong. That is ((2 + 3) * 4) ** 2, which applies the exponent to everything.
  • 100. Wrong. That is (2 + 3 * 4) ** 2, exponent applied last.

5. The answer is 512. Exponent is right-associative, and it is the only common operator that is. Everything else in this course groups left to right.

  • 64. Wrong. 64 is (2 ** 3) ** 2, grouping from the left. The exponent operator is the exception: it groups from the RIGHT.
  • 512. Correct. It reads as 2 ** (3 ** 2), which is 2 ** 9, which is 512.
  • 18. Wrong. 18 would be 2 * 3 * 3, which is not what any part of this expression does.
  • 12. Wrong. There is no reading of this expression that gives 12.

6. The answer is 24. x += 5 is exactly x = x + 5. Work these line by line and write the running value in the margin; the exam asks this shape often.

  • 24. Correct. 10 plus 5 is 15, minus 3 is 12, times 2 is 24. Each line uses the value the line before it left behind.
  • 12. Wrong. 12 is the value after the subtraction. The multiplication still has to happen.
  • 30. Wrong. 30 would be 15 times 2, which skips the subtraction.
  • 17. Wrong. 17 would be 10 plus 5 plus 2, which misreads two of the three operators.

7. The answer is True then False. Chained comparison is real Python and reads exactly as it does in mathematics. Most languages do not have it, so it is worth a mark when the paper shows one.

  • True then False. Correct. Python allows a chained comparison, and 1 < 5 < 10 is True. The second line asks for something and its own opposite at once, which can never be True.
  • True then True. Wrong. The second line cannot be True: x == 5 and x != 5 contradict each other by construction.
  • False then False. Wrong. The first line is True, because chaining is legal in Python and 5 does lie between 1 and 10.
  • TypeError. Wrong. Nothing here is a type error; all the operands are numbers.

8. The answer is True then False. Precedence among the three: not, then and, then or. Read them in that order and these questions become mechanical.

  • True then False. Correct. and binds tighter than or, so the first line is (True and False) or True, which is False or True, which is True. On the second, not binds tightest, so it is (not True) and False, which is False and False.
  • False then False. Wrong. The first line is True, because the or rescues it: only one side of an or needs to be true.
  • True then True. Wrong. The second line is False. not True is False, and False and anything is False.
  • False then True. Wrong on both counts, and it has the precedence backwards.

9. The answer is 10 then 5.0 then 42. int() truncates towards zero and round() rounds. Mixing an int with a float gives a float. Plus on two strings joins them.

  • 10 then 5.0 then 42. Correct. int("7") is 7 and int(3.9) TRUNCATES to 3, so the sum is 10. float("2.5") * 2 is 5.0, a float because one operand is. str(4) + "2" joins two strings into "42".
  • 10.9 then 5.0 then 6. Wrong. int() applied to a float does not keep the fraction. It truncates towards zero.
  • 11 then 5.0 then 42. Wrong. int(3.9) is 3, not 4. int() truncates, it does not round; round() is the function that rounds.
  • 10 then 5 then 42. Wrong. Multiplying a float by an int gives a float, so it prints 5.0, with the point.

10. The answer is Once created, a string object cannot be changed; operations return a new string. Immutable means the object cannot be modified in place. This is a question the paper asks in words ("Strings are Immutable. Explain and with reasons."), so have the sentence ready and an example with it.

  • A string cannot be printed twice. Wrong. Printing does not change anything, and there is no limit on how often you may print.
  • Once created, a string object cannot be changed; operations return a new string. Correct. s.upper() hands back a NEW string and leaves s untouched, and s[0] = "X" raises TypeError. To "change" a string you must rebind the name to a new one.
  • A string cannot be assigned to a variable more than once. Wrong. Rebinding a name is always allowed. That changes what the name points to, not the string it used to point at.
  • A string cannot contain numbers. Wrong. "abc123" is a perfectly ordinary string. The characters in it are irrelevant to mutability.

11. The answer is P N YTH NOHTYP. Index from 0, negative counts from the end, a slice excludes its stop, and [::-1] reverses. Those four facts answer most string questions on this paper.

  • P N YTH NOHTYP. Correct. Index 0 is the first character, minus 1 is the last, a slice stops BEFORE its end index so 1:4 gives characters 1, 2 and 3, and a step of minus 1 walks the string backwards.
  • P N YTHO NOHTYP. Wrong. The slice s[1:4] does not include index 4, so it is three characters, not four.
  • Y N YTH NOHTYP. Wrong. s[0] is P. Python indexes from 0, not from 1.
  • P O YTH NOHTYP. Wrong. s[-1] is the last character, N, not the second to last.

12. The answer is HELLO WORLD then ['Hello', 'World'] then a-b-c. strip, upper, lower, split, join, replace, find. Those seven cover nearly every string question this course has ever set.

  • HELLO WORLD then ['Hello', 'World'] then a-b-c. Correct. strip() removes the leading and trailing spaces, upper() uppercases what is left, split() with no argument splits on whitespace into a list of words, and join() glues a list together with the string it is called on as the separator.
  • HELLO WORLD then ['Hello World'] then a-b-c. Wrong. split() with no argument splits on EVERY run of whitespace, so two words come back as two items.
  • HELLO WORLD then ['Hello', 'World'] then a-b-c. Wrong. strip() really does remove the outer spaces. That is its only job.
  • Hello World then ['Hello', 'World'] then abc. Wrong on two counts: upper() does uppercase, and join() really does put the hyphen between the items.

13. The answer is ababab then ab3. Star repeats, plus joins, and "ab" + 3 is the error. The operator means different things for numbers and for strings, which is what operator overloading is.

  • ababab then ab3. Correct. A string times an integer repeats it. A string plus a string joins them. Both operators are overloaded for strings.
  • ab3 then ababab. Wrong, and it has the two operators swapped. Star repeats, plus joins.
  • abababab then ab3. Wrong. Times 3 gives three copies, not four.
  • TypeError then ab3. Wrong. String times int is perfectly legal. It is string PLUS int that raises TypeError.

14. The answer is Ada scored 87.5. f"..." substitutes; :.2f fixes the decimal places. Forgetting the f is the classic error and the output tells you at once.

  • Ada scored 87.456. Wrong. The .1f asks for one decimal place, so the full value is not printed.
  • Ada scored 87.5. Correct. The f before the quote turns it into a formatted string, the braces are replaced by the values, and .1f rounds to one decimal place, giving 87.5.
  • Ada scored 87.4. Wrong. Formatting ROUNDS, it does not truncate, and 87.456 rounds up to 87.5.
  • {name} scored {score:.1f}. Wrong. That is what you get WITHOUT the f prefix, which is a real and common slip: the braces then print literally.

15. The answer is a b then c then d then e\f. Backslash n newline, backslash t tab, double backslash for a real backslash. This matters for file paths, where a Windows path needs doubling or a raw string.

  • a b then c then d then e\f. Correct. Backslash t is a tab, backslash n is a newline, and two backslashes print one literal backslash.
  • a\tb then c\nd then e\\f. Wrong. That is what a RAW string would print, written r"a\tb". Without the r, the escapes are interpreted.
  • ab then cd then ef. Wrong. The escapes produce real whitespace: a tab and a line break, not nothing.
  • a b then cd then ef. Wrong. Backslash t is a tab character, which is wider than a single space, and the last line keeps its backslash.

16. The answer is True then False. == is equal in value, is is the very same object. Use is only for None, and use == for everything else.

  • True then True. Wrong. is asks whether they are the SAME object, and two separately written lists are two objects however alike they look.
  • True then False. Correct. == compares contents, so it is True. is compares identity, so it is False: a and b name two different list objects.
  • False then False. Wrong. == on two lists compares them item by item, and these match.
  • False then True. Wrong, and it has the two operators exactly backwards.

17. The answer is 2 1. a, b = b, a swaps in one line because the right side is built completely before anything is assigned.

  • 1 2. Wrong. That is the value before the swap.
  • 2 1. Correct. The right-hand side is evaluated first, into the pair (2, 1), and only then unpacked into a and b. So the swap needs no temporary variable.
  • 2 2. Wrong. That is what happens in a language where a = b runs first and destroys the old a. Python does not: it builds the whole right side first.
  • 1 1. Wrong, for the same reason: nothing is overwritten before it is read.

18. The answer is ValueError. TypeError is the wrong type, ValueError is the right type carrying an impossible value. int("abc") is the standard example of the second.

  • TypeError. Wrong. TypeError is for the wrong KIND of thing, such as "5" + 5. Here the kind is right, a string, and int() does accept strings.

  • The file is opened read-only. Wrong. "w" is write-only. Reading is "r", which is also the default.

7. The answer is It closes the file automatically, even if an error is raised inside the block. with guarantees the close. It is the same guarantee finally gives, written more briefly, and saying that in the exam earns the mark.

  • It is faster to type. Wrong. Brevity is not the reason, and it is barely shorter anyway.
  • It closes the file automatically, even if an error is raised inside the block. Correct. The with block guarantees f.close() runs on the way out, whether the block finished normally or raised. Without it, an exception can leave the file open and its buffer unwritten.
  • It is the only way to read a file line by line. Wrong. A plain open() can be iterated line by line just as well. The difference is only about closing.
  • It opens the file in a special faster mode. Wrong. The mode is whatever you pass to open. with changes nothing about how the file is opened.

8. The answer is f.readlines(). read whole, readline one, readlines list. Note the newline stays on each item, so print() of one adds a blank line unless you strip.

  • f.read(). Wrong. read() gives the WHOLE file as one string, newlines and all.
  • f.readline(). Wrong. readline() gives ONE line, the next one, as a string.
  • f.readlines(). Correct. readlines() gives a list with one string per line, each still carrying its trailing newline unless you strip it.
  • f.line(). Wrong. There is no such method.

9. The answer is caught then always. try, except by exception type, else if nothing was raised, finally always. finally is where you put the cleanup that must happen either way.

  • caught then always. Correct. The division raises, the matching except handles it, and finally runs afterwards as it always does.
  • always. Wrong. The except block ran too, and its print came first.
  • caught. Wrong. finally runs whether or not anything was raised. That is its whole point.
  • the program crashes. Wrong. The exception was caught, so nothing propagates and nothing crashes.

10. The answer is IndexError. IndexError for a sequence, KeyError for a mapping. Naming the right exception is worth marks on its own in this paper.

  • KeyError. Wrong. KeyError is for a missing DICTIONARY key. A list is indexed by position, not by key.
  • IndexError. Correct. The index is outside the range of the list, which is exactly what IndexError means.
  • ValueError. Wrong. ValueError is for a value of the right type that cannot be used, such as int("abc").
  • TypeError. Wrong. TypeError would be xs["a"], where the index is the wrong KIND of thing entirely.

11. The answer is It catches everything, including errors you did not anticipate, and hides real bugs. Catch the exception you expect and no more. A bare except turns a loud failure into a silent wrong answer.

  • It is slower than naming the exception. Wrong. Speed is not the issue and the difference is immeasurable.
  • It catches everything, including errors you did not anticipate, and hides real bugs. Correct. A bare except swallows every exception, including a typo raising NameError, so the program keeps going in a broken state and the real fault is invisible.
  • It is not valid Python. Wrong. It is valid, which is exactly why it is dangerous.
  • It can only be used once per program. Wrong. There is no such limit.

12. The answer is negative age. raise makes your own error, and validating input this way is what the paper means by defensive programming.

  • negative age. Correct. raise creates the exception with that message, the except catches it and binds it to e, and printing an exception prints its message.
  • ValueError. Wrong. Printing the exception object shows its MESSAGE, not the name of its class. For the class name you would print type(e).__name__.
  • -1. Wrong. The argument is never returned, because the raise happens first.
  • nothing is printed. Wrong. The except block does run and does print.

13. The answer is A string literal as the first statement of a function, module or class, describing what it does. First statement, a string, becomes __doc__. It is the "self-documenting" part of the modularisation answer.

  • A comment starting with a hash inside a function. Wrong. A hash comment is stripped and cannot be read back at run time. A docstring survives into the object.
  • A string literal as the first statement of a function, module or class, describing what it does. Correct. It sits directly under the def line, usually in triple quotes, and becomes the object's __doc__, which is what help() shows you.
  • A special variable holding the function name. Wrong. That is __name__, a different attribute entirely.
  • A file that documents the whole program. Wrong. A docstring lives inside the code, not beside it.

14. The answer is 120. Every recursion needs a base case and a step that moves towards it. Missing the base case gives RecursionError, and the paper has asked for exactly that fault to be identified.

  • 15. Wrong. 15 is 1+2+3+4+5, the SUM. This function multiplies.
  • 120. Correct. 5 * 4 * 3 * 2 * 1 is 120. The base case at n <= 1 stops the recursion.
  • 5. Wrong. The function does not simply return its argument; it multiplies down to the base case.
  • RecursionError. Wrong. There IS a base case, so the recursion terminates. Without one, RecursionError would be right.

Answers, and why every option is what it is

1. The answer is connect, cursor, execute, commit, close. connect, cursor, execute, commit, close. Forget the commit and the rows vanish when the program ends, which is the classic lost mark.

  • connect, cursor, execute, commit, close. Correct. Connect to the database, get a cursor from the connection, execute SQL through the cursor, commit so the change is saved, then close the connection.
  • cursor, connect, commit, execute, close. Wrong. A cursor is obtained FROM a connection, so the connection must exist first.
  • connect, execute, cursor, close, commit. Wrong. You cannot execute before you have a cursor, and committing after closing is too late.
  • open, read, write, close. Wrong. That is the file-handling pattern, not the database one.

2. The answer is No rows. Commit is what makes a change permanent. No commit, no data, and no error message to tell you.

  • All three rows. Wrong. Uncommitted work is not saved. It lived only in the transaction.
  • The first row only. Wrong. There is nothing special about the first row; all three are in the same uncommitted transaction.
  • No rows. Correct. Without a commit the transaction is rolled back when the connection closes, so the table is unchanged.
  • An error is raised. Wrong. Nothing raises. The program appears to work, which is what makes this bug expensive.

3. The answer is SELECT * FROM students WHERE score > 50. SELECT columns FROM table WHERE condition. That one line is most of what this course asks of SQL.

  • SELECT * FROM students WHERE score > 50. Correct. SELECT names the columns, FROM names the table, WHERE filters the rows.
  • SELECT * FROM students IF score > 50. Wrong. SQL filters with WHERE. IF is not part of a SELECT statement.
  • GET * FROM students WHERE score > 50. Wrong. There is no GET in SQL. Retrieval is SELECT.
  • SELECT students WHERE score > 50. Wrong. The table must be named after FROM, and the columns before it.

4. The answer is It keeps the values separate from the SQL, so a value cannot be read as SQL. The question mark placeholder separates data from code. It is the standard answer to "how do you prevent SQL injection".

  • It runs faster on small tables. Wrong. Speed is not the reason, though prepared statements can help on repeated inserts.
  • It keeps the values separate from the SQL, so a value cannot be read as SQL. Correct. The placeholder keeps data as data. Pasting a value into the text of a statement lets a value containing a quote change the statement, which is SQL injection.
  • It is the only form sqlite3 accepts. Wrong. String building is accepted. It is accepted and unsafe, which is the point.
  • It commits automatically. Wrong. You still have to commit yourself.

5. The answer is It runs the same statement once for each item in a sequence of parameter tuples. One statement, many parameter sets. It is the tidy way to insert a list of records and this manual teaches it because the paper reached for it.

  • It runs several DIFFERENT statements in one call. Wrong. The statement is the same every time. Only the parameters change.
  • It runs the same statement once for each item in a sequence of parameter tuples. Correct. You give it one statement and a list of parameter tuples, and it runs the statement once per tuple, which is how a batch insert is done.
  • It commits after every row. Wrong. It does not commit at all. You still call commit yourself.
  • It returns all the rows of a table. Wrong. Retrieving rows is fetchall(), after a SELECT.

6. The answer is The first row, as a tuple. fetchone next row or None, fetchall the rest as a list of tuples. A row is a tuple, so index it by position.

  • All five rows as a list. Wrong. That is fetchall(). fetchone gets one.
  • The first row, as a tuple. Correct. fetchone() hands back the next row as a tuple, and returns None once the rows run out.
  • The number 5. Wrong. Counting rows is done in SQL, with COUNT(*).
  • None. Wrong. None comes back only when there are no rows left, and here there are five.

7. The answer is COUNT(). COUNT how many, SUM the total, AVG the mean, MAX and MIN the extremes. The paper has asked for all five.

  • SUM(). Wrong. SUM() adds up the values in a column. It answers how much, not how many.
  • COUNT(). Correct. COUNT(*) counts rows; COUNT(column) counts the rows where that column is not null.
  • TOTAL(). Wrong. There is no standard TOTAL() in this course.
  • LEN(). Wrong. LEN() is not SQL. Python has len(); SQL has COUNT().

8. The answer is It sets score to 0 for EVERY row in the table. No WHERE means every row. Write the WHERE first and the SET second if that helps you never forget it.

  • Nothing: a WHERE clause is required. Wrong. WHERE is optional, and that is precisely the danger.
  • It sets score to 0 for EVERY row in the table. Correct. With no WHERE, the statement applies to the whole table. The same is true of DELETE FROM students, which empties it.
  • It sets score to 0 for the first row only. Wrong. SQL is set-based: it acts on every row that matches, and with no WHERE every row matches.
  • It deletes the score column. Wrong. Removing a column is ALTER TABLE. UPDATE changes values.

9. The answer is It starts the event loop, which waits for and dispatches user actions. Tk() makes the window, widgets are created and placed, mainloop() runs the event loop. Without the last one nothing stays on screen.

  • It draws the window once and returns. Wrong. Drawing once and returning would make the window appear and vanish immediately, which is exactly what happens if you forget mainloop.
  • It starts the event loop, which waits for and dispatches user actions. Correct. mainloop() keeps the program running, watching for clicks and keystrokes and calling the handlers bound to them, until the window is closed.
  • It creates the main window object. Wrong. Creating the window is Tk(). mainloop is what makes it live.
  • It closes the application. Wrong. It is what keeps the application OPEN.

10. The answer is Entry. Label shows, Entry takes one line, Text takes many, Button acts. Read what was typed with entry.get().

  • Label. Wrong. A Label DISPLAYS text. The user cannot type into it.
  • Entry. Correct. Entry is the one-line text box, and its get() method reads what was typed.
  • Button. Wrong. A Button is clicked; it does not accept typing.
  • Canvas. Wrong. A Canvas is a drawing surface for shapes and images.

11. The answer is When the button is clicked. Pass the function, not a call to it. command=run attaches it; command=run() runs it once immediately and attaches its result.

  • Immediately, as the button is created. Wrong, and this is the trap. It WOULD be immediate if you wrote command=run(), with brackets: that calls the function and hands its return value to command.
  • When the button is clicked. Correct. command is given the function ITSELF, without brackets, and tkinter calls it later, each time the button is pressed.
  • When mainloop() starts. Wrong. mainloop starts the waiting; it does not fire the handlers by itself.
  • Never, unless bind() is also used. Wrong. command= is a complete way to attach a handler to a button. bind() is for other events.

12. The answer is align. pack, grid, place. Three of them, and mixing pack with grid in one container makes the window hang while they argue.

  • pack. Wrong choice, because pack IS one: it stacks widgets in the space available.
  • grid. Wrong choice, because grid IS one: it places widgets by row and column.
  • place. Wrong choice, because place IS one: it positions by exact coordinates.
  • align. Correct. There is no align manager. The three are pack, grid and place, and you should not mix pack and grid in the same container.
