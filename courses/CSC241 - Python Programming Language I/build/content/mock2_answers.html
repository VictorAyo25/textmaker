Question One

AnswerQ1 (a)

A control structure decides which statements run, and how often. Without one a program is a list that runs top to bottom, once.

  • break leaves the loop immediately. Nothing after it in the loop body runs, and the loop does not continue. for i in range(5): if i == 2: break
  • continue abandons this pass only and jumps to the next. The loop carries on. for i in range(5): if i % 2: continue
  • else on a loop runs when the loop finishes without being broken. It is the part everyone forgets: it is not "otherwise", it is "and we got all the way through".

The three-way answer the examiner wants: sequence, selection (if), repetition (for, while). break and continue steer the third.

Question Three

AnswerQ3 (a)
  • Parameter against argument. The parameter is the name in the definition, def fee(hours). The argument is the actual value you pass, fee(3). One is the label, the other is the thing.
  • return hands a value back to whoever called the function, and ends the function there and then. Leave it out and the function still returns something: it returns None. That is not an error, which is exactly why it is dangerous, and it is what part (b) is about.
  • A default parameter supplies a value for an argument the caller does not give: def pay(hours, rate=500). It must come last because Python matches arguments to parameters by position. If a default came first, then pay(8) could not say whether the 8 is the defaulted one or the required one. Python refuses the definition outright rather than guess.
AnswerQ3 (b)

Two errors, and the second is invisible until the first is fixed.

  1. def fee(hours) has no colon. Nothing runs at all: SyntaxError: expected ':'
  2. Add it and the program runs cleanly and prints the wrong thing: None The function works out total and then throws it away. There is no return, so the function gives back None, and print faithfully prints it. No error, no warning, no marks.

print(fee(3))
500

200 for the first hour, then 2 more hours at 150, so 200 + 300 = 500. A function that computes and does not return is the most common quiet failure in this course. If your function prints None, this is why, every time.

AnswerQ3 (c)
4000
5600
  • pay(8) gives one argument, so hours is 8 and rate falls back to its default of 500: 8 * 500 = 4000.
  • pay(8, 700) gives two, so the second replaces the default: 8 * 700 = 5600.

The default is not a constant. It is the value used only when the caller stays silent. That is what makes rate optional without making it fixed, and it is the whole reason default parameters exist.

Question Four

AnswerQ4 (a)

A string is text: a sequence of characters in quotes. It is immutable, meaning it can never be changed after it is made.

What follows from that is the examinable half: a string method can never change the string it is called on, so it hands you a new one. name.upper() leaves name exactly as it was. If you do not catch the result, with name = name.upper(), the work is thrown away and nothing happens. This is the opposite of a list's sort(), which changes the list and hands back nothing.

MethodDoesExampleGives
upper()Returns a capitalised copy"ada".upper()'ADA'
strip()Returns a copy with the ends trimmed" hi ".strip()'hi'
split(sep)Cuts it into a list"a,b".split(",")['a', 'b']
isalpha()Asks a question, changes nothing"Ada".isalpha()True

The fourth is the one the question is fishing for. isalpha(), startswith() and find() interrogate a string rather than transform it; the rest hand back a changed copy.

It names it. Python prints the method itself, which is a real object and prints happily. (The 0x... is a memory address, and it is a different number every time the program runs.)

Question Five

AnswerQ5 (a)

with open(...) closes the file for you, whatever happens, even if the code inside raises an error. A plain open() leaves that to you, and if an exception fires before your close(), the file is never closed and the last thing you wrote may never reach the disk. with is not a convenience; it is the guarantee.

ModeDoesIf the file does not exist
"r"Read only. Cannot write.Error. It refuses to create it.
"w"Write, and empty the file first.Creates it.
"a"Append: add to the end, keep what is there.Creates it.

Reading against appending: "r" takes data out and changes nothing; "a" puts data in at the end and destroys nothing. The dangerous one is "w", which silently throws away the whole file the instant you open it.

AnswerQ5 (b)

Two errors.

  1. "r" is read only, and the program is trying to write. The mode should be "a" to add a name and keep the others.
  2. f.close has no brackets, so the file is never closed. Same fault as Q4(b), in a different coat.

The first error gives two different messages, and which one you get depends on something the code does not show you:

If names.txtPython says

AnswerQ5 (c)
second

Followed by a blank line, because the file's contents end in \n and print adds another.

The first line is gone. Opening in "w" empties the file immediately, before a single byte is written. The second with block therefore starts from nothing, and "first" is destroyed without a word.

Had the second block used "a", the file would hold both lines. This one question is the whole difference between the two modes, and it is why a program that saves records in a loop must open the file once, outside the loop: reopen it in "w" each time round and you finish with a file containing only the last record.

Question Six

AnswerQ6 (a)

i. A table is one kind of thing being stored, like products. A row is one of them: one product. A column is one fact held about every one of them: the price. A table is a grid, rows down, columns across.

ii. conn.commit() makes your changes permanent. Until you call it, inserts live in an open transaction and belong only to your connection. Forget it and the program runs, prints nothing wrong, exits, and the database is unchanged. No error is ever raised. It is the single most common way to lose work in this topic.

iii. fetchone() returns one row and moves on, or None if there are none left. fetchall() returns every remaining row, as a list of tuples, and an empty list if there are none. Use fetchone() when you expect a single answer, fetchall() when you want to loop over the lot.

AnswerQ6 (b)

Two errors.

  1. VALUE should be VALUES. This is SQL, not Python, so Python cannot help you: the string is perfectly good Python and the database is the one that objects. OperationalError: near "VALUE": syntax error
  2. conn.close has no brackets, so the connection is never closed. The third appearance of this fault in two mocks. Note that the program never even reaches it here: the error above stops everything first.
fixed
import sqlite3

IF NOT EXISTS is added for a reason worth a mark on its own: run the original twice and the second run dies with OperationalError: table products already exists. A program that only works once is not finished.

AnswerQ6 (c)

i. It opens shop.db, asks for the name column of every row in products, prints all the rows it gets back, and closes the connection.

ii. With the single Pen row from (b) in the table:

[('Pen',)]

A list of tuples, one tuple per row, even though only one column was asked for. That trailing comma in ('Pen',) is Python's way of writing a tuple of one item, and it is not a typo. To print plain names you would loop and take row[0].

iii. Three assumptions:

  1. shop.db can be opened. connect() creates the file if it is absent, so this never fails, and that is the trap.
  2. A table called products exists in it, with a name column. If not: OperationalError: no such table: products which is exactly what you get if connect() just made you a fresh, empty database because you misspelled the filename.
  3. The rows were committed by whoever inserted them. Uncommitted inserts from another connection are invisible here.

Must memoriseWhat both mocks were teaching

Two papers, sixty parts, and underneath them four patterns. Learn these and you have not learned two mocks, you have learned the exam.

PartAlways one of
(b)A first error that hides a second. Fix the crash and read the output again: it is usually None, or a method printed instead of called.
(c)A rule stated from one side. Mock One broke the loop so else was skipped; Mock Two did not, so it ran.
(d)A banding decided by boundaries. 49 against 50, 199 against 200, "under 13" against "13 and above".
(e)Sentinel loop (while True, break on 'done') or split and convert (one line, split(), int() each piece). Nothing else has ever been set.

The one habit worth more than any of them: read < as "strictly less than" and > as "strictly more than", out loud, every single time. A parcel above 20 kg is not a parcel of 20 kg. A pass of 50 and above includes 50. Every (d) and every (e) in both papers turns on that, and it is the cheapest mark on the paper to lose.
