The data flow diagram is the workhorse of Section B. It shows how data moves through a system: who sends it in, which processes transform it, where it is stored, and what comes out. Learn its four symbols, its three levels, and the handful of mistakes the examiner hunts for, and this becomes reliable, drawable marks.
Module Three · Unit 1

Data Flow Diagrams

By the end of this unit you can draw the four elements of a data flow diagram, build a context diagram, a Level 0 and a Level 1 from a scenario, and name and avoid the mechanical errors and illegal flows the examiner tests.

Anchor

Follow one form through an office. Somebody outside hands it in, that is an external entity. Somebody checks and stamps it, that is a process. It sits in a filing cabinet until it is needed, that is a data store. And it travels between all of these in somebody's hand, which is a data flow. Four things, and every data flow diagram you will ever draw is made of exactly those four.

TeachWhat process modelling is

Process modelling shows how a system works by following the data. The tool for it is the data flow diagram (DFD): a picture of how data moves from the outside world, through the processes that transform it, into and out of the places it is stored, and back out to the world. Where a use case diagram shows what the system does for its users, a DFD shows how data flows to make that happen.

The examiner also asks why a DFD is worth drawing before you build. Good reasons: it is a clear picture that non-technical users can check; it separates what the system does from how it is built; it shows the boundary of the system and every thing it touches; and it breaks a large system into manageable processes (functional decomposition again).

Must memoriseThe four elements

A DFD has exactly four elements. Draw each one exactly right; a wrong symbol loses the mark however good the logic.

  • External entity (a rectangle): a person, department or other system outside the system that sends data in or receives data out. Named with a noun (Customer, Bank).
  • Process (a circle or rounded rectangle, numbered): work that transforms data. Named with a verb phrase and given a number (1.0 Verify order).
  • Data store (an open-ended rectangle, two parallel lines, labelled D1, D2): data at rest, a file or table. Named with a noun (D1 Customers).
  • Data flow (an arrow): data in motion between the other elements. Named with the data it carries (order details), not with a verb.
TeachThe three levels

A DFD is drawn at levels, each an explosion of the one above. The terminology is examinable and slightly confusing, so pin it down:

  • The context diagram shows the whole system as a single process, numbered 0, with the external entities around it and the net data flows in and out. It has no data stores. It defines the boundary: everything inside the one circle is the system, everything drawn as a rectangle is outside it.
  • The Level 0 DFD (also called Diagram 0, and in some papers the Process 0 diagram) explodes that single process into the major processes of the system, numbered 1.0, 2.0, 3.0, and adds the data stores and the flows between them.
  • A Level 1 DFD explodes one of those processes into its sub-processes. A Level 1 of process 3.0 has processes numbered 3.1, 3.2, 3.3.

So when a paper says "draw a context diagram, a Level 0 and a Level 1 for the rent payment process", it wants three diagrams: the system as one bubble, then its major processes, then a close-up of the rent-payment process alone.

Must memoriseIllegal flows

A data flow shows data moving from one element to another, but a process must be at one end of every flow. Data cannot move on its own; something has to do the moving. So these four flows are illegal, and drawing one is a classic lost mark:

  • entity → entity (two outsiders talking bypass the system entirely)
  • entity → data store (nothing processed the data before storing it)
  • data store → data store (data copying itself with no process)
  • data store → entity (data leaving store straight to the outside with no process)

The rule in one line: every data flow must touch a process at one end. An entity talks to a process, a process talks to a store, a process talks to an entity; never store-to-store, store-to-entity, or entity-to-entity, or entity-to-store.

TrapData does not move itself

The sentence the paper gives you, "a data flow shows data movement from one system entity to another," is true but incomplete, and the follow-up "data cannot move between entities in a data flow diagram" catches people out. What it means: data never flows straight between two external entities, or straight into or out of a store without a process. If your diagram has an arrow from a rectangle to a rectangle, or from a data store straight to a rectangle, it is wrong. Put a process bubble in the middle.

Must memoriseMechanical errors

"What mechanical errors can result while constructing a DFD?" is a standard 3-mark question. There are three, all about a process whose inputs and outputs do not match:

  • Black hole: a process with input but no output. Data goes in and vanishes. (A process that stores data but produces nothing.)
  • Miracle (spontaneous generation): a process with output but no input. Data appears from nowhere.
  • Grey hole: a process whose inputs are insufficient to produce its output. Something needed is missing (a receipt that shows a price, from an input that never carried a price).

Memory hook: in goes nothing, out comes something = miracle; in goes something, out comes nothing = black hole; in goes too little = grey hole.

TeachData balancing

When you explode a process into a lower level, the data flowing into and out of the exploded process on the parent diagram must be exactly the data flowing into and out of its child diagram. This rule is data balancing (or balancing the DFD). If process 3.0 receives "payment" and sends out "receipt" on the Level 0, then its Level 1 must also receive "payment" and, in total, send out "receipt", no more and no less. An unbalanced DFD, where a flow appears or disappears between levels, is a mechanical error, and checking the balance is one way to validate the diagram's integrity after you draw it, along with checking that every process has both inputs and outputs and that no flow is illegal.

WorkedFrom a scenario to three diagrams

The routine for "draw a context diagram, a Level 0 and a Level 1" is always the same. Take the warehouse scenario: trucks arrive, drivers submit trucks, the manager tells a labourer to unload, the storekeeper takes inventory and generates a stock report for the manager.

  1. Find the external entities (who is outside sending or receiving). Truck driver, Warehouse manager. They become rectangles.
  2. Context diagram: one process for the whole system. One bubble "0 Warehouse system"; arrows in (truck, activity report) and out (stock report). No data stores yet.
  3. Level 0: explode into the major processes. 1.0 Unload truck, 2.0 Take inventory, 3.0 Generate report; add data store D1 Stock; wire the flows so each process has input and output.
  4. Level 1: explode one process, say 2.0 Take inventory. 2.1 Count stock, 2.2 Classify condition, 2.3 Update stock record; number them 2.x and balance the flows to match process 2.0.
  5. Validate. Every process has an input and an output (no black holes or miracles); no illegal flows; the levels balance.

Now you try: draw the context diagram for food ordering at a Nigerian airport, then give four reasons a DFD is helpful for modelling those processes before you build.

RecallCover the answers

1. Name the four elements of a DFD and the shape of each.

2. A process has an input but produces no output. Which mechanical error?

3. Why can you not draw an arrow straight from a data store to an external entity?

Answers

1. External entity (rectangle), process (numbered circle), data store (open-ended rectangle), data flow (arrow).

2. A black hole.

3. Every data flow must touch a process at one end; a store cannot send data to the outside without a process to move it.

Key point

A data flow diagram shows how data MOVES and is transformed, never when things happen or in what order. It has no decisions, no loops and no timing. Two rules then follow that the examiner checks first: every process must have at least one input and at least one output, and a child diagram must balance with the parent process it explodes.

Blunt version: a process must earn its outputs from its inputs. No inputs is a miracle, no outputs is a black hole, and not enough inputs is a grey hole.
