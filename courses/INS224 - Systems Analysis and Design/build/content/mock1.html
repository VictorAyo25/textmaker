AnswerMock 1 · Q1

a. ERD. Entities: CUSTOMER, ORDER, BOOK, COURIER. CUSTOMER 1:M ORDER (a customer places many orders, each order one customer); ORDER M:N BOOK (an order has many books, a book on many orders, resolved with an ORDER-LINE linking entity); COURIER 1:M ORDER (a courier delivers many orders). Crow's foot throughout.

b. DFDs. Context: one process "0 Bookstore" between CUSTOMER and COURIER, with order and payment in, confirmation and delivery out. Level 0: 1.0 Place order, 2.0 Take payment, 3.0 Arrange delivery, plus stores D1 Orders and D2 Books. Level 1 of 2.0: 2.1 Validate card, 2.2 Charge, 2.3 Issue receipt, balancing 2.0.

c. Succeed: clear requirements, user involvement, realistic schedule. Fail: unclear requirements, no user involvement, weak management support.

d. A crow's foot at each end is many-to-many: forward, one BOOK appears on many ORDERs; backward, one ORDER contains many BOOKs.

AnswerMock 1 · Q2

a. Class diagram. Classes MEMBER, STUDENT, STAFF, LOAN, BOOK, LIBRARIAN. STUDENT and STAFF generalise to MEMBER (hollow triangle). MEMBER 1 to * LOAN; LOAN * to 1 BOOK; LIBRARIAN records * LOAN. Give each class two attributes and a method.

b. Use case. Actors MEMBER and LIBRARIAN; use cases Register, Borrow book, Return book, Record loan. "Borrow book" includes "Check membership".

c. Activity. Start, "Request book", decision "registered member?" (no ends, yes continues), "Check availability", "Record loan", "Issue book", end.

d. A class is a blueprint (Book); an object is an instance of it (the specific copy of "Systems Analysis" with barcode 0012).

AnswerMock 1 · Q3

a. Is it technically feasible (can we build it)? Economically feasible (worth the cost)? Operationally feasible (will it be used and fit the business)?

b. Verify benefit outweighs cost; define requirements; develop alternatives; recommend the best; detail the chosen solution; implement (then monitor).

c. A model is a simplified picture of the system that shows the important parts so everyone can agree them before building, like an architect's drawing.

d. Technical skills: understanding computers, networks and databases and the tools of building, so she can specify and communicate technical requirements. (Business knowledge is also acceptable.)

e. Maintain the system, enhance the system, support the users (help desk).

f. Project manager, software architect, product designer.

AnswerMock 1 · Q4

a. Buy a packaged solution or outsource, not build; factors: short time available, lack of in-house skills, the system is not strategic (also cost, package fit).

b. Any two of data storage, data access logic, application logic, presentation logic.

c. Performance and security (the fourth is cultural/political).

d. Consistency, simplicity/clarity, user feedback.

e. Three tables, each with a primary key: Driver(driverId PK, name, phone), Trip(tripId PK, driverId FK, distance), Payment(payId PK, tripId FK, amount), five dummy rows each; driverId and tripId are the linking foreign keys.

AnswerMock 1 · Q5

a. Compare waterfall (strong documentation, rigid), prototyping (good for unclear needs, can be mistaken for finished), RAD (fast, weak on large systems), spiral (risk analysis each cycle, heavy), incremental (early delivery, integration effort), agile (handles change, light documentation clashes with audit needs), V-shape (test pairing, reliable, rigid). For a results system needing audit trails and one-session delivery, an incremental or V-shape approach fits well.

b. Define the problem, produce the schedule, confirm feasibility, staff the project, launch it.

c. Business: cut result-processing time, guarantee an audit trail. User: a lecturer enters marks online, a student views results instantly. Functional: record marks, compute the grade, generate a transcript. Non-functional: 99.9% availability, encrypt results. System: store results as time-stamped records keyed by matriculation number, integrate with the student database.

AnswerMock 1 · Q6

a. As-is: no remote consultation, records on paper, no e-prescriptions. To-be: video consultation, shared records, e-prescriptions. Assumptions: patients have devices and connectivity; the platform can integrate with hospital records; video quality is adequate for diagnosis.

b. Interview doctors (clinical workflow; depth); questionnaire to patients (what they want; reaches many); observe a clinic (real process); review existing records (data and integration).

c. UML is a standard notation for modelling object-oriented systems, created by Booch, Rumbaugh and Jacobson; used to visualise, specify, construct and document a system.

d. Structural (class, object) model what the system is; behavioural (use case, activity, sequence) model what it does.

e. Inheritance (hollow triangle, is-a); composition (filled diamond, part dies with the whole); aggregation (hollow diamond, part survives); association (plain line).
