Module Six · Unit 1

System Design and Architecture

By the end of this unit you can describe the client-server tiers, name the functions software architecture must provide and the non-functional requirements that shape hardware, state interface design principles, choose a system acquisition strategy, and design and populate a small relational database.

TeachClient-server tiers

Not in the course text A system's work can be split into three logical parts: presentation (the screens the user sees), application logic (the processing and rules), and data (storage and access). How these are spread across machines gives the client-server tiers, and the paper asks you to "explain the various client-server tiers to convince your boss":

  • Single-tier: all three parts on one machine (a mainframe or a standalone app). Simple, but does not scale.
  • Two-tier: a client holds the presentation (and often the application logic) and talks to a server that holds the data. The classic client and database server.
  • Three-tier: presentation on the client, application logic on a separate middle (application) server, and data on a database server. Each tier can be scaled and maintained on its own; this is the common web architecture.
  • N-tier (multi-tier): the middle tier is split further into more specialised servers. Most scalable, most complex.

Sell the three-tier to the boss on scalability and maintainability: because the tiers are separate, you can grow or replace one without disturbing the others.

TeachSoftware architectural functions

"Mention the software architectural functions the system will need to perform properly." Software architecture must provide four logical functions, which map onto the tiers above:

  • Data storage: holding the data (the database).
  • Data access logic: the processing needed to read and write that data (the queries).
  • Application logic: the business rules and processing.
  • Presentation logic: displaying information to the user and accepting their input.
Must memoriseHardware non-functional requirements

"The choice of hardware architecture depends on four non-functional requirements; the first is operational, name two others." The four categories of non-functional requirement that shape the hardware are:

  • Operational requirements: the environment the system must run in (operating system, network, hardware it must coexist with).
  • Performance requirements: speed, capacity, throughput and availability.
  • Security requirements: access control, encryption, protection of data.
  • Cultural and political requirements: local laws, languages, customs and standards the system must respect.

Memory hook: O P S C, "Operational, Performance, Security, Cultural". These are the non-functional "-ilities" of Module Two, grouped for choosing hardware.

TeachInterface design principles

Interface design decides how the system interacts with the outside world, chiefly the graphical user interface (GUI) the user works through. "Outline three principles of interface design":

  • Consistency: the same action looks and works the same way everywhere in the system, so the user can transfer what they learn.
  • Simplicity (and clarity): show only what is needed, in plain layout and language, so the interface is easy to learn and use.
  • User feedback: the system tells the user what is happening, confirms actions, and reports errors clearly.

Other acceptable principles: minimise user effort, prevent and handle errors gracefully, and respect the user's control.

Must memoriseSystem acquisition strategy

When a system is needed but the team lacks the time or skill to build it, you choose a system acquisition strategy. The three options, and the one to pick under time pressure:

  • Build (custom development): write it in-house. Best fit, most control, but slowest and needs the skills.
  • Buy (a packaged or off-the-shelf solution): purchase ready-made software. Fast and cheaper, but may not fit exactly.
  • Outsource: pay another company to build or run it. Good when you lack the skill or capacity in-house.

When a scenario says "the time frame is short and the project skills are not strategic", the answer is to buy a packaged solution or outsource, not to build. Supporting factors to cite: cost, time available, in-house skills, how well packages fit the need, and how strategic (core to the business) the system is.

Module Six · Unit 2

Project Management, Installation and Support

By the end of this unit you can list the project planning activities, decide whether to accept new features, give the reasons projects succeed or fail, name the stakeholders and their views, and describe installation and support.

Must memoriseProject planning activities

"Identify the five activities in project planning" (the Planning phase of Module One, as a delivery task):

  1. Define the problem (the business problem and scope).
  2. Produce the project schedule.
  3. Confirm project feasibility (technical, economic, operational, schedule, legal).
  4. Staff the project (allocate funds, assign members, obtain resources).
  5. Launch the project.
TeachScope creep and feature creep

Near the end of a project a client often asks for new features. Scope creep is uncontrolled growth of what the project must deliver; feature creep is the same at the level of individual features. The paper asks: as project manager, do you agree or refuse to add new features late? The exam-safe answer is to refuse (or defer), and give reasons:

  • It threatens the schedule and budget already agreed.
  • It risks the quality and stability of what is nearly finished.
  • New features belong in a change request or a later release, assessed properly, not bolted on under time pressure.

This is the "do not be afraid to cancel or revise scope" principle from Module One in action.

TeachWhy projects succeed or fail

"Enumerate reasons a project will succeed and reasons it can fail." The 25/26 paper gives you the first of each: a system succeeds when it is acceptable to the customer and fails if it cannot establish upper-management commitment. Others:

  • Succeed: clear requirements, strong user involvement, realistic schedule and budget, good project management, management support.
  • Fail: unclear or changing requirements, lack of user involvement, poor planning and estimation, weak management support, inadequate testing.
TeachStakeholders and their views

A stakeholder is anyone with an interest in the system. "Name three system stakeholders and describe how each views the system" wants you to show that different people want different things:

  • Users want the system easy to use and helpful to their daily work.
  • Managers want it to deliver business value on time and within budget.
  • Developers (the technical team) want clear requirements and a system that is feasible to build and maintain.

Others: owners, customers, and regulators. The point the examiner wants is that these views can conflict, and the analyst must balance them.

TeachJob roles, installation and support

Three loose ends the paper picks up:

  • Other job roles an analyst can grow into: project manager, software architect, software tester, product designer, business analyst.
  • Installation (conversion) uses one of the four strategies from Module One: direct cutover, parallel, phased, pilot. Choose by weighing risk against cost.
  • Support activities (the Support phase): maintain the system (fix bugs, minor adjustments), enhance it (add capability as the business changes), and support the users, which includes running a help desk. "What three activities will the support group participate in?" is exactly these three.
TeachWhat a model is, for the stakeholders

Finally, the paper asks how the analyst explains to stakeholders what a model is, given that "a model is a representation of an important aspect of the real world." Explain it plainly: a model is a simplified picture of the system that leaves out detail so everyone can see and agree the important parts before it is built, the way an architect's drawing lets a client approve a building before a brick is laid. The diagrams throughout this manual, the use case, the DFD, the ERD, the class diagram, are all models in exactly this sense.

RecallCover the answers

1. List the five project planning activities.

2. A client asks for new features near the deadline. What do you do, and why?

3. Name the three support-phase activities.

Answers

1. Define the problem, produce the schedule, confirm feasibility, staff the project, launch it.

2. Refuse or defer them, because they threaten the agreed schedule, budget and quality; handle them as a change request or later release.

3. Maintain the system, enhance the system, support the users (help desk).
