    Unit 1 — Foundations of Data Storage and Management 
 
INTRODUCTION 
 
In this unit, you will be introduced to the foundational concepts of 
information storage and management. You will also explore how 
digital information is captured, represented, stored, retrieved, se-
cured, and analysed. Understanding these processes is vital for 
building and working with effective databases and information sys-
tems. This unit also examines key performance attributes such as 
scalability, efficiency, and effectiveness, which determine how well 
a system handles growing data demands and serves users reliably. 
 
 
 
 
LEARNING 
OUTCOMES 
At the end of this unit, you should be able to: 
 Explain the purpose and scope of information storage and re-
trieval in database systems. 
 Identify real-world information management applications and 
their use cases. 
 Understand how information is captured and represented in 
digital form. 
 Describe techniques for indexing, searching, and ensuring in-
formation privacy. 
 Define the importance of data integrity and security. 
 Assess a system based on scalability, efficiency, and effective-
ness.

  1.1.1 
Information Storage and Retrieval 
 
Information storage refers to how data is persistently stored using digital structures 
(e.g., files, tables, documents) on physical or cloud-based storage systems. Retrieval 
is the process of locating and accessing this stored data using queries or indexing 
mechanisms. 
In database systems: 
 Data is typically stored in relations (tables) or documents (in NoSQL sys-
tems). 
 Structured data is stored with a schema (e.g., relational databases). 
 Unstructured or semi-structured data (e.g., logs, XML, JSON) is handled with 
flexible models. 
 Query languages (like SQL) are used to retrieve data efficiently. 
 Indexing, normalisation, and metadata improve data retrievability and or-
ganisation. 
 
  1.1.2 
Information Management Applications 
 
Information management systems help users and organisations to manage, access, 
and safeguard data. These include: 
 Library management systems (e.g., cataloguing books and lending his-
tory) 
 Healthcare information systems (e.g., patient records, treatment history) 
 Enterprise Resource Planning (ERP) systems (e.g., HR, accounting) 
 Customer Relationship Management (CRM) platforms (e.g., client inter-
actions) 
 Content management systems (e.g., websites, digital asset systems) 
These applications are underpinned by databases that enforce consistency, privacy, 
and availability of data. 
 
  1.1.3 
Information Capture and Representation 
 
Information capture 
Information capture refers to the process of collecting data from real-world sources. 
This could include: 
 Manual entry (e.g., filling forms) 
 Sensors/IoT devices

 Scanners/OCR 
 APIs from other systems 
Data representation  
Data representation refers to how captured data is formatted and stored: 
 Text, numbers, images, and binary formats 
 Use of schemas to define structure 
 Use of data types (e.g., INT, VARCHAR, DATE) in relational databases 
A database management system must ensure data types are enforced and suitable 
for intended use. 
 
  1.1.4 
Analysis and Indexing 
 
Once data is stored, systems must enable fast retrieval and meaningful analysis: 
Indexing creates lookup structures to improve query speed (e.g., B-trees, hash in-
dexes). 
 Search mechanisms use indexing to locate relevant records quickly. 
 Full-text search and natural language processing are used for unstructured 
data. 
Analysis involves summarising and extracting insights using: 
Aggregation (SUM, COUNT, AVG) 
 Filtering and sorting 
 Query optimisation to ensure performance 
 
  1.1.5 
Information Privacy, Integrity, and Security 
 
Privacy 
Ensures sensitive data (e.g., medical records, financial data) is not accessed by un-
authorised users. Involves: 
 Access control (e.g., role-based permissions) 
 Data anonymisation 
 Compliance with laws (e.g., GDPR, HIPAA) 
Integrity 
Guarantees that data is accurate and consistent over its lifecycle:

 Constraints (e.g., NOT NULL, UNIQUE, CHECK). 
 Referential integrity via foreign keys. 
 Transaction management (ACID properties). 
Security 
Protects against unauthorised access, alteration, or destruction: 
 Authentication and encryption. 
 Firewalls and database hardening. 
 Regular backups and disaster recovery planning. 
 
  1.1.6 
Scalability, Efficiency, and Effectiveness 
 
Scalability 
The ability of a system to handle increasing volumes of data or users. Achieved via: 
 Vertical scaling (stronger hardware) 
 Horizontal scaling (replication, sharding) 
Efficiency 
How well the system uses resources (CPU, memory, storage) to process operations. 
Relates to: 
 Query performance 
 Indexing strategies 
 Storage optimisation 
Effectiveness:  
Measures how well the system meets users' needs: 
 Accuracy of search results 
 System reliability and uptime 
 User satisfaction 
All three factors must be considered when designing or selecting an information 
system.

Data Definition Language (DDL) 
 
 It is a descriptive language that allows DBAs or users to describe and name

exist between different entities.

catalogue tables, information schema in some contexts).  
 The data directory contains metadata (data about data).

 A query language is a portion of DML involving information retrieval only.  
 The terms DML and query language are often used synonymously.

Levels of Abstraction 
 Levels of Abstraction: External level 
o This is the highest level in data abstraction.  
o At this level, users see the data in the form of rows and columns.  
o This level illustrates to the users how the data is stored in terms of 
tables and relations.  
o Users view full or partial data based on the business requirement.  
o The users will have different views here, based on their levels of ac-
cess rights.  
o For example, a student will not have access to see the lecturer's sal-
ary details, and an employee will not have access to see other em-
ployees' details, unless they are a manager.  
o At this level, one can access the data from the database and perform 
some calculations based on the data. 
o For example, calculate the tax from the salary of an employee, calcu-
late the CGPA of a Student, calculate the age of a person from his 
Date of Birth, etc. These users can be real users or any programs. 
o Any changes/ computations done at this level will not affect other 
levels of data.  
o That means, if we retrieve the few columns of the STUDENT table, it 
will not change the whole table, or if we calculate the CGPA of a Stu-
dent, it will not change/update the table.  
o This level of data is based on the levels below, but it will not alter the 
data at those lower levels 
 
 Levels of Abstraction: Logical/ Conceptual level 
o This is the next level of abstraction.  
o  It describes the actual data stored in the database in the form of ta-
bles and relates them through mapping.  
o This level does not have any information on what a user views at the 
external level.  
o This level has all the data in the database. 
o Any changes made in this level will not affect the external or physical 
levels of data.  
o That is, any changes to the table structure or the relation will not 
modify the data that the user is viewing at the external view or the 
storage at the physical level.

o For example, suppose we have added a new column ‘skills’, which 
will not modify the external view data on which the user was viewing

(using which Age will be derived) in the memory.

▪ Levels of Abstraction: Internal level

  1.2.11 Data Independence 
 
 Data Independence is the ability to modify the schema definition at one 
level without affecting the schema definition at the next higher level.  
 It is the type of data transparency that matters for a centralised DBMS.  
 It refers to the immunity of user applications to changes made in the defini-
tion and organisation of data. 
 The data independence and operation independence together give the fea-
ture of data abstraction. 
Types 
 
Figure 1.6: Data Independence 
▪ Physical Level of Data Independence 
o Physical data independence is the ability to modify the physical 
schema without causing application programs to be rewritten.  
o Modifications at this level are occasionally necessary to improve per-
formance; thus, this level deals with hiding the details of the storage 
structure from user applications.  
o It means the physical storage/level is changeable without affecting the 
conceptual or external view of the data.  
o The new changes are absorbed using mapping techniques. 
 
▪ Logical Level of Data Independence 
o Logical data independence is the ability to modify the logical schema 
without causing the application program to be rewritten.  
o Logical data independence is more difficult to achieve than physical 
data independence, since application programs are heavily dependent 
on the logical structure of the data that they access. 
o Modifications at the logical level are necessary whenever the logical 
structure of the database is altered (for example, when money-market 
accounts are added to the banking system).

  2.2.1 
Enhanced Entity-Relationship (EER) Model 
 
Enhanced entity-relationship (EER) is used to identify the model that resulted from 
extending the original E-R model with new modelling constructs. These extensions 
make the EER model semantically similar to object-oriented data modelling. 
 The most important modelling construct incorporated in the EER model is 
supertype/subtype relationships.  
o This facility enables the modelling of a general entity type (called the 
supertype) and then subdivides it into several specialised entity types 
(called subtypes) 
o Thus, for example, the entity type CAR can be modelled as a super-
type, with subtypes SEDAN, SPORTS CAR, COUPE, and so on.  
o Each subtype inherits attributes from its supertype and, in addition, 
may have special attributes and be involved in relationships of its 
own.   
o Adding new notation for modelling supertype/subtype relationships 
has greatly improved the flexibility of the basic E-R model. 
  
  2.2.2 
Supertypes and Subtypes 
 
One of the significant challenges in data modelling is to recognise and clearly rep-
resent entities that are almost the same, that is, entity types that share common 
properties but also have one or more distinct properties of interest to the organisa-
tion. 
A subtype  
A subgrouping of the entities in an entity type that is meaningful to the organisa-
tion.  
For example, STUDENT is an entity type in a university. Two subtypes of STUDENT 
are GRADUATE STUDENT and UNDERGRADUATE STUDENT.  
In this example, we refer to STUDENT as the supertype.  
A supertype  
A generic entity type that has a relationship with one or more subtypes.

Constraints in Supertype/Subtype Relationships 
 
There are additional notations to represent constraints on supertype/subtype rela-
tionships.  
These constraints make it possible to capture some of the important business rules 
that apply to these relationships. 
 The two most important types of constraints that are described in this sec-
tion are: 
o Completeness constraints 
o Disjointness constraints 
Completeness Constraints 
 A completeness constraint addresses the question of whether an instance 
of a supertype must also be a member of at least one subtype.  
 The completeness constraint has two possible rules:  
o Total specialisation  
o Partial specialisation 
 The Total specialisation rule specifies that each entity instance of the super-
type must be a member of some subtype in the relationship.  
 The Partial specialisation rule specifies that an entity instance of the super-
type is not allowed to belong to any subtype.

Disjointness Constraints 
 A disjointness constraint addresses whether an instance of a supertype may 
simultaneously be a member of two (or more) subtypes.  
 The disjointness constraint has two possible rules:  
o The Disjoint rule  
o The Overlap rule 
 The Disjoint rule specifies that if an entity instance (of the supertype) is a 
member of one subtype, it cannot simultaneously be a member of any 
other subtype.  
 The Overlap rule specifies that an entity instance can simultaneously be a 
member of two (or more) subtypes.

Storing XML Documents 
 
One of the biggest questions that needs to be answered as XML data becomes more 
prevalent is “Where do we store these data?”  
1. Store XML data in a relational database by shredding the XML document: 
Shredding an XML document essentially means that we store each element 
of an XML schema independently in a relational table and use other tables 
to store the relationships among the components. Modern databases such 
as Microsoft SQL Server and Oracle provide capabilities beyond standard 
SQL to help store and retrieve XML data.  
2. Store the XML document using special XML columns that are made available 
as part of the database: These columns can be associated with an XSD, for 
example, to ensure that the XML document that is being inserted is a valid 
document. 
3. Store the XML document using a native XML database: These are non-rela-
tional databases designed specifically to store XML documents. 
Note: the first two options are primarily used when XML is used as a data exchange 
format between a browser and an application server. 
The first option is used when the majority of the information being processed is 
originally in XML format.

 Commercial RDBMS products from numerous vendors started to appear

 The relational data model represents data in the form of tables. 
  The relational model is based on mathematical theory 
 The relational data model consists of three (3) components:

Properties of a Relation 
1. Each relation (or table) in a database has a unique name.

 The relational data model includes several types of constraints, or rules lim-

 All of the values that appear in a column of a relation must be from the

Entity Integrity 
 The entity integrity rule is designed to ensure that every relation has a pri-

 In particular, it guarantees that every primary key attribute is non-null. 
 In some cases, a particular attribute cannot be assigned a data value.

  4.1.1 
Introduction to Normalisation 
 
 Normalisation is the process of decomposing relations with anomalies to 
produce smaller, well-structured relations. 
 It is a formal process for deciding which attributes should be grouped to-
gether in a relation so that all anomalies are removed. 
 Normalisation is based on normal forms and functional dependencies, 
which define business rules, not data usage.  
 Normalisation is a logical data-modelling technique used to ensure that 
data are well-structured from an organisation-wide perspective. 
 There are two major occasions during the overall database development 
process when you can usually benefit from using normalisation: 
o During logical database design, you should use normalisation con-
cepts to verify the quality of the relations that are obtained from 
mapping E-R diagrams. 
o When reverse-engineering older systems, Many of the tables and 
user views for older systems are redundant and subject to anomalies. 
  
Goals of Normalisation 
1. Minimise data redundancy to avoid anomalies and conserve storage space. 
2. Simplify the enforcement of referential integrity constraints. 
3. Make it easier to maintain data (insert, update, and delete). 
4. Provide a better design that is an improved representation of the real world 
and a stronger basis for future growth. 
Steps in Normalisation 
 Normalisation can be accomplished and understood in stages, each of 
which corresponds to a normal form. 
 A normal form is a state of a relation that requires that certain rules regard-
ing relationships between attributes (or functional dependencies) are satis-
fied.  
Normal Forms 
1. First normal form: any multivalued attributes (also called repeating groups) 
have been removed, so there is a single value (possibly null) at the intersec-
tion of each row and column of the table 
2. Second normal form: any partial functional dependencies have been re-
moved (i.e., nonkey attributes are identified by the whole primary key). 

===== PDF PAGE 102 =====
 
DTS 224 | DATA MANAGEMENT I 
 
100 
3. Third normal form: any transitive dependencies have been removed (i.e., 
non-key attributes are identified by only the primary key). 
4. Boyce-Codd normal form: Any remaining anomalies that result from func-
tional dependencies have been removed (because there was more than one 
possible primary key for the same non-keys). 
Functional Dependencies 
 Normalisation is based on the analysis of functional dependencies.  
 A functional dependency is a constraint between two attributes in which the 
value of one attribute is determined by the value of another attribute. 
 Functional dependency could be full, partial or transitive. 
 For any relation R, attribute B is functionally dependent on attribute A if, for 
every valid instance of A, that value of A uniquely determines the value of B. 
  The functional dependency of B on A is represented by an arrow, as fol-
lows: A → B. 
  
 
 
Characteristics of functional dependencies used in normalisation 
 Have a 1:1 relationship between attribute(s) on left and right-hand side of a 
dependency; 
 Hold for all time; 
 Are nontrivial.

A person’s name, address, and birth date are functionally dependent on 
that person’s Social Security number (in other words, there can be only one 
Name, one Address, and one Birthdate for each SSN). 
2. VIN → Make, Model, Colour 
The make, model, and original colour of a vehicle are functionally dependent 
on the vehicle identification number (as above, there can be only one value 
of Make, Model, and Colour associated with each VIN). 
3. ISBN → Title, FirstAuthorName, Publisher  
The title of a book, the name of the first author, and the publisher are func-
tionally dependent on the book’s international standard book number (ISBN). 
Determinants 
The attribute on the left side of the arrow in a functional dependency is called a 
determinant.  
SSN, VIN, and ISBN are determinants in the previous three examples. 
In the EMP COURSE relation, the combination of EmpID and CourseTitle is a deter-
minant.

Relational Keys 
 
One or more attributes that determine other attributes are called the key attributes. 
Keys may be Single or Composite (composed of several key attributes). 
1. Superkey /Primary Key 
2. Candidate Key/Composite Key 
 A primary key that contains more than one attribute of which no 
proper subset is a super key within the relation.  
 Uniqueness: In each tuple of R, values of K uniquely identify that tuple 
 Irreducibility: no proper subset of K has the uniqueness property  
3. Alternate Keys 
 Candidate keys/Composite keys that are not selected to be the pri-
mary key. 
4. Foreign Key 
An attribute in a relation of a database that serves as the primary key of an-
other relation in the same database. 
  
Candidate Keys 
A candidate key is an attribute, or combination of attributes, that uniquely identifies 
a row in a relation. A candidate key must satisfy the following properties, which are 
a subset of the six properties of a relation. 
 Unique identification: For every row, the value of the key must uniquely 
identify that row. This property implies that each non-key attribute is 
functionally dependent on that key. 
 Non-redundancy: No attribute in the key can be deleted without de-
stroying the property of unique identification. 
Relationship between Candidate Key and Determinant 
 A candidate key is always a determinant, whereas a determinant may or 
may not be a candidate key.  
 For example, in EMPLOYEE2, EmpID is a determinant but not a candidate 
key.  
 A candidate key is a determinant that uniquely identifies the remaining 
(nonkey) attributes in a relation.  
 A determinant may be

 part of a composite candidate key (such as EmpID in EMPLOYEE2), or

 Step 2: Convert to Second Normal Form

 Step 3: Convert to Third Normal Form 
 A relation is in third normal form (3NF) if it is in second normal form and no 
transitive dependencies exist.  
 A transitive dependency in a relation is a functional dependency between 
the primary key and one or more non-key attributes that are dependent on 
the primary key via another non-key attribute. 
 For example, there are two transitive dependencies in the CUSTOMER OR-

o OrderID → CustomerID → CustomerName 
o OrderID → CustomerID → CustomerAddress 
 In other words, both customer name and address are uniquely identified by 
CustomerID, but CustomerID is not part of the primary key (as we noted 
earlier). 
 Transitive dependencies create unnecessary redundancy that may lead to 
the type of anomalies discussed earlier. 
Removing Transitive Dependencies 
You can easily remove transitive dependencies from a relation by means of a three-
step procedure: 
 For each nonkey attribute (or set of attributes) that is a determinant in a re-
lation, create a new relation.  
o That attribute (or set of attributes) becomes the primary key of the 
new relation. 
o Move all of the attributes that are functionally dependent only on 
the primary key of the new relation from the old to the new relation. 
o Leave the attribute that serves as a primary key in the new relation in 
the old relation to serve as a foreign key that allows you to associate 
the two relations.

Boyce–Codd Normal Form (BCNF) 
Based on functional dependencies that take into account all candidate keys in a 
relation, BCNF also imposes additional constraints beyond the general definition of 
3NF. 
Normalising 3NF to BCNF 
 A relation is in BCNF if and only if every determinant is a candidate key.  
 Note: The attribute on the left side of the arrow in a functional dependence 
is called the determinant. 
 The difference between 3NF and BCNF is that for a functional dependency 
 
A ® B,  
 3NF allows this dependency in a relation if B is a primary-key attribute and A 
is not a candidate key. 
 Whereas BCNF insists that for this dependency to remain in a relation, A must 
be a candidate key.  
 To test whether a relation is in BCNF, we identify all the determinants and 
make sure that they are candidate keys. Recall that a determinant is an at-
tribute, or a group of attributes, on which some other attribute is fully func-
tionally dependent.

 Fifth normal form: Any remaining anomalies have been removed.

INTRODUCTION 
 
In this unit, you will learn about two key categories of SQL com-
mands: Data Definition Language (DDL) and Data Manipulation Lan-
guage (DML). You will explore the CREATE command, which is used 
to build new database structures. You will also focus on the core 
DML operations: INSERT for adding data, SELECT for retrieving data, 
and UPDATE for modifying existing data. These commands are es-
sential for interacting with and managing data within a database sys-
tem. Practical examples will guide you in understanding how to use 
these SQL statements effectively. 
 
 
 
LEARNING 
OUTCOMES 
At the end of this unit, you should be able to: 
 Understand DDL commands and use the CREATE, ALTER and 
DROP commands efficiently 
 Manipulate a given database practically using DML commands 
such as SELECT.

  5.2.6 
Writing SQL Commands 
 
 SQL statement consists of reserved words and user-defined words. 
 Reserved words are a fixed part of SQL and must be spelt exactly as re-
quired and cannot be split across lines.  
 User-defined words are made up by the user and represent names of vari-
ous database objects, such as relations, columns, and views. 
 Most components of an SQL statement are case insensitive, except for lit-
eral character data. 
 More readable with indentation and lineation:  
o Each clause should begin on a new line. 
o Start of a clause should line up with the start of other clauses. 
o If a clause has several parts, each should appear on a separate line 
and be indented under the start of the clause. 
  
  5.2.7 
Literals 
 
 Literals are constants used in SQL statements. 
 All non-numeric literals must be enclosed in single quotes (e.g. ‘London’). 
 All numeric literals must not be enclosed in quotes (e.g. 650.00).

SELECT Statement – Grouping 
 Use the GROUP BY clause to get sub-totals. 
 SELECT and GROUP BY are closely integrated: each item in the SELECT list 
must be single-valued per group, and the SELECT clause may only contain: 
o column names 
o aggregate functions  
o constants 
o expression involving combinations of the above. 
 All column names in the SELECT list must appear in the GROUP BY clause 
unless the name is used only in an aggregate function.  
 If WHERE is used with GROUP BY, WHERE is applied first, then groups are 
formed from the remaining rows satisfying the predicate. 
 ISO considers two nulls to be equal for purposes of GROUP BY. 
  
Example 1: Use of GROUP BY 
Find the number of staff in each branch and their total salaries. 
SELECT branchNo,  
     COUNT(staffNo) AS count, 
 
SUM(salary) AS sum 
FROM Staff 
GROUP BY branchNo 
ORDER BY branchNo;

Restricted Groupings – HAVING clause 
 HAVING clause is designed for use with GROUP BY to restrict groups that 
appear in final result table. 
 Similar to WHERE, but WHERE filters individual rows whereas HAVING filters 
groups. 
 Column names in HAVING clause must also appear in the GROUP BY list or 
be contained within an aggregate function. 
Example 1: Use of HAVING 
For each branch with more than 1 member of staff, find number of staff in each 
branch and sum of their salaries. 
SELECT branchNo,  
    COUNT(staffNo) AS count, 
  
 SUM(salary) AS sum 
FROM Staff 
GROUP BY branchNo 
HAVING COUNT(staffNo) > 1 
ORDER BY branchNo;

Unit 1: Answers to Self-Assessment Questions 
 
Q1: What is the purpose of indexing in a database, and how does it improve 
performance? 
Indexing creates lookup structures to improve query speed. It enhances perfor-
mance by allowing the database to quickly locate relevant records without scanning 
the entire dataset. Techniques like B-trees and hash indexes are used to build index 
structures. Search mechanisms utilise these indices to accelerate retrieval, especially 
in large datasets.  
Q2: Explain the differences between data privacy, data integrity, and data 
security. 
1. Data Privacy ensures that sensitive data, such as medical or financial records,

Q1. What is the purpose of the relational keys? 
Relational keys are used to ensure logical consistency and uniqueness within data-
base tables. 
 A primary key is an attribute or combination of attributes that uniquely 
identifies each row in a relation. 
 A composite key is a primary key made up of more than one attribute. 
 A foreign key is an attribute in one relation that serves as the primary key of 
another relation, enabling relationships between tables. 
 Their purpose is to maintain connections between tables, prevent duplicate 
rows, and ensure that each record can be accurately retrieved and refer-
enced. 
Q2. What are integrity constraints? Explain them. 
Integrity constraints are rules applied to ensure the accuracy, consistency, and va-
lidity of data in a relational database. There are three major types: 

===== PDF PAGE 177 =====
 
DTS 224 | DATA MANAGEMENT I 
 
175 
 Domain Constraint: specifies the permissible values for an attribute, includ-
ing data type, length, and value range. 
 Entity Integrity: ensures that every table has a primary key and that none of 
its values is null. This guarantees that each record can be uniquely identi-
fied. 
 Referential Integrity: ensures that foreign key values in one table must ei-
ther match a primary key in another table or be null, maintaining con-
sistency across related tables

Q1. What is normalisation, and why is it important in relational database 
design? 
 Normalisation is the process of decomposing relations with anomalies into 
smaller, well-structured relations. 
 It ensures that data are logically structured, reduces data redundancy, and 
eliminates update, insertion, and deletion anomalies. 
 It simplifies the enforcement of referential integrity constraints, ensures 
better data integrity, and provides a stronger foundation for future data-
base growth. 
 Normalisation is a key part of logical database design and helps represent 
real-world entities more accurately.

Q2. What is the purpose of the Cartesian product and join operations, and 
how do they differ in terms of output and use cases? 
 The Cartesian product (×) combines every tuple of one relation with every 
tuple of another, generating all possible combinations. It is used to merge 
relations when no explicit condition is given, typically as a precursor to a 
join. 
 The JOIN operation (⋈) combines related tuples from two relations based 
on a common attribute or condition. The natural JOIN merges relations us-
ing attributes with the same name and eliminates duplicate columns.  
Key Differences: 
 Output: Cartesian product returns all combinations (may be large and irrel-
evant), while join returns only meaningful combinations based on matching 
attributes. 
 Use Case: Cartesian product is rarely used directly; join is preferred when 
combining logically related data from multiple tables.
