Module Two · Unit 3

Semi-Structured Models: XML and JSON

Not all data fits neatly into a table with fixed columns. Semi-structured models keep some structure, tags and nesting, while letting every record differ. XML and JSON are the two you must be able to read and write.

By the end of this unit you can: say what semi-structured data is and when it is used; read and write both XML and JSON; and explain how XML data is stored, queried, and displayed.

3.1 Between rigid and formless

A structured model (the relational table) has a fixed schema: every row has the same columns. Unstructured data (a plain document, an image) has none. A semi-structured model sits between: it carries structure through tags or keys, but the structure can vary from one record to the next and change often.

  • Flexible schema. Two forms: wide-column, where the set of attributes is not fixed and new ones are added as needed; and sparse-column, where there is a fixed but huge set of possible attributes and each record fills in only the few it uses, the rest left null.
  • Multivalued types. An attribute may hold a set or array of values, for example interests = {basketball, cooking, jazz}, which a flat table forbids.
  • Nested types. An attribute may itself be structured, for example name broken into first and last. The two models built on these ideas are JSON and XML.

3.2 JSON and XML, side by side

Both represent the same fact. JSON (JavaScript Object Notation) uses braces and key-value pairs; XML (eXtensible Markup Language) uses paired tags in angle brackets. The same staff record in each:

JSON
{
  "staffNo": "SG37",
  "name": { "first": "Ann", "last": "Beech" },
  "skills": ["admin", "sales"]
}
XML
<staff>
  <staffNo>SG37</staffNo>
  <name><first>Ann</first><last>Beech</last></name>
  <skills>admin</skills>
  <skills>sales</skills>
</staff>

Both are self-describing (the tags or keys name the data), hierarchical (values nest inside values), and need no fixed schema. XML tags always come in pairs, <tag>...</tag>, and can represent both relational rows and tree-shaped documents such as a purchase order with nested line items.

3.3 Storing, querying, and displaying XML

  • Storing. Three ways: shredding it into relational tables (each element to a column, with relationship tables); a dedicated XML column type (optionally validated against an XSD schema); or a purpose-built native XML database.
  • Querying. XPath expressions locate data by a path through the tree; XQuery is the full query language built on XPath. As the text puts it, "XQuery is to XML as SQL is to relational databases".
  • Displaying. A stylesheet in XSL (Extensible Stylesheet Language), applied through XSLT, transforms XML into a display format such as an HTML table, so the same data can render on a phone, a tablet, or a page.
Must memoriseKey features of semi-structured data
  • Schema flexibility: no fixed schema; fields vary per record.
  • Hierarchical structure: data nests in trees or graphs.
  • Self-describing: tags or keys carry the data's own metadata.
  • Partial organisation: more manageable than unstructured data because the tags impose some order.
WorkedTEXT M2U3 self-assessment

Is XML the same as HTML? Justify. No. HTML has a fixed set of tags with a fixed meaning, and its job is to display content in a browser. XML lets you define your own tags, and its job is to describe and carry data, not to display it. HTML says how something looks; XML says what something is.

Explain the semi-structured data types. Flexible-schema records (wide-column and sparse-column), multivalued attributes (sets or arrays of values), and nested attributes (structured values within values), as realised by JSON and XML.

Four inconveniences of semi-structured models (TMA): no enforced schema so data quality is harder to guarantee; querying is less mature than SQL (XQuery is not widely adopted); larger storage because tags repeat on every record; and weaker support for the integrity constraints a relational DBMS enforces automatically.

Q. Differentiate between SQL and NoSQL databases.

A SQL (relational) database stores data in tables with a fixed schema and relationships enforced by keys, and is queried with SQL; it favours strong consistency and structured data. A NoSQL database stores data in flexible forms (documents, key-value pairs, wide-columns, graphs) with little or no fixed schema, and scales out across many machines; it favours flexibility and horizontal scaling over strict structure. Use SQL when the data is regular and integrity matters most; use NoSQL when the data is varied, huge, or rapidly changing.

Why create a conceptual model before building a database (TMA3)? It captures the business rules and the structure of the data in a form everyone can agree on, before any cost is sunk in tables or code. It surfaces mistakes early (a missing relationship, a wrong cardinality) when they are cheap to fix, improves communication between users and developers, and gives a DBMS-independent blueprint that the logical and physical designs are then derived from.
