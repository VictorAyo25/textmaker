Functional Dependencies
and Normalization

One table crammed with everything hides errors that only surface when you insert, update, or delete. Normalization is the disciplined splitting of that table into well-behaved relations, and it is the single most reliable source of marks on the paper.
Module Four · Unit 1

Normalization

A procedure with a fixed set of steps. You are given a table and its functional dependencies; you produce a set of relations in third normal form, or Boyce-Codd normal form, showing your working. Master one worked example and the rest are the same moves.

By the end of this unit you can: define full, partial, and transitive functional dependencies; draw a functional-dependency diagram; and normalize any given table to 3NF or BCNF, stating every step and the resulting relations.

1.1 Why: the update anomalies

Put everything in one table and three faults appear. Insertion anomaly: you cannot record a new property until someone inspects it, because inspection data shares the row. Update anomaly: a staff member's name, repeated on every inspection row, must be changed in every one or the copies disagree. Deletion anomaly: deleting the last inspection of a property loses the property's address too. Normalization removes all three by giving each fact one home.

1.2 Functional dependencies

An attribute B is functionally dependent on A, written A → B, if each value of A has exactly one value of B. A is the determinant. Three kinds are examined by name:

Must memoriseThree functional dependencies
  • Full functional dependency: B depends on the whole of a composite determinant A, not on any part of it. (propertyNo, iDate) → iTime is full: you need both.
  • Partial functional dependency: B depends on only part of a composite key. With key (propertyNo, iDate), propertyNo → pAddress is partial: pAddress needs only propertyNo.
  • Transitive functional dependency: B depends on the key only through another non-key attribute. (propertyNo, iDate) → staffNo → sName makes sName transitively dependent.

A determinant is the attribute (or set of attributes) on the left of a functional dependency, the thing that determines another. In fd propertyNo → pAddress, propertyNo is the determinant. The three dependency types are in the box above; the one-line hooks are: full needs the whole composite key, partial needs only part of it, transitive reaches the key only through a non-key attribute. (For 25/26's EMPLOYEE2, the determinants are EmpID → Name, DeptName, Salary, and the composite (EmpID, CourseTitle) → DateCompleted, the only full dependency.)

1.3 The normal forms

Must memorise1NF to BCNF
  • 1NF (first normal form): every cell holds a single value; no repeating groups.
  • 2NF (second normal form): in 1NF, and no partial dependency (every non-key attribute depends on the whole key).
  • 3NF (third normal form): in 2NF, and no transitive dependency (no non-key attribute depends on another non-key attribute).
  • BCNF (Boyce-Codd normal form): in 3NF, and every determinant is a candidate key. The strictest of the four.

The pattern is always the same: 2NF removes partial dependencies, 3NF removes transitive dependencies, BCNF removes any determinant that is not a candidate key.

Given StaffPropertyInspection(propertyNo, pAddress, iDate, iTime, comments, staffNo, carReg, sName) with primary key (propertyNo, iDate): draw the FD diagram, explain transitive dependency, and normalize to 3NF.

FDs: fd1 (propertyNo, iDate) → iTime, comments, staffNo, carReg, sName; fd2 propertyNo → pAddress; fd3 staffNo → sName; fd4 (staffNo, iDate) → carReg.

Answer

Functional-dependency diagram

Transitive dependency here: (propertyNo, iDate) determines staffNo, and staffNo determines sName, so sName depends on the key only through staffNo. That is what 3NF removes.

Step to 2NF (remove the partial dependency)

pAddress depends on propertyNo alone (part of the key), so lift it out:

Property(propertyNo, pAddress)                          PK propertyNo
PropertyInspection(propertyNo, iDate, iTime, comments, staffNo, carReg, sName)
   PK (propertyNo, iDate)   FK propertyNo -> Property

Step to 3NF (remove the transitive dependency)

sName depends on non-key staffNo, so lift staffNo → sName into its own relation:

Property(propertyNo, pAddress)              PK propertyNo
Staff(staffNo, sName)                       PK staffNo
PropertyInspection(propertyNo, iDate, iTime, comments, staffNo, carReg)
   PK (propertyNo, iDate)  FK propertyNo -> Property  FK staffNo -> Staff

Three relations, each fact in one place. carReg stays with the inspection because it is identified by that inspection (propertyNo, iDate). This is the final 3NF answer.

Candidate keys

Patient(PNo, PName)                          PK PNo

To 3NF (remove transitive dependencies)

StaffNo → DentistName (non-key to non-key) and (StaffNo, ADate) → SurgeonNo both violate 3NF. Lift each out:

Patient(PNo, PName)                          PK PNo
Staff(StaffNo, DentistName)                  PK StaffNo
SurgeonAssign(StaffNo, ADate, SurgeonNo)     PK (StaffNo, ADate)
Appointment(PNo, ADate, StaffNo, ATime)

In Appointment, both (PNo, ADate) and (StaffNo, ADate, ATime) are candidate keys, and they are the only determinants, so every determinant is a candidate key. The four relations above are already in BCNF.

WorkedPQ 21/22 Q2c R(A,B,C,D) to BCNF

Q. R has attributes ABCD with FDs C → D, C → A, B → C. Find the candidate key, the best normal form R is in, and decompose to BCNF.

Candidate key. B determines C (given), C determines A and D, so B determines A, C, D, hence B determines everything: B is the sole candidate key.

Best normal form. Non-key attributes are A, C, D. B → C → A and B → C → D are transitive dependencies, so R is not in 3NF. There is no partial dependency (the key B is a single attribute), so R is in 2NF but not 3NF.

Decompose to BCNF. The offending determinant is C (not a candidate key). Split it off:

R1(C, A, D)    PK C     (from C -> A, C -> D)
R2(B, C)       PK B     FK C -> R1     (from B -> C)

Now every determinant (C in R1, B in R2) is a candidate key of its relation, and the join of R1 and R2 on C reconstructs R, so the decomposition is lossless and dependency-preserving.

TrapPartial vs transitive

The examiner's favourite snare is labelling a dependency wrongly. A partial dependency is on part of the key; a transitive dependency is on a non-key attribute. If the determinant is a piece of the primary key, it is partial (fix in 2NF). If the determinant is an ordinary attribute, it is transitive (fix in 3NF). Read the determinant, not the dependent.
