Module Three · Unit 1

The Relational Model

A relation is a table, and that is nearly the whole idea. The marks are in the precise vocabulary, the several kinds of key, and the two integrity rules, all of which the examiner asks for by their exact names.

By the end of this unit you can: define relation, tuple, attribute, domain, degree, cardinality, and schema; distinguish super, candidate, primary, alternate, and foreign keys; state the entity and referential integrity rules; and list the properties of a well-formed relation.

WorkedPQ 25/26 Q4a · PQ 24/25 Q1a · PQ 15/16 Q4a

Q. Describe the relational data model; and define relation, relational algebra, data model, attribute and tuple, domain, degree and cardinality.

The relational data model represents all data as a collection of relations (two-dimensional tables of rows and columns), where relationships between data are expressed by common values, not by pointers. A relation is a table with named columns and unordered rows. Relational algebra is the set of operations (select, project, join, and so on) used to query relations, covered in Module Five. A data model is a collection of concepts for describing data, its relationships, and its constraints. An attribute is a column; a tuple is a row. A domain is the set of permitted values of an attribute. Degree is the number of attributes; cardinality is the number of tuples.

1.2 Keys

Must memoriseThe five keys
  • Super key: any set of attributes that uniquely identifies a tuple (may include extra, unnecessary attributes).
  • Candidate key: a minimal super key, one with no unnecessary attribute removed. A relation may have several.
  • Primary key (PK): the one candidate key chosen to identify tuples. Cannot be null.
  • Alternate key: a candidate key not chosen as the primary key.
  • Foreign key (FK): an attribute in one relation whose values must match the primary key of another (or be null); this is what links tables.

From here on, schema listings write PK for the primary key and FK for a foreign key, so a relation such as ROOM(roomNo, hotelNo, price) is annotated PK roomNo, hotelNo · FK hotelNo -> HOTEL.

WorkedPQ 24/25 Q5a · PQ 23/24 Q1a · PQ 25/26 Q6a

Q. Define: primary key, candidate key, foreign key, super key, alternate key, schema, tuple.

All are in the boxes above. Compact model answers: a super key uniquely identifies a row but may carry spare attributes; a candidate key is a super key with nothing spare; the primary key is the chosen candidate key and is never null; an alternate key is a candidate key not chosen; a foreign key matches a primary key elsewhere and links the two relations; a schema is a relation's name and its attributes; a tuple is one row.

WorkedPQ 15/16 Q2a

Q. What is the relationship between a candidate key and a foreign key?

A candidate key uniquely identifies tuples within its own relation. A foreign key refers from one relation to a candidate key (in practice the primary key) of another. So a foreign key's whole purpose is to point at a candidate key elsewhere: the candidate key is the target, the foreign key is the pointer, and referential integrity is the rule that the pointer must always find its target.

1.3 The two integrity rules

Must memoriseEntity and referential integrity

Entity integrity: no part of a primary key may be null. (If it were, the row could not be identified.)

Referential integrity: every foreign-key value must either match an existing primary-key value in the referenced relation, or be wholly null. (No row may point at a row that does not exist.)

WorkedPQ 15/16 Q4b

Q. Given Hotel(hotelNo, hotelName, city), Room(roomNo, hotelNo, type, price), Booking(hotelNo, guestNo, dateFrom, dateTo, roomNo), Guest(guestNo, guestName, guestAddress): (i) identify the foreign keys; (ii) explain how entity and referential integrity apply; (iii) give sample rows that observe integrity.

(i) Foreign keys

Room.hotelNo references Hotel.hotelNo. Booking.hotelNo references Hotel.hotelNo, Booking.guestNo references Guest.guestNo, and Booking.(roomNo, hotelNo) references Room.(roomNo, hotelNo).

(ii) The rules here

Entity integrity: no Hotel may have a null hotelNo; no Booking may have a null in any of hotelNo, guestNo, or dateFrom (its composite primary key). Referential integrity: a Booking's hotelNo must be a hotel that exists, its guestNo a guest that exists, and its (roomNo, hotelNo) a room that exists.

(iii) Sample rows that observe integrity

Hotel
hotelNo  hotelName    city
H1       Grand        London
H2       Bayview      Glasgow
Guest, Room, Booking (each FK matches a row above)
Guest:   G1  John Kay  London
Room:    R1  H1  single  60.00
Booking: H1  G1  2026-01-10  2026-01-12  R1

The Booking is legal because H1 is a real hotel, G1 a real guest, and (R1, H1) a real room. Change any one to a value not shown above and referential integrity is broken.

1.4 What makes a relation well-formed

WorkedPQ 24/25 Q2b six properties of a good relation

Q. List six properties that define a well-structured relation.

  1. Each cell holds a single value (the relation is atomic, no repeating groups).
  2. Each attribute has a distinct name.
  3. All values in an attribute come from the same domain.
  4. The order of attributes is irrelevant.
  5. The order of tuples is irrelevant.
  6. Every tuple is unique (no two identical rows; guaranteed by the primary key).

Module Three · Unit 2

From Conceptual to Logical Design

The mechanical step every year: an ER or EER diagram is handed to you and you turn it into relations. There is a fixed set of rules; learn them and the question becomes bookkeeping.

By the end of this unit you can: map entities, every kind of relationship, multivalued attributes, and supertype/subtype structures into relations with correct primary and foreign keys.

2.1 The mapping rules

Must memoriseER to relations
  • Each strong entity becomes a relation; its identifier becomes the primary key.
  • A one-to-many relationship puts the primary key of the "one" side into the "many" side as a foreign key.
  • A many-to-many relationship becomes its own relation, whose primary key is the two entities' keys together, plus any relationship attributes.
  • A one-to-one relationship puts the key of one side into the other as a foreign key (usually on the optional side).
  • A multivalued attribute becomes its own relation, keyed by the entity's key plus the attribute.
  • A weak entity becomes a relation whose primary key includes the identifying owner's key.
  • A supertype/subtype maps either to one relation with all attributes (plus a type flag), or to a relation per subtype sharing the supertype's key. The common choice: one relation for the supertype and one per subtype, each subtype keyed by the supertype's key.

2.2 Worked: employee, certificate, course

Exam questionPQ 19/20 Q1c

Transform to a relational schema showing referential integrity: EMPLOYEE (Employee ID, Employee Name, Birth Date) earns, through the associative entity CERTIFICATE (Certificate Number, Date Completed), a COURSE (Course ID, Course Title, Topic). An employee earns many certificates; each certificate is for one course.

Answer

Two strong entities become relations. CERTIFICATE is an associative entity between EMPLOYEE and COURSE, so it becomes a relation carrying both foreign keys.

EMPLOYEE(EmployeeID, EmployeeName, BirthDate)
   PK EmployeeID

COURSE(CourseID, CourseTitle, Topic)
   PK CourseID

CERTIFICATE(CertificateNumber, DateCompleted, EmployeeID, CourseID)
   PK CertificateNumber
   FK EmployeeID -> EMPLOYEE
   FK CourseID   -> COURSE

Referential integrity: every EmployeeID and CourseID in CERTIFICATE must match a real EMPLOYEE and COURSE.

2.3 Worked: the bank card (an EER with subtypes)

Exam questionPQ 24/25 Q4b

Transform the bank-card conceptual design to a logical design. CUSTOMER (Customer ID, Name, Address) holds a CARD ACCOUNT (Account ID, Exp Date, Card Type). CARD ACCOUNT is a disjoint supertype over DEBIT CARD (Bank No) and CREDIT CARD (Cur Bal). A CREDIT CARD is billed through CHARGES (Charge Date, Charge Time, Amount) to a MERCHANT (Merch ID, Merch Addr).

Answer
CUSTOMER(CustomerID, Name, Address)          PK CustomerID
CARD_ACCOUNT(AccountID, ExpDate, CardType, CustomerID)
   PK AccountID   FK CustomerID -> CUSTOMER
DEBIT_CARD(AccountID, BankNo)                PK AccountID  FK -> CARD_ACCOUNT
CREDIT_CARD(AccountID, CurBal)               PK AccountID  FK -> CARD_ACCOUNT
MERCHANT(MerchID, MerchAddr)                 PK MerchID
CHARGES(AccountID, MerchID, ChargeDate, ChargeTime, Amount)
   PK (AccountID, MerchID, ChargeDate)
   FK AccountID -> CREDIT_CARD   FK MerchID -> MERCHANT

Each subtype becomes a relation sharing the supertype's key (AccountID). CHARGES, a many-to-many with attributes, becomes its own relation.

2.4 Worked: the university dining service

Exam questionPQ 25/26 Q2d

Transform the University Dining Service EER to relational schemas: MENU (Menu ID, Description, Type) contains many DISH (Dish ID, Name, Prep Time, and a multivalued Ingredient) and is served at EVENT (Event ID, Date, Location, Time). STAFF (Emp ID, Name, Salary, multivalued Skill) work a WORK SCHEDULE (Start, End, Position) at events, and a staff member supervises other staff.

Answer

Entities become relations; the multivalued Ingredient and Skill each become their own relation; the many-to-many "contains" and "served at" become relations; "supervises" is a unary one-to-many, so a supervisor foreign key goes into STAFF.

MENU(MenuID, Description, Type)      PK MenuID
DISH(DishID, Name, PrepTime)         PK DishID
DISH_INGREDIENT(DishID, Ingredient)  PK both, FK DishID -> DISH
MENU_DISH(MenuID, DishID)            PK both  (contains, M:N)
EVENT(EventID, Date, Location, Time) PK EventID
MENU_EVENT(MenuID, EventID)          PK both  (served at, M:N)
STAFF(EmpID, Name, Salary, SupervisorID)  PK EmpID, FK SupervisorID -> STAFF
STAFF_SKILL(EmpID, Skill)            PK both, FK EmpID -> STAFF
WORK_SCHEDULE(EmpID, EventID, Start, End, Position)
   PK (EmpID, EventID), FK EmpID -> STAFF, FK EventID -> EVENT

Vacation Property Rentals. RENTER signs a RENTAL AGREEMENT which books a PROPERTY; PROPERTY is a disjoint supertype over BEACH (Blocks to Beach) and MOUNTAINS (Activity), and has a unary relationship on itself.

PHYSICIAN(PhysicianID, PhysicianName)          PK PhysicianID
PATIENT(PatientID, PatientName)                PK PatientID
TREATMENT(TreatmentCode, Description)          PK TreatmentCode
PATIENT_TREATMENT(PatientID, PhysicianID, TreatmentCode, PTDate, PTTime, PTResults)

WorkedPQ 20/21 mid Q1 · PQ 15/16 Q1d convert ER to tables

The general recipe applies to the Project/Organisation/Employee diagrams these questions give. Work top-down through the mapping rules: every entity a relation, every one-to-many a foreign key on the many side, every many-to-many a link relation, every subtype a relation sharing the supertype key. For example, an ORGANISATION executes many PROJECTs and employs many EMPLOYEEs, with a WorksFor link and a payment history:

ORGANISATION(OrgID, Name, Address, City, State)   PK OrgID
PROJECT(ProjectID, Name, Purpose, StartDate, EndDate, OrgID)
   PK ProjectID   FK OrgID -> ORGANISATION            (Executes, 1:M)
EMPLOYEE(SSN, Name, DOB, Address, City)            PK SSN
WORKS_FOR(SSN, OrgID, Cost)                         PK (SSN, OrgID)
   FK SSN -> EMPLOYEE  FK OrgID -> ORGANISATION       (WorksFor, M:N)
RecallCover the answers

1. Where does the foreign key go in a one-to-many relationship?

2. How is a many-to-many relationship mapped?

3. How is a multivalued attribute mapped?

4. How is a supertype with two subtypes usually mapped?

5. A unary one-to-many (staff supervises staff): how is it mapped?

Answers

1. Into the "many" side, as a foreign key to the "one" side. 2. As its own relation keyed by both entities' keys plus any relationship attributes. 3. As its own relation keyed by the entity key plus the attribute. 4. One relation for the supertype and one per subtype, each subtype keyed by the supertype's key. 5. A supervisor foreign key added to the same relation, referencing its own primary key.
