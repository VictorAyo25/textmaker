Module One · Unit 1

Foundations of Data Management

Before a single table is drawn, three questions: what is data, what do we actually do with it, and what makes a system that holds it good rather than merely large.

By the end of this unit you can: tell data from information; describe how data is captured, represented, stored, and retrieved; explain the difference between privacy, integrity, and security; and judge a system by its scalability, efficiency, and effectiveness.

1.1 Data, and information

A single value, 08:00, or Glasgow, or 350, is data: a raw fact with no context. On its own it tells you nothing. The moment you put it in context, "the 08:00 inspection of property PG4 in Glasgow was priced at 350", it becomes information: data that has been organised so a person can act on it.

Everything in this course is machinery for turning the first thing into the second reliably, for many users at once, without the facts contradicting each other. That is what "data management" means.

Must memoriseData vs information

Data is raw, unprocessed facts. Information is data processed and placed in a context that gives it meaning. Data is the input; information is the output you can make a decision with.

Storing data well means being able to find it again quickly, which is the job of an index, and retrieval is fetching it with a query. Indexing earns its own question on the paper, so it earns a worked answer here.

WorkedTEXT M1U1 Self-Assessment 1

Q. What is the purpose of indexing in a database, and how does it improve performance?

  1. Say what an index is. An index is a separate lookup structure that maps the values of a column to the locations of the rows that hold them, in the way the index at the back of a book maps a topic to its page numbers.
  2. Say what it replaces. Without an index, finding every row where city = 'Glasgow' means reading every row in the table, a full table scan. On a million-row table that is a million reads.
  3. Say how it helps. With an index on city, the system jumps straight to the matching entries (using a structure such as a B-tree or a hash index) and reads only those rows. Search, sorting, and joining all get faster.
  4. State the cost, because a complete answer names the trade-off. An index takes extra storage and must be updated on every insert, update, and delete, so indexing every column would slow writing down. You index the columns you search on.
Now you try: in one sentence each, give one column in a STAFF(staffNo, fName, lName, branchNo) table you would index and one you would not, and why.

1.3 Three things people confuse: privacy, integrity, security

These three words are used loosely in ordinary speech and precisely in this course. The examiner asks you to separate them, so separate them.

WorkedTEXT M1U1 Self-Assessment 2

Q. Explain the differences between data privacy, data integrity, and data security.

Data privacy concerns who is permitted to access which data. It is enforced with access control (role-based permissions), anonymisation of sensitive fields, and compliance with data-protection law. Example: an ordinary student may see their own results but not a lecturer's salary.

Data integrity concerns whether the data is accurate and consistent. It is enforced with constraints (NOT NULL, UNIQUE, CHECK), referential integrity (foreign keys that must match a real row), and transaction management so a half-finished update never leaves the data in a broken state. Example: a booking cannot reference a guest number that does not exist.

Data security concerns protection against unauthorised access and attack. It is enforced with authentication, encryption, firewalls, database hardening, and backups for disaster recovery. Example: passwords are stored encrypted, not in plain text.

One-line hook to remember them: privacy = who may see it, integrity = is it correct, security = keeping attackers out.

Must memoriseACID

Integrity leans on the transaction, and a good transaction has four properties, ACID: Atomicity (all of it happens or none of it does), Consistency (it moves the database from one valid state to another), Isolation (concurrent transactions do not tread on each other), Durability (once committed, it survives a crash). Learn the word and what each letter means.

1.4 Judging a system: scalability, efficiency, effectiveness

Three attributes decide whether a data system is any good. They sound similar and are not.

  • Scalability is the ability to keep working as data and users grow. You scale vertically by giving one machine more power (more CPU, memory, disk), or horizontally by spreading the load across many machines (replication, sharding).
  • Efficiency is how little resource the work costs: CPU, memory, storage, and query time. Good indexing and storage design buy efficiency.
  • Effectiveness is whether the system actually meets the users' needs: accurate results, reliable uptime, and user satisfaction.

The distinction between the last two is a favourite short question, so here it is, answered.

WorkedPQ 19/20 Q6a

Q. Differentiate between Information Efficiency and Information Effectiveness. Not in syllabus (phrased in the older wording; the ideas are the efficiency/effectiveness pair above, so you can still answer it fully.)

Information efficiency is about doing the thing right: producing the required information with the least resource and time, cost per query, storage used, response time. A report that is generated in one second using little memory is efficient.

Information effectiveness is about doing the right thing: producing information that actually serves the user's purpose, that is accurate, relevant, timely and complete enough to decide on. A report delivered instantly but showing the wrong figures is efficient yet not effective.

Hook: efficiency = doing it right (cheaply, quickly); effectiveness = doing the right thing (usefully, correctly).

Module One · Unit 2

Database Systems and Architecture

Why organisations abandoned loose files for databases, what a DBMS is and what sits inside it, and the layered architecture that lets the data and the programs change independently.

By the end of this unit you can: list the limitations of the file-based approach and the advantages of the database approach; define a database, a DBMS, a schema, and an instance; separate DDL from DML; explain the three levels of data abstraction and the two kinds of data independence; and tell a personal database from an enterprise one.

2.1 The file-based approach, and why it failed

Before databases, each part of an organisation kept its own files and wrote its own programs to read them. The sales department had a sales file; accounts had an accounts file; each with its own copy of the customer list. This is the file-based approach, and it fails in ways the examiner returns to every year.

Must memoriseLimitations of the file-based approach
  • Data redundancy. The same fact (a customer's address) is stored in several files.
  • Data inconsistency. Update it in one file and not another, and the copies now disagree.
  • Data isolation. Data is scattered across files in different formats, so writing a program to combine it is hard.
  • Program-data dependence. The file's structure is written into every program, so changing the structure means rewriting the programs.
  • Difficult concurrent access. Letting many users write at once safely is left to each program to solve, and mostly it is not solved.
  • Weak security and integrity. Rules live in program code, applied unevenly, easy to bypass.
WorkedPQ 25/26 Q2a · also PQ 20/21 Q1a, PQ 15/16 Q1c

Q. Explain two limitations of the file-based approach to data processing. (25/26 asks for two; 20/21 asks for three; 15/16 asks for five. One answer, scaled to the marks.)

Model answer (two, stated then explained)

1. Data redundancy and inconsistency. Because each program keeps its own files, the same data is duplicated across them. When one copy is updated and another is not, the files disagree, and there is no single correct version.

2. Program-data dependence. The physical structure of a file (its fields and their order) is embedded in the code of every program that reads it. A change as small as widening a field forces a change to every one of those programs.

For three, add data isolation (data scattered in incompatible formats is hard to combine). For five, add difficulty of concurrent access and weak security and integrity control. Naming the limitation and then explaining it in a sentence is what earns the mark; a bare list does not.

Now you try: the database approach fixes each of these. For redundancy and for program-data dependence, name the database feature that removes it. (Answers appear in 2.4 and 2.5 below.)

2.2 Database, DBMS, schema, instance

Four definitions the examiner asks for by name. Learn them in these words.

Must memoriseThe four core definitions

Database: a shared collection of logically related data (and a description of that data), designed to meet the information needs of an organisation.

DBMS (Database Management System): the software that lets users define, create, maintain, and control access to the database. Examples: MySQL, Oracle, PostgreSQL, Microsoft SQL Server.

Schema: the description of the data using a given data model, that is, the structure. It changes rarely. Example: Student{matricNo, name, address, programme, age}.

Instance (database instance): the actual data in the database at a particular moment. It changes constantly, on every insert, update, and delete.

Schema is to instance as the empty form is to the filled-in form: the form's layout is the schema, today's stack of completed forms is the instance.

WorkedPQ 24/25 Q4c · PQ 19/20 Q2c

Q. With two examples, describe a Database Management System. (24/25 Q4c) And define: data model, database instance, DBMS. (19/20 Q2c)

A DBMS is the software layer between the users and the stored data. It lets them define the structure (through a data-definition language), put data in and take it out (through a data-manipulation language), and it controls access, enforces integrity, and manages concurrency and recovery, so the applications do not each have to. Two examples: MySQL and Oracle Database (also acceptable: PostgreSQL, Microsoft SQL Server, IBM Db2).

A data model is a collection of concepts used to describe the structure of a database, that is, the data, the relationships between it, and the constraints on it. The relational model (tables) is the one this course centres on.

A database instance is the information held in the database at a particular point in time, a snapshot of its current contents.

You talk to a database in two registers. One defines the structure; the other moves the data around.

WorkedPQ 24/25 Q4d · PQ 25/26 Q5a

Q. Differentiate between data definition language (DDL) and data manipulation language (DML).

DDL is the part of a database language used to define and change the structure of the database: creating tables, altering columns, dropping objects, and stating constraints. Its statements are CREATE, ALTER, and DROP, and their effect is recorded in the data dictionary.

DML is the part used to work with the data itself: inserting new rows, updating and deleting existing ones, and retrieving them. Its statements are INSERT, UPDATE, DELETE, and SELECT.

In short: DDL changes the container, DML changes the contents.

2.4 Inside the DBMS: its components and its people

A DBMS is not one program but several parts working together, and it is run by people with defined roles. Two roles are regularly confused on the paper.

TeachComponents a DBMS provides

Asked to "list components of a DBMS", name from this set: the DDL compiler, the DML compiler / query language processor, the query processor (breaks a request into steps), the database manager (moves data between disk and memory), the file manager, the data dictionary / system catalogue, the DML pre-compiler, the authorisation and integrity manager, the transaction manager, and the recovery / backup manager. The database manager is the module that interfaces between the low-level stored data and the application programs and queries.

WorkedPQ 19/20 Q4b · PQ 21/22 Q5a(i)

Q. Explain the Database Manager and its responsibilities, and differentiate it from the Database Administrator.

The Database Manager is a software module inside the DBMS. It is the interface between the low-level data stored on disk and the application programs and queries that ask for it. Its responsibilities are moving data between disk and main memory, and enforcing, at run time, the integrity and access controls the database is set up with. It is a program.

The Database Administrator (DBA) is a person with central control over the data and the programs that access it. Their responsibilities are: defining the schema, granting authorisation for data access, specifying integrity constraints, defining storage structures and access methods, and modifying the schema or physical organisation as needs change.

The one-line separation: the Database Manager is a program inside the DBMS; the Database Administrator is a person who runs the database.

2.5 The layered architecture: three levels of data abstraction

This is the central idea of the whole unit, and the answer to the "program-data dependence" problem from 2.1. A database hides its physical storage behind layers, so that a user sees only what they need and a change at one layer does not ripple up to the next. The classic picture is the three-schema architecture, also called the three levels of data abstraction.

Must memoriseThe three levels

External level (view level): the highest. Each user or program sees only the slice of data relevant to it, as rows and columns, tailored to its access rights. A student's view can compute a CGPA or an age without ever seeing a lecturer's salary. Many different external views can exist over the same data.

Conceptual level (logical level): the middle. It describes all the data in the database as tables and the relationships between them, without any concern for how it is stored. This is the level the database designer works at.

Internal level (physical level): the lowest. It describes how the data is actually stored: the file organisation, the indexes, whether hashing or a B+ tree is used. (Some texts name a separate physical level below the internal one; the exam wants the three: external, conceptual, internal.)

WorkedPQ 25/26 Q2c · PQ 19/20 Q1b

Q. What is meant by data abstraction? Explain the three levels of data abstraction with examples. (25/26 Q2c) Equivalently: explain the differences between user views, a conceptual schema, and an internal schema as different perspectives of the same database. (19/20 Q1b)

Data abstraction is the hiding of the complex details of how data is stored, showing each user only what they need. It is what lets a user work with a table without knowing anything about disks or files.

  1. External level (user views). What one user or program sees: a customised subset of the data. Example: the "Student" view shows a student their courses and results but not other students' records, and not any salary data.
  2. Conceptual level (conceptual schema). The community view: every table and relationship in the database, described independently of storage. Example: the whole university schema, STUDENT, COURSE, LECTURER, DEPARTMENT, and how they relate.
  3. Internal level (internal schema). The storage view: how those tables are physically held, which files, which indexes, which access method. Example: STUDENT is stored as an indexed file with a B+ tree index on matricNo.

They are three perspectives on one database: the same STUDENT data, seen as a tailored view, as a logical table, and as bytes in an indexed file.

2.6 Why the layers matter: data independence

The layers are not decoration. They deliver data independence: the ability to change the schema at one level without having to change the level above it. This is the precise cure for the file-based approach's program-data dependence.

Must memoriseTwo kinds of data independence

Physical data independence: the ability to change the internal (physical) schema, adding an index, changing the file organisation, without changing the conceptual schema or rewriting any application program. Comparatively easy to achieve.

Logical data independence: the ability to change the conceptual schema, adding a column or a table, without changing the external views or rewriting programs that do not use the change. Harder to achieve, because programs depend closely on the logical structure.

Example of logical independence: users A and B both read EmployeeNumber and EmployeeName. B adds a Salary column to the schema. A's view and A's programs are untouched.

2.7 Two sizes of database: personal and enterprise

Teach

A personal database system supports a single application with a few tables, on one computer, for one user: simple. An enterprise-level database system supports many users at once and multiple applications, across many computers, with many tables and often many databases: complex. The difference the examiner wants is number of users, number of applications, and complexity.

WorkedPQ 25/26 Q3a

Q(i). Would you choose a database system instead of simply storing data in operating-system files? Justify with two points. Q(ii). When would it make sense not to use a database system?

(i) Yes, choose a database, because:

1. Controlled, consistent, shared access. A DBMS gives one shared copy of the data with concurrency control, so many users can read and write at once without corrupting it or duplicating it, which loose OS files cannot do safely.

2. Integrity, security, and independence built in. Constraints and access control are enforced centrally, and the layered architecture gives data independence, so the structure can change without rewriting every program. With OS files, all of this is left to hand-written code.

(ii) When not to use one

A database system carries cost and overhead (licensing, hardware, expertise, and slower simple access). For a small, single-user, single-application task with little data, few or no concurrency needs, and a fixed structure, plain files are cheaper and simpler, and a full DBMS is not worth its overhead. Real-time systems with very tight timing, or purely temporary data, are other cases where files can be preferable.
